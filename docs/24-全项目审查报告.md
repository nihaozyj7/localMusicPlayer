## 三、本轮修复明细（含证据与验证）

### 3.1 `cacheDir` 指向旧数据目录 → 缓存「消失」（用户报的第 2 条）

- **现象**：改过代码之后，之前匹配好的封面全部不见了；界面上 58 行歌曲**没有一行**显示封面。
- **根因**：`cacheDir` 在配置里是**绝对路径**。0.1.0 之前数据目录叫 `%APPDATA%\MusicPlayer`，
  改名时 `migrateLegacyDataDir` 把整个目录 rename 成 `LocalMusicPlayer`，但配置里那条绝对路径没跟着改。
  程序下一次启动又按老路径**新建了一个空的** `MusicPlayer\cache`，之后所有封面/歌词都写进那里；
  用户真正的缓存仍躺在 `LocalMusicPlayer\cache`，界面上一张都读不到。
- **证据**：`config.json` 的 `cacheDir = C:\…\MusicPlayer\cache`；
  统计 `metadata-cache.json` 的 41 条 `coverFile`：40 条只在 `LocalMusicPlayer\cache\covers`、
  1 条只在 `MusicPlayer\cache\covers`；扫描目录里 `covers` 的 mtime 也分成两批。
- **修法**：`internal/bootstrap/config.go` 新增 `repairLegacyCacheDir`（在 `normalize` 里调用）：
  只要 `cacheDir` 落在旧数据目录之内，就按同样相对位置映射到新数据目录，
  并把旧目录里**缺失**的文件补过去（不覆盖新目录里已有的，旧目录保留不删）。
  判据收得很窄，用户手动指到 `D:\cache` 这类合法配置不受影响。
- **回归测试**：`internal/bootstrap/cachedir_repair_test.go`（4 例：修正+合并、自定义位置不动、目录名认不出不动、空值）。
- **实测验证**：修复后重扫 → **58 行里 57 行有封面**（修复前 0 行）；
  `/cover/<hash>` 同源路由 40 张、元数据缓存 16 张、兜底 1 张。

### 3.2 元数据缓存载入失败 → 空表覆盖 + 封面全灭

- **现象**：一次瞬时读失败（杀软占文件 / 并发写 / 跨机器拷贝）就可能让整份元数据缓存与**全部内嵌封面文件**消失。
- **根因**：`loadCache` 的 4 条失败路径都是静默 `return`，内存里留下一个空表；
  `SaveCache` 随后把这个空表整份写回 `metadata-cache.json`；
  `pruneCoverCache` 又拿空表当「没有任何封面仍被引用」的依据，把 1 小时前的封面文件**全部回收**。
- **证据**：代码路径（`library.go` 236-254 / 341-367 / 376-390）；`cacheOnce` 让失败不会重试。
- **修法**：新增 `cacheUsable` 标志；载入失败时 `SaveCache` 直接返回错误、
  `pruneCoverCache` 直接 return，并留一份 `.broken` 现场。
- **回归测试**：`internal/library/cache_guard_test.go`（4 例：拒绝覆盖、拒绝回收、坏缓存下扫描仍可用、下载目录残留）。

### 3.3 下载目录被写进用户配置 → 旧下载目录永远是扫描根

- **现象**：改过下载位置之后，旧目录仍出现在「本地歌曲」里；严重时会出现两条同 id 不同 path 的文件夹（状态互相覆盖）。
- **根因**：`EffectiveFolders()` 会合成一条 `{id: "auto_downloads"}`，而 `Scan` 结束时把
  `m.folders`（就是 `EffectiveFolders()` 的结果）整体写回 `config.Folders`。
- **证据**：用户自己的 `config.json.broken` 里确实留着 `"id": "auto_downloads"`。
- **修法**：写回时滤掉 `DownloadFolderID`；`EffectiveFolders` 同时忽略配置里的历史残留并按当前 `DownloadDir` 重新合成。
- **回归测试**：`TestEffectiveFoldersDropsStaleDownloadFolder`。

### 3.4 内嵌封面永久 404（`covercache.URL` 不校验存在）

- **现象**：文件里明明有内嵌封面，界面只显示默认图。
- **根因**：`URL()` 只拼字符串（刻意不碰磁盘，因为列表里每首都调）；
  缓存目录一变，URL 仍指向不存在文件；命中元数据缓存的路径又不会重新解析文件，于是**永久**没有封面。
- **修法**：`covercache.Exists()` + `library.songFromCandidate` 复用缓存前先确认封面文件还在，
  不在就退回完整读取一次（自动把封面重新 Put 回当前目录）。
- **回归测试**：`internal/library/cover_selfheal_test.go`。

### 3.5 播放界面卡顿：`magia` 每帧同步布局（用户报的第 3 条）

- **现象**：播放详情页明显掉帧；用户感受是「帧率跟不上显示器」。
- **定位过程**（可复现）：
  1. 给 rAF 打桩计数：`classic` = **0 次/秒**（它没有帧循环），`magia` = **12~16 次/秒**；
  2. 逐样式量帧间隔（100Hz 档屏）：classic/immersive/minimal 9.6ms、anime 12~15ms、arcade 11ms、**magia 23~50ms**；
  3. CPU profile：**48% 采样落在 `magia` 的 `follow()`**（强制同步布局算在调用者账上），classic 同位置 96% 是 idle；
  4. 反复重挂 magia，帧率单调恶化（61 → 76 → 108ms），而 classic 全程稳定 9.7ms。
- **根因**：`follow()` 每帧「读 `scroll.scrollTop` → 写回」，而该滚动区里有 100+ 行、
  每行几十个字素 span（4000+ 元素，还叠着滤镜与混合模式）→ 每帧一次强制布局。
- **修法**：与 `lyrics-view` / `fx-lyrics` 对齐——只在**目标位置变化**时调一次
  `scrollTo({behavior:'smooth'})`，滚动交给合成器，JS 侧不再每帧读写 `scrollTop`。
- **答案**：这是**软件的问题**，不是 WebView2 / 浏览器的问题——同一个 WebView 里 classic 能跑满 103fps。
- **可复现工具**：新增 `tools/perf-skins.mjs`（对着带调试端口的真实应用逐个样式量帧间隔，`--profile` 附 CPU profile）。
- **⚠ 测量条件说明**：后续复测时本机后台负载明显升高（多个常驻进程占满 CPU），
  于是四个「整窗背景 + 逐字」样式的帧间隔从 12~23ms 变成 60~116ms，
  而同时刻 classic/immersive/minimal 仍然稳定 9.6ms。
  **跨时间的帧率数字不可直接对比**；上面的结论依据的是与负载无关的两组数据：
  ① 强制布局次数（`scrollTop` 访问 22 次/秒 → 0 次/秒）；
  ② profile 的占比（同一个 `follow` 从 46~48% 降到不再出现）。

### 3.6 歌词「匹配中 / 匹配失败」提示（用户报的第 4 条）

- **现象**：自动匹配期间（AI 清洗元数据时可能十几秒）显示的是「暂无歌词」，用户以为这首歌没歌词。
- **根因**：宿主只把「歌词文本」推给皮肤，匹配期间文本恒为空；
  去重判断也只比文本，状态从 matching → failed 时根本不会推。
- **修法**：
  - 宿主给歌词快照加 `status`（loading/matching/failed/none/ok）与 `statusText`，
    并在开始联网匹配前先推一次；**状态变化也参与「变了才推」**（`playerhost.js`、`desktop-wallpaper.js`）。
  - 皮肤包新增共享 `lyricsEmptyText()`，7 个内置样式统一走它（原来 6 份各自判断来源的副本已删）。
  - 歌词工作台的面板徽章也显示「歌词匹配中… / 歌词匹配失败」。
- **回归测试**：`frontend/tests/player-skins.test.js` 新增 3 例（状态映射、老宿主回退、空白 statusText）。

### 3.7 自动匹配优先等时长（用户报的第 4 条）

- **修法**：`internal/lyricsfetch` 新增 `orderByDuration`：在**分数已经接近**（分差 ≤18）的候选里，
  把时长与目标相差 ≤2s 的稳定提到前面；没有任何时长对得上的候选时**原样返回**，退化为纯按分数排序。
  只按分数加权做不到这件事（同名同时长不同的原唱 / 伴奏 / Live 是最常见的错配场景）。
- **回归测试**：`internal/lyricsfetch/duration_rank_test.go`（7 例，含「低分候选不能因时长被顶上来」与端到端 `Match`）。

### 3.8 磁盘上的旧第三方皮肤永久顶替内置样式（皮肤 id 双命名空间）

- **现象**：上面 3.5 的修复做完、重新构建之后，真机上的帧率**一点没变**，CPU profile 的热点仍然在
  `follow @ skin.js:947`。追查发现：profile 里的 `skin.js` 不是构建产物（无 hash），
  而是运行时从 `/skins/magia/skin.js` 加载的文件。
- **根因**：`magia` 早年是第三方样式，后来并入了内置；但用户数据目录里那份旧副本
  （`%APPDATA%\LocalMusicPlayer\player-skins\magia\skin.js`）**还在**。
  而 `registerSkin()` 是按 id 覆盖的，`discoverSkins()` 又在启动时无条件加载外部皮肤 ——
  于是磁盘上那份旧代码把内置样式**永久顶掉**。用户看到的一直是旧版，
  内置里修的一切（包括性能）都不会生效。
  这正是皮肤子报告里的 P1-1，本轮实测复现。
- **证据**：`Get-ChildItem %APPDATA%\LocalMusicPlayer\player-skins` → 存在 `magia\skin.js`
  （模块内 `id: "magia"`）；`performance.getEntriesByType('resource')` 里有 `/skins/magia/skin.js`；
  内置 magia 确实在 bundle 里（`frontend/dist/assets/index-BQWb5Z7E.js` 含 `mg-shell`）。
- **修法**：`loadExternalSkin` 拒绝注册与内置样式同 id 的外部样式，并抛出可读原因；
  宿主已有的失败清单会把它显示在设置的「样式加载失败」里，提示用户改目录名与模块内 id。
- **回归测试**：`frontend/tests/player-skins.test.js` 新增 2 例（同名拒绝 + 不同名正常注册/注销）。
- **给用户的动作**：可以手动删掉 `%APPDATA%\LocalMusicPlayer\player-skins\magia\`
  （那是旧版副本，内置样式已经包含它，而且更新）。

### 3.9 零依赖静态预览整页白屏（工程问题）

- **现象**：`node tools/dev-server.js` 打开的页面白屏，`tracks: 0`；依赖它的 10+ 个 headless 自检脚本全线失效
  （而它们各自只看退出码，所以长期没人发现）。
- **根因**：迁移到 Lit 之后，`dev-server.js` 的裸包名白名单里仍然只有 `sortablejs`。
- **修法**：改成「按包名白名单从 node_modules 解析 + `/vendor/*` 302 到真实文件路径」
  （后者是必须的：`@lit/reactive-element` 的入口文件里有相对 import，
  模块 URL 停在包名上时相对路径会被解析成 `/vendor/@lit/css-tag.js`，少一层必然 404）。
  顺带支持 `package.json` 的 `exports`/`module`/`main` 入口。
- **验证**：修复后整页正常渲染、逐样式帧率可量（见 3.5 的工具）。

## 四、已确认但本轮未修（按严重度）

> 下列条目**已复核成立**，修法写在子报告里；本轮为控制回归面没有动手。

1. **P1 · `settings-view` 的 `s.config` 依赖永不变化**（`ui/settings-view.js:191` + `store.js:1458/1578`）。
   配置是原地 `Object.assign` 修改，引用不变 → `sameDeps` 永远相等。
   最省事的修法是把两处改成 `state.config = { ...state.config, ...cfg }`（整体替换引用），
   或在 store 里维护 `configRev` 并加进各组件 deps。
2. **P1 · `magia` 没有实现 `interactive:false`**（全文 0 命中）。桌面背景歌词窗口里歌词行仍是
   `role="button"`、当前行 `tabindex="0"`，5 个监听器照挂。修法：按 `ctx.options().interactive`
   决定是否挂监听与写 `role/tabindex`。
3. **P1 · `audio.js` 取播放地址失败的失败分支不回滚**（`loadedFor` 已置位、`node.src` 未清、
   `state.playing` 未置 false）→ 上一首继续出声、这首永不重试。修法：失败时清 `loadedFor`/`src` 并置 `playing=false`。
4. **P1 · `tools/*` 自检脚本腐烂**：`ui-round2.mjs:450` 断言的 `#cover-url` 全仓不存在；
   `probe-live-settings.mjs:331+` 用不存在的 `#sp-play`；`origin-check.mjs:22-26` 把 Edge 候选写成 `chrome.exe`。
   修法：删掉这些断言或对齐选择器，并让脚本在「选择器找不到」时明确报错而不是静默失败。
5. **P1 · 队列面板 O(n²)**（`ui/panels.js:242-244` 每行 `state.queue.indexOf`）。
   修法：先建一次 `Map(id → index)`。
6. **P2 · `coverfetch` 的缓存与 `InvalidateCovers` 是死代码**（已复核）→ 要么接上，
   要么删掉以免误导（设置里的「清空封面缓存」目前是空操作）。
7. **P1 · 四个「特效样式」的帧开销远超其余样式（本轮只做了部分优化，仍未达标）。**
   实测（`tools/perf-skins.mjs`，同一轮里把 classic 插在中间做对照）：
   classic/immersive/minimal 稳定 9.6~10.0ms/帧（≈103fps），
   而 anime / arcade / magia / stage 是 40~105ms/帧。
   用 CDP 注入 CSS 做过逐项归因（anime 样式）：
   基线 85.9ms → 去掉 `.fxl` 的整区 `mask-image` 66.2ms → 再关掉每字素入场动画 43.3ms。
   也就是说**共享的 `fx-lyrics` 渲染器**占了大头：4000+ 个字素 span + 每行入场动画
   + 覆盖整个滚动区的遮罩。本轮已经做的优化：
   - `fx-lyrics.css`：整区 `mask-image` 换成上下两条固定高度的渐变覆盖层；
   - 入场 / 残影动画**去掉 `filter: blur()`**（只保留 transform + opacity，走合成器）；
   - 新样式 `stage`：去掉大面积的 `filter: blur()` 光晕、去掉 `mix-blend-mode: difference`、
     网纹不再进相机（避免每帧重新栅格化整层）。
   **但这三项在负载升高后的复测里没有体现出可见收益**（数字被后台负载淹没），
   所以它仍是待办。真正的解法是换渲染模型，而不是继续抠 CSS：
   用「前缀测量 + `background-clip: text` + mask 扫过」替代「每个字素一个 span + 每个字素一个动画」
   （Folia 的 `MonetWordSweep` / `PendoloSweepLine` 就是这么做的，见 `docs/20` 第四节）。
8. **P2 · 转码缓存只有内存账本**（`internal/media/server.go:78`）→ 600MB 预算跨进程失效，
   `cache\transcode` 磁盘无上限增长。修法：`SetCacheDir` 时清点 `tc_*.wav` 入表。
9. **P2 · `services_download.go` 的 `uniquePath` TOCTOU** + 同名任务共用 `target+".part"`。
   修法：受锁保护的路径分配 + `O_CREATE|O_EXCL`。
10. **已修**：皮肤报告 P1-1（外部皮肤顶替内置 id）见 3.8，不再列在待办里。
11. 其余 P2/P3（`ffmpeg.Reset` 不复位解包 `once`、`loudness` 先清 dirty 再写盘、
    `metacache` 持锁 fsync、`desktop_lyrics` 的 `posSaveSeq` 无锁、
    `anime/arcade` 不归还 `backgroundRoot`、皮肤 id 双命名空间…）见三份子报告。

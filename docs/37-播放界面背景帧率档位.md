# 37 · 播放界面背景动效帧率档位（流畅优先 / 性能优先）

> 起因：用户是 120Hz 屏，反馈「感觉卡卡的，怀疑被限制在 60fps」。
> 诊断见 [`docs/36-120Hz屏幕卡顿诊断报告.md`](36-120Hz屏幕卡顿诊断报告.md)。
> 本文件记录**修复方案与实现**。

---

## 一、问题定性（诊断结论回顾）

诊断确认三处**基于 60Hz 假设**的省电优化，在高刷屏上暴露为「不流畅」：

| 位置 | 原值 | 问题 |
|---|---|---|
| `arcanum.js:71` / `magia.js:1172` | `FPS_PLAYING = 45` | 注释自称「45 与 60 肉眼无差别」——**只在 60Hz 屏成立** |
| `arcanum.js:72` / `magia.js:1173` | `FPS_IDLE = 22` | 暂停时比屏幕慢 5 倍 |
| `fx-camera.js:74` | `maxFps: 60` | 注释自称「WebView 上 60 足够」 |

**关键澄清（用户指出，已核实）**：这些限制**只对播放界面背景（canvas/rAF）有意义**。
设置界面与曲库列表**不挂皮肤、没有 rAF 循环、deps 里也没有 `position`**，
天然就是满帧的 —— 它们本来就不受这些常量影响。

诊断阶段我在报告里把「250ms 量化」列为「最主要原因」，**这个说法需要修正**：
250ms 量化只影响**底栏进度条**与**推给皮肤的数据**，不影响设置界面/曲库列表的重绘。
详见 §四「与诊断报告的差异」。

## 二、实现方案

### 2.1 设置项

设置 → 外观 → **背景动效（播放界面）**，两个选项：

| 选项 | 值 | 行为 |
|---|---|---|
| **流畅优先**（默认） | `smooth` | 背景动画**不限帧**，跟随显示刷新率（120Hz 屏跑 120fps） |
| **性能优先** | `performance` | 恢复原有的省电预算：播放 45fps / 空闲 22fps |

**为什么默认「流畅优先」**：高刷屏用户最容易感知到的就是不够流畅；省电档随时可以自己切。

**作用域（文案里也写明了）**：只影响**播放详情页里由皮肤绘制的背景动画**。
设置界面、曲库列表、底栏等一律满帧，与此开关无关。

### 2.2 两档都保留的优化

**「暂停 6 秒后停帧」在两个档位下都生效**（`IDLE_STOP_MS = 6000`）。

它省的是「静止画面持续重绘」，与「流畅优先」不冲突 —— 暂停时画面本来就该静止。
这条不在帧预算的门控分支里，两个档位共用同一个收尾判断。

### 2.3 设计取舍：为什么宿主传「意图」而不是「数字」

宿主（`playerhost.js`）只告诉皮肤 `performanceMode: "smooth" | "performance"`，
**不传具体帧率数字**。理由：内置皮肤对「省电」的取舍各有判断
（arcanum/magia 用 45/22 两档，fx-camera 用 60fps 上限），宿主不该替它们决定。
宿主表达意图，皮肤自己落成具体帧率。

（`fx-camera` 额外提供了 `setMaxFps()`，因为它原来的上限是构造期常量、无法运行期切换。）

### 关键代码（arcanum / magia 的门控）

```js
const playing = inst.playing && inst.anim;
// smooth 档 minFrame = 0 ⇒ 下面的 `minFrame > 0` 恒假 ⇒ 每帧都画
const minFrame = inst.perfMode === "performance" ? 1000 / (playing ? FPS_PLAYING : FPS_IDLE) : 0;
if (!inst.last) inst.last = now - 1000 / 30;
const since = now - inst.last;
if (minFrame > 0 && since < minFrame - 1) { schedule(); return; }   // ← 只有性能档才会命中
```

**为什么用 `minFrame = 0` 表示「不限帧」**：门控条件本来就写成 `minFrame > 0 && …`，
把 0 当作「无预算」不需要新增分支，也不会误伤原有的暂停停帧逻辑。

## 四、与诊断报告的差异（一处自我修正）

`docs/36` §2.3 把「250ms 量化」列为「最主要原因」，并称它影响「进度条/歌词高亮」。
**这个定性不够准确**，需要修正：

| 界面 | 是否受 250ms 影响 | 原因 |
|---|---|---|
| 设置界面 | ❌ 不受影响 | 不挂皮肤、无 rAF、deps 无 `position` |
| 曲库列表 | ❌ 不受影响 | 同上（`track-table.js` 全文无 canvas/rAF） |
| 底栏**进度条** | ✅ 受影响 | `playerbar.js:111` 订阅 notify 后 `paintProgress()` |
| 详情页**歌词高亮** | ✅ 受影响 | 由推给皮肤的数据驱动 |
| 皮肤**背景动画** | ✅ 受影响（另有 45fps 上限） | 本轮修复对象 |

也就是说：**250ms 量化影响的是「播放相关的连续视觉元素」，不是「所有界面」**。
用户指出的作用域判断是对的。

**本轮未改 250ms 量化**，原因：
1. 它服务的是「按 250ms 一档推进度」，改成逐帧会让**每次 rAF 都写 store + notify**，
   对所有订阅者（含皮肤推送）产生 60~120 次/秒的负载 —— 需要单独评估；
2. 进度条本身的视觉载体是 `width` 过渡（`playerbar.css:274`），属**非合成器属性**，
   真要让它顺滑需要同时改 CSS 与推进频率，是一个独立的改动；
3. 用户本次要求的作用域是「播放界面背景」，250ms 不在其中。

**待定**：若用户仍觉得进度条「一跳一跳」，可单独做一轮（改推进频率 + 换 `transform: scaleX()`）。

## 五、验证

### 5.1 帧预算逻辑（复刻计算，实测输出）

```
=== arcanum / magia 皮肤帧预算 ===
  smooth       playing=true  animations=true  → 不限帧（跟随刷新率）   ✅
  smooth       playing=false animations=true  → 不限帧（跟随刷新率）   ✅
  performance  playing=true  animations=true  → 45.0 fps               ✅（原行为）
  performance  playing=false animations=true  → 22.0 fps               ✅（原行为）

=== fx-camera（anime 运镜）帧预算 ===
  smooth       minFrame=0.00ms  → 不限帧        ✅
  performance  minFrame=15.67ms → ≈60fps       ✅（原行为）
```

### 5.2 新增测试（6 个 Go 用例，全绿）

| 测试 | 钉住什么 |
|---|---|
| `TestSkinPerformanceModeNormalize` | 8 种输入（含空串、大写、空白、非法值）→ 非法值必须落 **smooth** |
| `TestSkinPerformanceModeDefaultIsSmooth` | 默认配置必须是流畅档 |
| `TestSkinPerformanceModeBackfillsLegacyConfig` | 旧配置（无该字段）经 `normalize` 补齐为 smooth |

**为什么专门测「非法值兜底成 smooth」**：如果兜底成 `performance`，
一个手改坏/拼错的配置会让用户莫名其妙回到省电档，表现是「我明明没开省电，怎么还是卡」
—— 这类静默降级最难排查。

## 六、给后续维护者的提醒

1. **`performanceMode` 的作用域只限皮肤背景。**
   新增任何「跟随刷新率」的开关前先确认：设置界面/曲库列表**不挂皮肤、无 rAF**，
   它们已经是满帧的。不要给它们套这个开关（会变成无意义的第二层限制）。

2. **`pushOptions()` 是逐字段比较，新增 options 字段必须同时加进去。**
   漏加的表现是「设置里改了，皮肤没反应」——而且是静默的。

3. **`fx-camera.setMaxFps()` 改完会清 `last`。**
   不要「优化掉」这一步：否则新预算会拿上一次的帧间隔去比，
   让切换后的第一帧被误判成「还没到下一帧」而多等一帧。

4. **桌面壁纸窗口只覆盖 `interactive`，不覆盖 `performanceMode`。**
   它同样是「皮肤在画背景」，应当与详情页保持一致；覆盖了会出现
   「详情页流畅、桌面上还是卡」的割裂表现。

5. **暂停 6 秒停帧在两个档位下都保留。**
   它省的是「静止画面持续重绘」，不是流畅度问题。若要改成「流畅档也不停」，
   需先想清楚：一张静止的桌面背景每秒重绘 120 次是纯浪费。

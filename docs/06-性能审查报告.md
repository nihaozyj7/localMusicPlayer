# 性能审查报告（启动 / 首屏 · 运行时）

- 审查对象：`C:\Users\Example\Desktop\项目合集\音乐播放器`（Go 1.25 + Wails v3 beta.14，前端原生 ESM + Vite 7）
- 审查方式：只读代码审查；本报告是唯一写入的文件，**未修改任何源码**。
- 结论摘要：启动慢的主因**不在浏览器**，而在 `main()` 里「创建窗口之前」的一串同步磁盘工作
  （5.9MB 元数据缓存解析 + 内置 ffmpeg 的 sha256/落盘）；内存大的主因是**整个曲库把内嵌封面
  当成 base64 data URL 常驻**，并且这份数据在 Go 内存、IPC 报文、JS 状态、DOM 里各存一份。
  运行时的严重问题集中在「每帧全表扫描」和「每次按键整表重建」两条。

## 0. 本机实测基线（用于量化影响）

| 项目                                | 实测值                                                                         | 取法                                                    |
| ----------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------- |
| metadata-cache.json                 | **5.86 MB**                                                                    | Get-Item "$env:APPDATA\MusicPlayer\metadata-cache.json" |
| 其中条目数                          | **56 首**                                                                      | 正则计 "modTime" 出现次数                               |
| 其中有内嵌封面的条目                | **40 首**                                                                      | "cover": "data: 出现次数                                |
| 封面 data URL 字符总量              | **5,845,780 / 5,862,819 ≈ 99.7%**                                              | 正则求和                                                |
| 首屏 JS/CSS 产物                    | index-_.js 248.2 KB、style-_.css 167.3 KB、modulepreload 的 index-*.js 68.2 KB | frontend/dist/assets                                    |
| $env:APPDATA\MusicPlayer\cache\meta | 1.23 MB                                                                        | 同上                                                    |

即：**一首歌的内嵌封面平均约 146KB base64**，而缓存文件的 99.7% 都是封面。下面所有「20k 曲库」的估算
都按同一比例线性外推（1000 首带封面 ≈ 146 MB）。

## A. 启动 / 首屏

### [P0] 冷启动在**主线程**同步解析 5.9MB 元数据缓存（含全部 base64 封面）

- **位置**：`internal/library/library.go:204`（`loadCache`），调用点 `main.go:80`（`library.NewManager`）
- **现象**：双击图标后到窗口出现之间完全没有反馈（此时窗口都还没创建）；库越大越明显，进程内存瞬间抬高。
- **证据**：

```go
  // main.go:80
  lib := library.NewManager(store)
  ...
  // main.go:253（窗口创建工作在这一切之后）
  state.window = app.Window.NewWithOptions(winOpts)
```

```go
  // internal/library/library.go:204
  func (m *Manager) loadCache() {
  	raw, err := os.ReadFile(m.cachePath())
  	if err != nil {
  		return
  	}
  	var cf cacheFile
  	if err := json.Unmarshal(raw, &cf); err != nil {
```

而缓存条目里带的是整张封面的 data URL：

```go
  // internal/library/library.go:48
  Cover    string `json:"cover,omitempty"` // data URL，体积大，能省则省
```

- **影响**：这是 `main()` 主 goroutine 上的**同步**读文件 + JSON 解析，发生在 `app.Window.NewWithOptions`
  之前，所以 100% 落在「首屏之前」。本机 5.86MB 约 30–80ms；按每首约 146KB 外推，1000 首 ≈ 146MB →
  解析 1–3 秒、峰值内存 = 条目结构 + 原始字节 ≈ 500MB+。注释自己写着「能省则省」，
  但封面实际占了缓存文件的 99.7%。
- **建议修法**：① 把 `loadCache()` 从 `NewManager` 挪到 `main.go:284` 的后台 goroutine（首帧不需要标签缓存）；
  ② 更彻底：`cacheEntry` 不再存 `Cover`，封面只由 `internal/metacache` 按需从文件读。
  行为变化：无（缓存只是加速手段，未命中就重新解析一次标签）。
- **验证方式**：`(Get-Item "$env:APPDATA\MusicPlayer\metadata-cache.json").Length` 看体量；
  `Select-String -Path metadata-cache.json -Pattern '"cover": "data:'` 数封面占比；
  代码路径 `main()` → `library.NewManager` → `loadCache` 与 `app.Window.NewWithOptions` 的先后顺序即可确认。

### [P0] 内置 ffmpeg 的 sha256 + 落盘被两处调用**拖回主线程**，且发生在窗口创建之前

- **位置**：`internal/ffmpeg/ffmpeg.go:150`（`writeCached`）、`:128`（`extractBundled`）、`:95`（`resolve`）；
  调用链 `main.go:82 → internal/loudness/loudness.go:114 → ffmpeg.Resolve()` 与
  `main.go:86 → internal/media/server.go:76 → ffmpeg.Resolve()`
- **现象**：首次启动（或换版本后首次启动）明显卡在「双击了但没窗口」；之后每次启动仍有一次全量哈希。
- **证据**：

```go
  // internal/loudness/loudness.go:112（main.go:82 同步调用，早于建窗口 main.go:253）
  m := &Manager{
  	dataDir: dataDir,
  	tools:   ffmpeg.Resolve(),
```

```go
  // internal/ffmpeg/ffmpeg.go:159
  sum := sha256.Sum256(data)          // ← 先哈希整份二进制
  short := hex.EncodeToString(sum[:8])
  name := fmt.Sprintf("%s-%s", short, BinaryName())
  target := filepath.Join(dir, name)

  // 已存在且大小一致 → 直接复用
  if st, err := os.Stat(target); err == nil && st.Size() == int64(len(data)) {
  	return target, nil              // ← 存在性检查却在哈希之后
  }
  ...
  if err := os.WriteFile(tmp, data, 0o755); err != nil {   // ← 首跑/换版要写整份
```

而它自己的注释是「放在启动流程里同步做会拖慢窗口显示，因此在后台 goroutine 里调用它」：

```go
  // internal/ffmpeg/ffmpeg.go:83
  // Prewarm 提前把内置二进制解包到磁盘。
  // 155MB 的解包需要一两秒，放在启动流程里同步做会拖慢窗口显示，
  // 因此在后台 goroutine 里调用它，完成后再 Resolve() 就能拿到路径。
```

但 `Resolve()`/`extractBundled()` 共用同一个 `sync.Once`（`ffmpeg.go:120`）：
主线程一旦先到（`loudness.NewManager` 就在 `main.go:82`）就自己把整份工作做完；
即使后台 goroutine 抢到 once，主线程的 `Resolve()` 也会**阻塞等待**它写完。

- **影响**：每次冷启动至少一次 sha256（仓库内嵌件 6.0MB，注释声称发布版 155MB）；
  首跑/换版还多一次 6MB–155MB 写盘 + rename。按 155MB 估算哈希 0.2–0.5s、写盘 1–3s，
  **全部发生在首屏之前**（`app.Run()` 在 `main.go:300` 才被调用）。
- **建议修法**：把「解包」与「探测」解耦——`resolve()` 先 `os.Stat` 目标文件（用大小比较），
  命中直接返回，未命中才 `sha256`/写盘；并让 `loudness.NewManager`/`media.New` 接受「稍后注入」的 tools
  （或读取 `Prewarm` 完成后写入的原子值），使 `Resolve()` 在启动路径上永不阻塞。
  行为变化：启动瞬间 ffmpeg 可能短暂不可用（`ffmpeg:ready` 事件本来就在后台发，前端已按可用/不可用渲染）。
- **验证方式**：把 `MUSICPLAYER_FFMPEG_DIR` 指到空临时目录，用 `Measure-Command` 计首次启动时间；
  或在 `writeCached` 入口/出口打 `log.Printf` 时间戳，对照 `main.go:253` 的建窗口日志。

### [P1] 每帧多次 O(n) 线性查找（`songById` = `state.songs.find`）

  或读代码确认 `Scan` 内的多次调用。

## D. 附带发现（非性能，但同源风险）

### [P2] 主题注册表在读/写两侧都没有加锁（并发 map 读写在 Go 里是致命错误）

- **位置**：`internal/theme/theme.go:141`（`List` 读 `m.order`/`m.byID`）与 `:135`（`Reload` 整体替换）
- **证据**：

```go
  // internal/theme/theme.go:141
  func (m *Manager) List() []Info {
  	out := make([]Info, 0, len(m.order))
  	for _, id := range m.order {
  		out = append(out, m.byID[id])
```

```go
  // internal/theme/theme.go:135
  	m.byID = byID
  	m.order = order
```

- **影响**：`/early-theme.js` 的 HTTP handler 每次请求都走 `themeExists → mgr.List()`（`early_theme.go:150`），
  而 `ThemeService.Reload/Delete/Import` 会在任意时刻替换这两张 map。并发读+写 map 会直接
  `fatal error: concurrent map read and map write`（进程崩溃，不可恢复）。
  这不是性能问题，但属于读代码时必报的严重缺陷。
- **建议修法**：给 `Manager` 加 `sync.RWMutex`，`List/CSS/BuiltinIDs` 用 RLock、`Reload` 用 Lock。
- **验证方式**：`go test -race ./internal/theme`；或在界面上一边刷新页面一边点「重新扫描主题」。

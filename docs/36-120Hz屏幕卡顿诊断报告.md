> **结论先说：不是你的错觉，也不是系统问题，更不是 60fps 上限——是应用自己把画面按 45fps / 22fps / 4Hz 三档限死了。**

## 0. 一句话回答你的怀疑

你怀疑「被限制在 60fps」——**方向对了，但具体数字比 60 更糟**：

| 你看到的画面 | 实际帧率 | 上限来源 |
|---|---|---|
| 播放详情页（arcanum 皮肤）动画 | **45fps** | `arcanum.js:71` `FPS_PLAYING = 45` |
| 暂停时的动画 | **22fps** | `arcanum.js:72` `FPS_IDLE = 22` |
| 暂停 6 秒后 | **0fps**（完全停） | `arcanum.js:73` `IDLE_STOP_MS = 6000` |
| **进度条 / 歌词高亮 / 桌面歌词** | **4 次/秒** | `audio.js:340` 的 250ms 量化 ← **这才是「卡卡的」最主要来源** |
| anime 皮肤的运镜 | 60fps | `fx-camera.js:74` `maxFps: 60` |
| 频谱柱状 | 30Hz | `playerhost.js:1314` `SPECTRUM_HZ = 30` |

**120Hz 屏幕意味着一帧 8.33ms。而进度条每秒只动 4 次——每次间隔 250ms，恰好是 30 帧。** 这必然看起来是「一跳一跳」的。

## 2. 实测到的三档「限帧」（源码逐行核对）

### 2.1 皮肤动画：45fps / 22fps / 6 秒后完全停止 ✅ 确认

```js
// frontend/packages/player-skins/src/skins/arcanum.js:66-73（注释原文）
//   播放中 45fps（法阵转得很慢，45 与 60 肉眼无差别，但省掉四分之一的合成）
//   暂停中 22fps（只有粒子在飘、法阵在慢慢变暗）
//   暂停超过 6 秒 → 画完最后一帧彻底停下（用户的电脑不该为一张静止画面转风扇）
const FPS_PLAYING = 45;
const FPS_IDLE = 22;
const IDLE_STOP_MS = 6000;
```

门控逻辑 `arcanum.js:1079`：

```js
const minFrame = 1000 / (playing ? FPS_PLAYING : FPS_IDLE);
```

**【事实】** 作者写下「45 与 60 肉眼无差别」——**在 60Hz 屏上确实如此，但在 120Hz 屏上不成立**。这是一条基于 60Hz 假设的优化，正是你感觉不对的根源之一。

**【事实】** 你现在用的皮肤正是 `arcanum`（本机 `config.json` 实测 `playerViewMode: "arcanum"`）。
`magia.js:1172-1174` 有同样的三个常量。

### 2.2 anime 皮肤的相机：硬编码 60fps ✅ 确认

```js
// frontend/packages/player-skins/src/fx-camera.js:73-74
/** 帧率上限（folia 的 frameRateLimiter 思路；WebView 上 60 足够） */
maxFps: 60,
```

同一个 60Hz 时代假设，注释直说了「60 足够」。

### 2.3 **进度条 / 歌词高亮：每秒只更新 4 次** ← 最主要原因 ✅ 确认

```js
// frontend/src/js/audio.js:338-341
// 250ms 量化：与 audio.js 原来 runtime.js 的依赖键频率一致，
// 歌词高亮与进度条不需要更细。
if (!force && Math.round(rounded / 250) === Math.round(lastPushedPosition / 250)) {
  return;   // 丢掉这 250ms 内的所有中间值
}
```

```js
// frontend/src/js/audio.js:245
tickTimer = setInterval(extrapolate, 250);   // 位置本身也只每 250ms 采一次
```

```js
// frontend/src/js/runtime.js:32-33
// 250ms 一档：歌词高亮 / 桌面推送不需要更细
Math.round((state.position || 0) / 250),
```

**【事实】** 三层都卡在 250ms：采样（`setInterval`）、量化（`pushPosition`）、依赖键（`runtime.js`）。
**⇒ 不管屏幕是 60Hz 还是 120Hz，进度条每秒走 4 格。** 120Hz 下每格之间隔 30 帧，视觉上就是明显的「一顿一顿」。

**这一条比 45fps 更值得优先修**，因为进度条是最连续的视觉元素——它「跳」，整机就「显得卡」。

### 2.4 频谱：30Hz

```js
// frontend/src/js/playerhost.js:1314
const SPECTRUM_HZ = 30;
```
（仅 arcanum 用，且画在 canvas 上）

### 2.5 还有两处 60fps 时代的 `dt` 钳制

| 位置 | 代码 | 含义 |
|---|---|---|
| `magia.js:1219` | `const dt = Math.min(50, since);` | 单帧最大按 50ms 算（=20fps 下限的经典写法） |
| `arcanum.js:1086` | `const dt = Math.min(0.1, since / 1000);` | 最大 100ms |

这两条本身不会限帧，但说明整套时间步进是按「帧间隔约 16.7ms」设计的。

### 2.6 加重因素：全窗 `filter: blur()` 在 2560×1440 上的每帧成本

| 位置 | 值 |
|---|---|
| `arcanum.css:428` | `filter: blur(44px) saturate(1.4) brightness(0.5)` |
| `background-layer.css:56` | `filter: blur(var(--skin-bg-blur))` |
| `arcanum.css:165-166` / `magia.css:145-146` | `backdrop-filter: blur(...)` |
| 本机 `config.json` | `glassBlur: 18` |

**【事实】** 全屏大半径模糊是每帧最贵的操作之一。它**不会把帧率限到某个数字**，但会拉长每帧耗时——所以即使把 45 改成 120，也可能因为单帧成本太高而达不到。

## 3. 判定：不是错觉，是应用自查可证的设计选择

| 你的怀疑 | 判定 |
|---|---|
| 「感觉卡」 | ✅ **真实存在**，有源码依据 |
| 「被限制在 60fps」 | ⚠️ **部分正确但低估了**：皮肤是 **45fps**，UI 是 **4Hz**，相机才是 60fps |
| 「是系统问题」 | ❌ **不是**：120Hz 生效、GPU 加速开、无省电限制、无驱动异常 |
| 「是显示器/线材问题」 | ❌ **不是**：`Win32_VideoController` 报告 120Hz 且驱动正常 |
| 是 WebView2 的锅 | ❌ **不是**：GPU 进程正常运行，无软件渲染 |

**根因排序（按对「卡」的贡献）**：
1. **250ms 量化（4Hz）** —— 进度条/歌词每秒只动 4 次，最刺眼
2. **45fps 皮肤上限** —— 详情页动画比屏幕慢 2.7 倍
3. **全屏 `blur(44px)` 的每帧开销** —— 拉长帧时间，可能长到吃满 8.33ms 预算
4. 30Hz 频谱 / 22fps 暂停档 / 6s 停帧 —— 影响较小（暂停时本来就该静）

## 4. 建议怎么改（**全部非破坏性**，不需要动系统）

> ⚠️ 你明确要求不做破坏性变更、不碰系统——**以下改动全部只涉及应用自己的源码**，不动注册表、不动显卡设置、不动系统电源计划。而且它们都**可一键回退**（改的都是常量）。

### 优先级 1（收益最大，风险最低：**只改数字**）

| 改动 | 位置 | 从 → 到 | 效果 |
|---|---|---|---|
| 进度/歌词量化 250ms → 帧同步 | `audio.js:340`、`audio.js:245`、`runtime.js:33` | 250 → 按 rAF 或 ~16ms | 进度条从 4Hz 变顺滑（**最明显**） |
| 皮肤播放帧率 | `arcanum.js:71`、`magia.js:1172` | `45` → `60` 或 `120` | 详情页动画跟满屏幕 |
| 皮肤空闲帧率 | `arcanum.js:72`、`magia.js:1173` | `22` → `30` | 暂停时更顺（仍是省电档） |
| anime 相机 | `fx-camera.js:74` | `60` → `120` | 运镜跟满屏幕 |

**注意**：这些常量当初是**为了省 CPU 而刻意压低的**（注释写明了「省掉四分之一的合成」和「用户的电脑不该为一张静止画面转风扇」）。改成高帧率会让 CPU/GPU 占用上升——**建议做成可配置项**，而不是直接改死。

### 优先级 2（需要设计决策，建议先测再改）

- **全屏 `blur(44px)` / `backdrop-filter`**：可以只在「不需要模糊的皮肤」上关掉，或降半径。这需要视觉确认。
- **`glassBlur: 18`**：这是你自己的设置项，**可以直接在界面里调小或关掉**试手感——零风险。

### 优先级 3（我可以直接给你做，但需要你确认）

我**没有**擅自改这些常量，因为：
1. 它们是有意的省电设计，改成 120fps 会明显增加功耗与风扇转速；
2. 你要求不做破坏性变更，而「提高帧率」在低端机上可能导致更严重的掉帧（单帧成本超过 8.33ms 时反而更卡）。

**建议做法**：把上面这几个常量接到一个「动画流畅度」设置项（跟随屏幕 / 60fps / 省电），默认跟随屏幕刷新率。这样既解决你的问题，又不牺牲省电档。

## 5. 当时为什么没测成「实机 CDP 帧率」（过程说明）

我原本想用仓库自带的 `tools/perf-skins.mjs` 对你的实例采样 rAF 帧间隔（那是**直接测量**，比读源码更硬）。但遇到两个障碍：

1. **仓库自带工具需要 `LMPLAYER_DEBUG_PORT`**，而实测发现 **Wails v3 beta.14 并没有把 `browserArgs` 里的 `--remote-debugging-port` 传给 WebView2**——我检查了实际 WebView2 命令行，**只有 `--embedded-browser-webview` 等参数，没有调试端口**。所以这个调试通路在当前框架版本下是失效的（这本身是一个值得记录的发现）。
2. 我尝试启动带调试端口的新实例时，**误判了 PID**：把 `22912` 当成自己启动的测试实例清理，实际上它是**你正在运行的那个窗口的渲染进程**（启动时间 18:25:46 属于你的实例，我的实例在 18:27）。你已经主动关闭了那个窗口，未造成持久影响（配置与音乐文件全程未改动），但这是我的操作失误——清理进程前应当先核对父进程 PID。

**因此本报告的结论依据是源码逐行核对 + 环境实测，而非实时帧采样。** 不过对「是否存在限帧」这个问题，源码里的常量是**确定性证据**——`FPS_PLAYING = 45` 这一行就足以证明上限存在，不需要再采样。

### 如果你想补上实机帧率数据（可选，我可以做）

不必依赖那个失效的调试端口，有两个更可靠的办法：
- **A. 用 `LMPLAYER_DEBUG_PORT` 之外的方式**：临时在 `main.go` 里把端口号写进 `browserArgs`（当前是「读了环境变量但没生效」），跑一次 `perf-skins.mjs` 取真实帧间隔，然后回退。
- **B. 零改动方案**：用 Windows 自带的**任务管理器 → 性能 → GPU**，或 AMD 驱动面板的帧率计数器，观察播放时的实际出帧；也可以看「桌面背景歌词」窗口是否在出帧。

## 6. 结论

1. **你的感觉是对的**，而且比「60fps 上限」更严重——是 **45fps + 4Hz** 的双重限制。
2. **系统完全正常**：120Hz 生效、硬件加速开启、无省电限制、驱动正常。**不需要改任何系统设置。**
3. **根因是三处刻意的省电优化**（写在注释里、基于 60Hz 假设），在 120Hz 屏上暴露了。
4. **修复成本很低**：改动集中在 4~6 个常量 + 一处量化逻辑，全部可回退，且建议做成设置项而非改死。
5. 本次**未修改任何源码、未改动任何系统设置**；仅有的副作用是我误杀了一个渲染进程（你已关闭窗口），已说明并致歉。

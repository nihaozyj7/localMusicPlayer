# 歌词工作台 设计方案（产品 + UI + 交互）

> 本文是「动手之前」的那一步：先把功能和界面想清楚，再实现。
> 实现完成后的差异与验证记录见本文件末尾的「实现对照」。

---

## 1. 现状与要解决的问题

| 现状                                                         | 问题                                                                                           |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 底栏有一个「手动匹配歌词」按钮，点开是一个只有搜索框的小面板 | 能力太窄：只能在线匹配。匹配到的歌词**时间轴不对**（不同版本前奏长度不同）时，用户没有任何办法 |
| 歌词时间轴整体偏移在别处无解                                 | 只能换一个候选碰运气，或者放弃                                                                 |
| 完全没有手动编辑                                             | 冷门歌（没有在线歌词）永远显示「暂无歌词」；用户手里明明有歌词文本（贴吧、专辑内页、视频简介） |
| 桌面歌词窗口每次启动都回到默认位置                           | 用户把它拖到副屏/左上角，重启后又跑回屏幕底部中间，每次都要重拖                                |

所以这次做两件事：**把「匹配歌词」升级成「歌词工作台」**，以及**桌面歌词位置记忆**。

---

## 2. 信息架构

```
底栏按钮：词 → 「歌词」                   ← 改名（原来叫「手动匹配歌词」）
└─ 歌词工作台（右侧抽屉面板，宽 720px）
   ├─ [在线匹配]  搜索候选 → 试听/应用（**行为完全不变**）
   ├─ [微调]      整首歌的时间轴整体提前 / 延后
   └─ [手动编辑]  粘贴歌词 → 边听边打轴 → 保存
```

**为什么是抽屉而不是全屏层**：打轴时必须能看见/操作底栏的播放控件（播放、上一首、
进度条）。抽屉从上方 52px 起、到底栏上方 90px 止，底栏完整露出来。宽度从 520px
放宽到 720px，因为手动编辑器要同时放「文本区 + 行列表 + 走带」。

**为什么三个 tab 而不是三个入口**：这三件事是**同一条工作流的前后步** ——
先匹配（拿到一份歌词）→ 不对就微调 → 差得太多就自己打轴。放在一个面板里，
用户不用回到底栏换按钮，而且「保存后立刻能看到效果」这件事天然成立。

**三个 tab 的共同上下文**：都作用于「当前播放的这首歌」（`state.currentId`）。
面板顶部固定显示当前曲目（封面 + 标题 + 歌手 + 现有歌词来源徽标），
让用户始终知道自己在改哪首。切歌时面板跟着切，编辑中的未保存内容给出提示。

---

## 3. Tab 1：在线匹配（保持现状）

内容与逻辑**一行不改**，只把它从「一个独立面板」搬进 tab 里：
关键词输入框 → 搜索 → 候选列表（标题/歌手/来源/评分/时长）→ 「使用」。

新增一件小事：顶部曲目信息里显示**当前歌词来源**（内嵌 / .lrc 文件 / 缓存 /
在线 / 暂无），因为后面两个 tab 都要靠它来判断「保存后能不能生效」。

### 3.1 候选区的四种状态（空状态也要有话说）

候选区不再是「一行灰字」，而是四种居中的状态卡片（`[data-online-state]`）：

| 状态        | 触发                  | 内容                                                                                        |
| ----------- | --------------------- | ------------------------------------------------------------------------------------------- |
| `idle`      | 打开面板、还没搜过    | 放大镜图标 + 「还没有开始搜索」+ 一句说明 + 主按钮「搜索歌词」                              |
| `searching` | 搜索进行中            | 转圈图标 + 「正在搜索…」；搜索按钮同时变成「搜索中」并禁用，回车也能搜                      |
| `error`     | 接口报错 / 服务不可用 | 警告图标 + 「搜索失败」+ 人话解释 + 原始报错（小字，留给排查）+ 「重试」「手动编辑歌词」    |
| `empty`     | 搜过但没有候选        | 歌词图标 + 「没有找到候选歌词」+ 「只用歌名重搜」（关键词里带歌手时才有）+ 「手动编辑歌词」 |

搜到候选时显示候选列表（与旧版一致）。空/失败状态里的两个出口都直接落到
对应的 tab，用户不必自己回到顶部点页签。

## 4. Tab 2：微调（整体时间轴偏移）

### 4.1 用户要解决的问题

「这首歌的歌词比声音快了大约半秒。」

### 4.2 界面

界面里**只留操作，不留说明文字** —— 解释性内容全部收进右下角的「说明」按钮
（见 4.6）。预览区因此能占满剩下的高度。

```
┌ 微调 ──────────────────────────────────────────────────────┐
│ 偏移  0.00 秒  ● 未应用           [−1.0][−0.5][−0.1][+0.1][+0.5][+1.0] │
│ [歌词快了 → 延后 0.5s]  [歌词慢了 → 提前 0.5s]  ├──●────┤   │
├────────────────────────────────────────────────────────────┤
│  00:35.10  上一句…                                        ▲ │
│ ▸00:38.60  当前这一句…   ← 高亮 + 自动滚到中部（整首歌）    │ 可
│  00:42.05  下一句…                                        ▼ │ 滚
│  …                                                         │ 动
├────────────────────────────────────────────────────────────┤
│ [重置] [ⓘ 说明]                            [应用到歌词（永久）] │
└────────────────────────────────────────────────────────────┘
```

### 4.3 交互细节

- **立即生效**：每点一次按钮/拖一次滑条，高亮行**当场**跟着变（不是等保存）。
  实现上是一个「待应用偏移」，只作用于渲染时的定位，不改歌词文本。
- **未应用标记**：偏移 ≠ 0 时读数旁显示「● 未应用」（离开本页会丢弃未应用的调整）。
- **滑条量程** ±10 秒、步长 0.05 秒（50ms，比人耳可辨的阈值更细）；
  按钮是给「听感校准」用的快调，滑条是精修。
- **两个听感按钮**的文案刻意写成因果句而不是「提前/延后」：
  用户看到的现象是「歌词跑在声音前面」，动作是「让它晚一点出来」。
  只写「提前/延后」会让用户在心里做一次反向换算，很容易点反。
- **预览列表是整首歌**（不是「当前行 ±5 行」的窗口），显示**偏移后**的时间；
  高亮的正是**当前播放位置**对应的那一句，跟着播放实时走（不额外重渲染，
  由 store 的订阅回调里改 class + 滚动），点某一行会把播放跳到那一行的
  （偏移后）时间，方便反复核对同一句。
  早期版本用「±5 行窗口 + 每次重渲染」实现跟随，结果是：当前行还没进入第一句
  时（`active = -1`）会**无限重渲染**，而且窗口重新居中会让列表自己乱跳。
- **跳转必须走 `audio.js#seekTo`**（= `store.seek` + `seekAudio`）：只调
  `store.seek` 的话进度条会先动一下，然后被下一次位置外推按**真实播放位置**
  拉回去（那个 `player:seek` 事件没有任何订阅者）—— 表现就是「进度条跳一下
  又跳回去」，听感上等于点了没反应。
  微调预览、编辑页行列表、编辑页 −5s/+5s 三处都是这么接的；
  `frontend/tests/seek-must-reach-audio.test.js` 用源码扫描守着这条。
- **重置**：偏移归零，回到进入本页时的状态。
- **应用到歌词（永久）**：把偏移**烙进时间戳**（每行时间 + offset），写回歌词
  缓存，然后读数归零、提示「已应用」。烙进去而不是存一个「偏移量」，
  是为了让桌面歌词、桌面背景歌词、第三方皮肤都自动看到同一份结果 ——
  它们各自都有读取路径，存偏移量意味着每一处都要记得加一次。

### 4.4 边界与保护

| 情况                                      | 处理                                                                                                                                          |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 没有歌词                                  | tab 内容替换为空态：「这首歌还没有歌词」+ 「去在线匹配」「去手动编辑」两个跳转按钮                                                            |
| 歌词是字级（逐字/QRC）                    | 保存时归一化成**增强 LRC**留在缓存里（逐字时间轴不丢，来源徽标会标「逐字」），微调连 `<00:12.000>` 一起平移；只有写进歌曲文件那一步才剥成行级 |
| 时间被推成负数                            | 允许：偏移恒定 ±10s，被压到 0:00 的行由 `shiftLrc` 钳住，读数旁提示「有 N 行被压到 0:00」                                                     |
| **歌词来源是「音频内嵌」或「同名 .lrc」** | **必须提示**：这两者在本程序的读取优先级里**高于缓存**，只写缓存的话下次打开还是旧歌词。见 4.5                                                |
| 离开了面板没保存                          | 丢弃（并在未保存时给出提示），不做静默持久化                                                                                                  |

### 4.5 关于「保存后不生效」这个坑（重要）

本程序的歌词读取顺序是（`internal/lyrics/lyrics.go`）：

```
内嵌歌词  →  同名 .lrc  →  本程序缓存  →  在线匹配
```

用户手动编辑/微调的结果只能写进**缓存**，而缓存排在第三位。因此对
「带内嵌歌词」或「有同名 .lrc」的歌，只写缓存会导致**下次打开又变回旧歌词**。

产品上的处理是**明说 + 给出口**，而不是假装没问题：

- 面板顶部一直显示当前来源徽标；
- 保存时如果来源是 `embedded` / `lrc-file`，弹出确认框：
  「这首歌的歌词来自音频内嵌（或同名 .lrc 文件），它的优先级高于程序缓存。
  只保存到缓存的话，下次打开仍会显示旧歌词。」
  给三个可选动作：
  1. **写入歌曲文件并保存**（走现有的内嵌写入，m4a / flac 支持）——推荐；
  2. **只保存到缓存**（用户知道自己在做什么，例如他打算自己删掉 .lrc）；
  3. 取消。
- 格式不支持写标签（mp3 / wav / ogg）时，第 1 项改成「另存为同名 .lrc 文件」——
  .lrc 的优先级高于缓存，同样能生效（见下）。

> 「另存为 .lrc」需要一个后端新方法（把歌词写成 `同名.lrc`）。
> 这是本方案里唯一的新增后端能力，优先级放在微调/编辑之后实现。

### 4.6 「说明」按钮（介绍与指引的出口）

微调这件事不解释就没法用（哪边是快、点哪个按钮、预览怎么读），但**把这些文字
铺在面板里会把预览区挤没**。所以板面上只留操作，说明集中在底部「重置」右侧的
`[ⓘ 说明]`：点开是一个 `modal--wide modal--scroll` 的弹层，六节：
微调在改什么 / 怎么判断该往哪边调 / 界面上的数字 / 预览区怎么用 / 微调还是手动编辑 /
什么时候真的写进去。弹层只留「知道了」（`modal--single` 藏掉取消按钮），关掉就回到板面。

## 5. Tab 3：手动编辑（贴歌词 → 打轴 → 保存）

这是三个 tab 里最复杂的一个，也是本次的重点。

### 5.1 用户要解决的问题

手里有一份纯文本歌词（没有时间），或者有一份时间不对的 LRC，
需要在听歌的同时把每一行的起始时间标出来。

### 5.2 界面（分三块：走带 / 打轴 / 行列表）

**文本编辑器不常驻板面**，而是收在左上角 `[✏ 编辑歌词文本]` 的弹层里 ——
这个界面的主要用途是**打轴**，常驻一个占了半屏的文本框会把行列表挤到看不见。

```
┌ 手动编辑 ─────────────────────────────────────────────────┐
│ [✏ 编辑歌词文本]  共 28 行              [清空全部时间]      │
├───────────────────────────────────────────────────────────┤
│ ▶/⏸  −5s  +5s   位置 00:38.60   已打轴 12 / 28           │
│         ┌─────────────────────────────────┐               │
│         │   打轴并下一行   （空格）        │               │
│         └─────────────────────────────────┘               │
│ [撤销 ⌘Z]  [上一行] [下一行]                              │
├───────────────────────────────────────────────────────────┤
│  #   时间         歌词                                     │
│  11  00:35.10     上一句                                   │
│ ▸12  00:38.60     当前这一句        ← 高亮 + 自动滚到中部   │
│  13  未打轴        下一句                                  │
│                                     [从这里播放][清除时间] │
│                            [复制 LRC]  [保存并应用]        │
└───────────────────────────────────────────────────────────┘

「编辑歌词文本」点开（modal--wide modal--scroll）：
┌ 编辑歌词文本 ─────────────────────────────────────────────┐
│ 一行一句；已打过轴的行会自动带上 [mm:ss.xx] 时间标签        │
│ 共 28 行                 [载入当前歌词] [清空文本]          │
│ ┌───────────────────────────────────────────────────────┐ │
│ │ [00:12.34]第一句                                      │ │
│ │ 第二句                  ← 纯文本也能粘，自动编号         │ │
│ │ 第三句  [00:15.00]也可以直接写时间标签                  │ │
│ └───────────────────────────────────────────────────────┘ │
│                                        [取消]  [应用文本]  │
└───────────────────────────────────────────────────────────┘
```

### 5.3 核心流程（用户描述的那套，逐字落到界面上）

1. **粘贴或编写**：点「编辑歌词文本」在弹层里粘歌词（板面放不下文本框）。
   带不带时间标签都行 —— 带的话会被解析出来并填进行列表（= 在现有歌词上继续改）。
2. **点「应用文本」**：行列表按新文本重建（**按行文本匹配保留已打轴的时间**，
   见 5.5），已有的时间标签会被识别；没有的就是「未打轴」。
   文本为空时弹层不关，提示「没读到歌词文本」。
3. **一边播一边定位**：播放音乐（面板里的 ▶/⏸，或者直接按底栏的、
   或者用全局快捷键）。听清当前这一行唱到时，
4. **点「打轴并下一行」（或按空格）** → 把**当前播放时间**写进当前行的开头，
   **选中行自动进入下一行**。重复到打完。
5. **保存并应用** → 生成标准 LRC 写回歌词缓存，界面立刻生效。

> 弹层每次打开都会带出**当前草稿**（没有草稿才是这首歌已有的歌词文本），
> 「载入当前歌词」= 放弃草稿内容、回到这首歌当前生效的那份文本。

### 5.4 交互细节（含「打错了怎么办」）

| 操作                     | 效果                                                                                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 点「打轴并下一行」/ 空格 | 当前行 ← 当前播放时间；选中行 +1                                                                                                                                |
| `Backspace` / `Delete`   | 清除当前行的时间（选中行不动）                                                                                                                                  |
| `↑` / `↓`                | 选中行上/下移（已打轴的可以回头重打）                                                                                                                           |
| `Ctrl+Z` / 点「撤销」    | 回退上一次时间改动（撤销栈保留 50 步）                                                                                                                          |
| 点某一行                 | 选中该行并滚到可视区中部；**已打轴的行同时把播放跳过去**（未打轴的行只选中不跳，避免整片新文本被带到上一句的位置），并挡住自动跟随 4 秒，免得刚点中的行又被滚走 |
| 点行内「从这里播放」     | 播放跳到该行（未打轴则跳到上一行的位置）                                                                                                                        |
| 点行内「清除时间」       | 只清这一行                                                                                                                                                      |
| 双击时间徽标             | 直接手输时间（`mm:ss.xx`），给「我知道它应该是 1:23 但不想听」的情况                                                                                            |
| 文本弹层「应用文本」     | 重建行列表，但**按行文本匹配保留已打轴的时间**（见 5.5）；文本为空则不关弹层                                                                                    |

**按键冲突**：空格是本程序全局的「播放/暂停」。所以打轴态下，
面板在 `keydown` 捕获阶段拦截空格并 `preventDefault()`，
且**焦点在文本框/输入框里时不拦截**（那种情况空格应该是打字）。
另外额外支持 `S` 键作为无冲突的第二选择。

**为什么用「当前播放时间」而不是「点下去的那一刻自己计时」**：
真正要对齐的是音频位置，直接取 `state.position`（后端/audio 元素给的播放位置）
最准。用户按下按钮的几十毫秒延迟在 10ms 精度下可以忽略，而它换来的是
「可见即可得」：打轴时面板上就显示着这个数，用户能立刻发现取错了值。

### 5.5 文本 ↔ 行列表的同步规则（关键设计）

用户在打轴途中改文本（改错别字、补一行）是很常见的，不能因此把已打的时间全丢掉。
规则（在弹层点「应用文本」时执行一次；板面不常驻文本框，所以也没有「边打字边重建行列表」的去抖路径）：

1. 文本按行切分 → 新的行列表；
2. 对每一行新文本，在**旧列表里找尚未被占用、且文本完全相同**的行：
   - 优先取**同下标**的（用户只是改了一个字，位置没动）；
   - 否则取最近的同类行（对应「插入/删除了一行」，后面的时间整体跟着走）；
3. 找不到就不带时间（未打轴）。

重复行（副歌两句一模一样）由「未占用优先 + 就近取」自然处理，
不会出现两行抢同一个时间戳。

### 5.6 保存规则与边界

| 情况           | 处理                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| 全部行都已打轴 | 直接保存                                                                                                             |
| 有行未打轴     | 保存前确认：「还有 N 行没有时间，保存后这些行不会显示（LRC 里没有时间标签的行会被忽略）。」→ [继续保存] / [返回打轴] |
| 一行都没有时间 | 不允许保存，提示「至少要先给一行打上时间」                                                                           |
| 时间不是升序   | **允许保存**（有些歌词确实会回退/重复），但保存前提示一次「时间不是升序，播放时高亮可能跳来跳去」                    |
| 文本里全是空行 | 空态提示，禁用保存                                                                                                   |
| 保存后         | 生成 `[mm:ss.xx]正文` 逐行、按时间升序；写缓存 + 按设置决定是否内嵌；关闭面板并 toast「歌词已保存」                  |
| 保存失败       | 保留编辑内容 + 错误提示（绝不能把用户的工作清掉）                                                                    |

**时间格式**：`[mm:ss.xx]`（百分秒）。LRC 事实标准是百分秒，
现有解析器也支持 1–3 位小数；输出两位是兼容性最好的选择。
内部计算保留毫秒，只在序列化时取整到 10ms。

### 5.7 范围外（明确不做）

- 逐字/卡拉OK 级的**单独**时间编辑（行级时间照常可改；逐字标记作为正文的一部分原样保留，微调时跟着整体平移）；
- 多版本歌词管理 / 撤销到任意历史版本；
- 把编辑结果导出成文件（「复制 LRC」已经覆盖了「我要拿去别的地方用」这个诉求）。

## 6. 桌面歌词：位置记忆

### 6.1 现状

窗口每次创建都走 `desktopLyricsOptions()`：主屏工作区水平居中、底部往上 108px。
用户拖走后没有任何记录（`--wails-draggable: drag` 让系统直接移动窗口，
JS 侧根本收不到拖拽事件），于是重启就回到默认位置。

### 6.2 方案

- 配置里新增 `desktopLyricsX` / `desktopLyricsY`（DIP 逻辑像素，默认 `-1` = 没存过）。
- 窗口创建时：有存档且**校验通过**就用存档，否则用默认算法。
- 校验规则（防止换显示器/改分辨率后窗口跑到看不见的地方）：
  存档点必须落在**当前所有屏幕的并集**内，且窗口至少有 1/3 面积可见；
  不满足则忽略存档、回默认位置。
- 记录时机：监听窗口的 `WindowDidMove` 事件（Wails 自带 50ms 去抖），
  再做 400ms 去抖后写配置；**关闭窗口时立刻写一次**（避免最后一次移动丢掉）。
- 只存位置、不存尺寸：宽度是按当前屏幕算出来的，存下来换屏后必然错位。

### 6.3 UI 补充

设置 → 歌词 → 桌面歌词那一行加一个「重置位置」小按钮（位置记忆出问题时的出口）。
不做「锁定位置」之类，需求里没有。

## 8. 实现对照（完工后回填）

### 8.1 与设计一致的

三个 tab、抽屉尺寸与位置、微调的 ±10s 与 50ms 档位、听感校准两个按钮的方向、
手动编辑的「打轴并下一行 + 空格」流程、撤销栈 50 步、文本↔行列表按文本匹配保留时间、
未打轴/时间非升序的保存确认、桌面歌词位置记忆（含 1/3 可见面积校验与「重置位置」出口）
—— 全部按设计实现。

### 8.2 实现中发现并修掉的问题（设计里没预见到的）

这三条都是**验证阶段实测**出来的，记在这里是因为它们都属于「看起来能跑，
实际用起来是错的」那一类：

1. **tab 点不动**：面板的点击委托只匹配 `[data-act]`，而 tab 按钮上是
   `data-tab`，于是点 tab 直接被 `return` 掉。更糟的是**第一版自检没发现** ——
   它读的是隐藏 pane 里的元素（`[data-nudge-value]`、`[data-editor-text]` 都存在），
   元素还在、值也能读，只有"可见性"这一条没断言。现在自检明确断言
   `visiblePanes`（见 `tools/check-playerbar-tools.mjs`）。

2. **微调只改了宿主的 `lyrics.index`，详情页高亮不动**：皮肤（`classic.js`、
   `fx-lyrics.js`）会拿 `ctx.playback().position` **自己再算一遍行号**，
   所以偏移必须加在**歌词行的时间上**（`playerhost.linesForSong`），
   而不是加在"定位用的时间"上。加在时间上只有宿主自己那一份生效，
   表现就是"微调面板的预览变了、播放界面没变" —— 最难查的那种不一致。
   改到行上之后，宿主、皮肤、桌面歌词、桌面背景歌词天然一致，且不用改皮肤契约。
   （代价是「无偏移时零分配」，有偏移时按 `songId + offset` 缓存一次平移结果。）

3. **往前调被自己的下限卡死**：最初的规则是"最早一行不能被推到 0 之前"，
   于是**第一句就在 0:00 的歌**（很常见）下限算出来是 0，永远不能往前调 ——
   而那正是最常需要往前调的情况（歌词整体比人声晚）。现在恒定 ±10s，
   被压到 0 的行由 `shiftLrc` 钳住，并在读数旁提示"有 N 行会被压到 0:00"。

另外顺手补了一条**数据安全**约束（设计里只写了"草稿要保留"，没写归属）：
编辑草稿带 `songId`，保存**永远写到草稿所属的那首歌**。编辑途中切歌时，
顶部会提示"已切歌，草稿仍属于《X》"，并且**拒绝打轴**（此时的播放位置属于另一首歌，
打进去必然全错）；用户要么保存它，要么点"载入当前歌词"改成编辑当前这首。
不这么做的话，切歌后按保存会把 A 的歌词静默写到 B 上。

## 3. 首屏与内存

真正压在第一帧之前的两个大头已经移走：

1. **5.86MB 元数据缓存**不再在建窗口前同步解析（懒加载）；
2. **内置 ffmpeg 的解包**（读盘 + 哈希 + 落盘）不再由主线程触发，只发生在后台
   prewarm 里；热启动连解压都不做（见下节）。

### 本机实测（重要：不要照抄报告里「秒级」的量级）

在同一台机器（56 首、`metadata-cache.json` 5,865,829 字节、其中 99.7% 是封面
base64）上实测这两段原本由主线程承担的开销：

| 动作                  | 本机实测 | 说明                                |
| --------------------- | -------- | ----------------------------------- |
| 读 5.86MB JSON        | 3 ms     | NVMe + 页缓存                       |
| `json.Unmarshal`      | 6 ms     | 56 条记录                           |
| `ffmpeg.exe` sha256   | 4 ms     | 6,280,718 字节                      |
| 首跑写 6MB 到缓存目录 | 3 ms     | 不含杀软扫描；热启动只 `stat`，不写 |

也就是说：**在这台机器的当前曲库规模下，这次优化的绝对收益是 10–20ms 级**，
不是报告里估的「秒级 + 数百 MB 峰值」。报告那个量级是按 1000 首 / 155MB 内嵌件
**外推**出来的，没有实测（见第 5 节）。

那为什么仍然值得改：

- 两项成本都与曲库/内嵌件规模成正比：1000 首时缓存 JSON 约 146MB，解析时间与
  峰值内存都会线性上涨，而且解析出来的 base64 字符串会**长期驻留**（内存不是
  一次性开销）；
- `ffmpeg` 那一段原本被 `sync.Once` 从后台 goroutine「抢」回主线程 ——
  注释声称「在后台做」，实际第一次 `Resolve` 由 `loudness.NewManager` /
  `media.New` 在建窗口前触发，首次启动还要写 6MB 出去，被杀软拦截时是秒级；
- 这两项都在「建窗口之前」，属于关键路径上的同步 I/O，改成懒加载/后台之后，
  规模增长不会再反馈到首屏。

同时把「每帧」的开销压下去（渲染键、选中行同步、id 查找），这几项在长曲库下
是持续性的 CPU 与 GC 压力，间接也影响滚动与首屏后的可交互时间。

内存方面本次只做了「不再每帧重建渲染键字符串 / 不再逐字素提升合成层」这类
不改变数据驻留的优化；封面 base64 的三份驻留（Go 侧缓存、IPC 载荷、前端状态 +
DOM）是内存占用的主要来源，需要按 1.4 的说明单独重构。

## 4. exe 产物体积

内嵌的 ffmpeg 改为 **gzip 压缩后嵌入**（`internal/ffmpeg/bin/ffmpeg.exe.gz`，
由 `tools/build-ffmpeg.mjs` 在编译完 exe 后顺手生成）：

|                 | 原始嵌入 | gzip 嵌入            |
| --------------- | -------- | -------------------- |
| 内嵌件          | 5.99 MB  | **2.21 MB**（37.0%） |
| production 产物 | 19.87 MB | **16.22 MB**         |

关键点是不牺牲启动性能：

- 缓存文件名取**压缩数据的 sha256**，「能否复用」比对 **gzip 尾部的解压后长度
  （ISIZE）** —— 两者都不需要解压，所以热启动一次解压都不发生；
- 只有缓存缺失时才真的解压一次，而且那次解压发生在后台 prewarm 里，不在首帧路径上；
- 解压依赖「单成员 gzip」这一前提，压缩包是构建脚本自己生成的，代码里有注释说明。

没有采用的方案：UPX（会显著增加杀软误报与冷启动解压时间）、把 ffmpeg 改成
按需下载（会破坏「离线开箱即用」这个既定需求）。

## 5. 复核中发现的「报告本身的问题」

审查报告整体质量很高（每条都能对到真实代码），但有三处偏差，已在复核时纠正，
提醒后来人不要照抄：

1. **行号漂移**：`docs/06` 说 `store.js:200 commit()` 会「重建 id→song Map（:326）+
   整库重排（:355）+ localStorage（:980）」。实际 `:326` / `:355` 属于
   `currentSongList` / `recalcVisible`，不在 `commit` 里。结论（commit 每次都做
   持久化、存在每帧调用）是对的，但引用位置需要按当前树重新核对。
2. **"`npm run check` 当前失败"** 这一条在审查开始时成立，但同一批任务里已经顺手
   修掉了（`magia.js` 字符类里多余的 `\-`），复核时不应再当作未修问题。
3. **影响量级是外推、不是实测**：`docs/06` 的 P0-1 写「秒级 + 数百 MB 峰值」、
   P0-2 写「按 155MB 估算哈希 0.2–0.5s、写盘 1–3s」。这两个数字分别按
   1000 首与 155MB 内嵌件外推，**与当前仓库的实际情况不符**（内嵌件是 6MB、
   本机曲库 56 首）。本机实测见第 3 节：两项加起来是 10–20ms 级。
   **结论方向是对的**（成本随规模线性增长、且确实都在建窗口之前），
   但排期/收益判断应该按实测，不能按报告的估算值。

另外 `docs/05` 的「轻微」条目里有一条判定为「存疑」（`meta:embed-progress`），
复核后按「真问题」处理并修掉了 —— 依据是后端一直在发事件、且批量写文件可能持续
几分钟，界面毫无进度确实会让人以为卡死。

## 7. 补充修复：列表闪烁 + 桌面背景歌词首帧黑屏（本轮）

本轮处理两处用户可感知的闪烁，都是「渲染时机」问题，与业务逻辑无关。

### 7.1 进入界面 / 切换歌曲时列表区域闪一下

**复核**（不看结论看代码）：`docs/06` 的 P0「曲目表零虚拟化」在本轮之前只做了
「渲染键不再逐 id 拼接」这一半，而那半个修法**引入了新问题**：

    // store.js（修复前）
    state.visibleVersion = (state.visibleVersion || 0) + 1;   // recalcVisible 里无条件 +1

`recalcVisible` 是 `commit()` 里无条件跑的，而 `commit()` 到处都是 —— 切歌、调音量、
播放/暂停、扫描结束、封面回填都会来一次。于是**任何**状态变更都让渲染键变化，
`renderContent` 里的 `body.innerHTML = '<div class="page"></div>'` 重建整块列表：

- 所有 `<img>` 被重新创建 → 每张封面重新解码 → 闪一下；
- `.page` 是新建的，它上面的 `fade-in` 入场动画跟着重播一遍 → 再闪一下；
- 行的 hover / 拖拽中间态 / 焦点全部丢失。

原来的渲染键 `visibleSongs.map(id).join(",")` 反而**没有**这个问题（内容不变时字符串
不变）—— 所以那次「优化」在这一点上是倒退的。

**处置**：

| 位置                                               | 改动                                                                                                                                                                              |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `store.js#recalcVisible`                           | `visibleVersion` 改由**内容指纹**决定（id 顺序 + 长度做一次 FNV-1a；曲库数组被整体替换时也算变更）。列表没变就**不动**版本号                                                      |
| `tracks.js#renderTracks`                           | 整表 `innerHTML` 改为**按 song.id 增量渲染**：只有新出现的歌才创建行元素，已有的行只把变了的字段写回去，顺序用 `insertBefore` 对齐（无需移动时一个节点都不动）                    |
| `tracks.js#setCoverSrc`                            | 换封面地址时先在一个游离 `Image` 上预加载，就绪后再替换 —— 直接改 `src` 会让旧图先被丢掉，那一格在新图解码前是空的                                                                |
| `tracks.js#bindQueueSort`                          | 记下 Sortable 实例绑的是哪个 `.tracks__body`，同一个不再 destroy+create（否则每次重绘都会打断正在进行的拖拽）                                                                     |
| `shell.js#renderContent`                           | `.page` 只在「进入另一个列表」（换视图 / 换歌单）时重建；数据更新都在同一个 `.page` 上做增量。这样入场动画只在真正换页时播一次                                                    |
| `shell.js#renderSidebar` / `tracks.js#renderEmpty` | 加内容签名去重，纯选中态变化不再重建 DOM                                                                                                                                          |
| `main.js`                                          | 封面缓存回填 `hydrateCachedCovers()` 提前到**首帧之前**收口（与主题/下载面板/播放栏的装配并行，通常早就完成）：否则列表会先按文件自带封面画一遍、几百毫秒后再整片刷成用户选的那张 |

**不做的事**：行窗口化（虚拟滚动）仍然没做 —— 那是结构改造，见 1.4 的理由。
本轮的增量渲染把「重建」变成「打补丁」，但节点总数依旧是 O(可见行数)。

### 7.2 桌面背景歌词启动初期黑一下

**复核**：`ensureDesktopWallpaper` 是「Hidden 创建 → `attachDesktopWallpaperWindow`
→ `w.Show()`」，看起来与主窗口（`main.go` 的 `Hidden` + `MarkReady`，Wails issue #4611）
是同一套。但 `attachDesktopWallpaperWindow` 里原本有这两行：

    style |= wsChild | wsVisible | wsClipSiblings | wsClipChildren   // ← WS_VISIBLE
    procSetWindowPos.Call(hwnd, hwndBottom, 0, 0, w, h,
        swpNoActivate|swpFrameChanged|swpShowWindow)                  // ← SWP_SHOWWINDOW

「Hidden 创建」被这两行一次性抵消了 —— 窗口在挂到壁纸层的同时就可见了，而那一刻
页面才刚开始加载：它自己的底色是深色，皮肤要等主窗口把曲目/封面/歌词/主题推过来
才画得出东西。于是先出现的是一块纯色 —— 就是「刚打开的时候黑一下」。

**处置**：

| 位置                           | 改动                                                                                                                                                                                                       |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `desktop_wallpaper_windows.go` | 去掉 `WS_VISIBLE` 与 `SWP_SHOWWINDOW`：挂载阶段只改父子关系、摆位置、排 z 序，**不动可见性**                                                                                                               |
| `desktop_wallpaper.go`         | 新建窗口后不再立刻 `Show()`；改由页面画好第一帧后调 `MarkDesktopWallpaperPainted` 触发（`CompareAndSwap` 保证只显示一次）。另有 5 秒兜底定时器：页面加载失败/脚本报错/后端没连上时窗口也必须能出现         |
| `desktop-wallpaper-window.js`  | 「第一帧就绪」的判据 = **皮肤已挂上** 且 **收到过主窗口的媒体快照**（`type: song`，`song` 为 `null` 也算 —— 曲库为空时那同样是合法画面）。两个条件缺一不可：只有样式没数据是空皮肤，只有数据没挂样式是空壳 |

兜底定时器**刻意给到 5 秒**（主窗口那条是 1.5 秒）：它真正覆盖的是「启动时恢复上次
开着的桌面背景歌词」，那一刻主窗口还在 `bootstrap`；定得太早会在主窗口准备好之前
显示一块空画面，又是一次黑屏。用户手动开关这个模式时主窗口早已就绪，正常路径延迟
只有几十毫秒，用不到兜底。

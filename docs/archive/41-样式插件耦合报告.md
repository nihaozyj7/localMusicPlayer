# 样式插件耦合报告

> ⚠️ **历史文档（已归档）** —— 本文是针对**当时那个代码快照**的一次性审查 / 修复记录。
> 文中的「现状」「文件:行号」「问题清单」描述的是当时的工作区，**多数已不再成立**。
> 请**不要**据此判断当前实现；当前事实来源是 [`docs/19-开发说明.md`](../19-开发说明.md)
> 与仓库根目录的 [`AGENTS.md`](../../AGENTS.md)。保留本文只为存档「当时为什么这样判断 / 修了什么」。


> 结论先说：现在的「播放器样式」有**两套加载路径**，但它们不是同一套东西 ——
> 内置样式是**包的一部分**（静态 import + 打包 + 进 exe），第三方样式才是**插件**
> （运行时从数据目录 import）。于是出现一个反直觉的结果：**程序自带的样式比第三方
> 样式更"不自由"** —— 它们不能自包含、必须依赖包与宿主的内部实现，删掉一款要改源码
> 并重新构建，而第三方样式只要丢一个目录进去。
>
> 本报告只做诊断，不做改造（按你的要求：解耦那一部分先不做）。
> 与本次改动直接相关的是第 3 节的 C1 / C2 / C3 / C4 / C7。

## 1. 两套加载路径的实际样子

### 1.1 内置样式：编译期，静态 import

```js
// frontend/packages/player-skins/src/index.js
import classic from "./skins/classic.js";
import immersive from "./skins/immersive.js";
import "./lyrics.css";
import "./background-layer.css";
import "./fx-lyrics.css";

export const BUILTIN_SKINS = [classic, immersive];
for (const skin of BUILTIN_SKINS) registry.set(skin.id, skin);
```

链路：`src/index.js` 静态 import → Vite 打包进 `frontend/dist/assets/index-*.js`
→ `main.go` 的 `//go:embed all:frontend/dist` 进二进制 → 用户看到的 exe。

**样式清单是代码，不是数据。** 删/加一款内置样式 = 改 `index.js`（必要时删文件）
→ 重跑 `node tools/build-frontend.mjs` → 重编 Go（`go:embed` 会重算）→ 重发 exe。

### 1.2 第三方样式：运行期，清单 + 动态 import

```
<数据目录>/player-skins/<id>/
  skin.json     { "name": …, "module": "skin.js", "styles": ["skin.css"] }   可选
  skin.js       export default { id, name, icon, order, mount, update, destroy }
  skin.css      可选（清单不写就带上目录里所有 .css）
```

链路：Go 侧 `internal/skins` 扫目录 → 前端 `playerhost.js#discoverSkins()`
`import(/* @vite-ignore */ "/skins/<id>/skin.js?t=<token>")` → `injectSkinStyles()`
往 `<head>` 插 `<link data-skin="<id>">` → `registerSkin()`。

**样式清单是数据。** 加一款样式 = 复制 `_template/` 改个名 → 设置里点「重新扫描样式」，
**不需要碰源码，也不需要重新构建**。

### 1.3 两条路径的差异一览

| 维度 | 内置样式 | 第三方样式 |
| --- | --- | --- |
| 清单来源 | `index.js` 里的静态 import | 数据目录 + `skin.json` |
| 生效时机 | 构建期（进 bundle / exe） | 运行期（每次启动扫描，可重扫） |
| 能否 import 包内模块 | 能（相对路径 `../html.js`） | **不能**（数据目录里没有那些文件） |
| CSS 如何加载 | `import "./x.css"`（打包器处理） | 清单 `styles` 字段 → 宿主插 `<link>` |
| 共享骨架 CSS | 由包入口统一 import | 拿不到（除非自己抄一份） |
| 卸载 | 不可注销（`unregisterSkin` 直接拒绝） | 可注销、可删目录 |
| 改动成本 | 改源码 + 重建前端 + 重编 exe | 丢目录 + 重扫 |

## 2. 一个具体的对照：这四款样式为什么"搬不动"

2026-10 移除的 4 款（简约 / 二次元手绘 / 魔法阵 / 星阵咏唱）备份在桌面
`播放器样式备份/`。它们的 import 形状是这样的（从备份里直接抄）：

```js
// 简约
import { defineSkin } from "../contract.js";
import { createLyricsView } from "../lyrics-view.js";
import { EMPTY_TRACK, lyricsEmptyText } from "../html.js";
import "./minimal.css";

// 二次元手绘
import { createFxLyrics } from "../fx-lyrics.js";
import { createCamera } from "../fx-camera.js";
import { applyFit as writeFit } from "../fit.js";

// 星阵咏唱
import { ELEMENT_NAME, createElementAnalyzer } from "../arcanum-audio.js";
import { createStageCamera } from "../arcanum-stage.js";
import { createDust, createScene } from "../arcanum-scene.js";
```

把它们整目录丢进「样式目录」会**直接 import 失败**：`../contract.js` 在数据目录里
并不存在。备份里因此附了 `shared/`（递归解析出来的依赖）与 README 的改造步骤 ——
这本身就是"插件系统没能把内置样式也当成插件"的证据。

## 3. 耦合清单

### C1 内置样式清单被写死在包入口（静态 import）

- **现象**：`BUILTIN_SKINS` 是一个数组字面量，元素是 import 进来的对象。
- **证据**：`frontend/packages/player-skins/src/index.js`。
- **影响**：程序自带的样式反而不能"配置化"；每次增删样式都要动源码 + 重建 +
  重新发版；用户无法禁用某个自带样式（只能被它占着按钮位）。
- **方向**：把内置样式当作**随包分发的第三方样式**（构建时复制到数据目录 /
  只读资源目录），宿主只保留注册表 + 接口；`BUILTIN_SKINS` 退化成"默认随包附带的那批 id"。

### C2 样式直接 import 包内私有模块（不是公开契约）

- **现象**：内置样式用 `../xxx.js` 引用包内模块；这些模块**没有**导出边界，
  也没有"哪些是给样式用的 SDK"这样的划分。
- **证据**：上面第 2 节的 import 形状；`index.js` 里还把它们中的一部分继续
  `export` 出去（见 C5）。
- **影响**：
  1. 样式不可自包含 → 第三方复用不了（C1 的后果放大）；
  2. 任何模块重构都可能弄坏样式，而**没有编译期护栏**（都是相对路径）；
  3. 想在数据目录里 import 同一个模块，只能"整包复制一份"，于是同一份代码
     在磁盘上有多个副本（版本漂移）。
- **方向**：定义一个**稳定的样式 SDK 入口**（例如
  `@localmusicplayer/player-skins/sdk`，只导出 `defineSkin` / 歌词渲染器 /
  背景层 / fit / 工具），第三方通过宿主注入的 import map 或全局对象拿到它；
  样式文件只 import SDK，不 import 内部实现文件。

### C3 CSS 双轨：内置走打包器 import，第三方走清单，而骨架样式由包入口注入

- **现象**：
  - 内置样式写 `import "./minimal.css"` —— **只有打包器能理解的语法**；
  - 第三方样式只能在 `skin.json` 的 `styles` 里列出 css 文件，由宿主插 `<link>`；
  - `lyrics.css` / `fx-lyrics.css` / `background-layer.css` 这三张**骨架样式**
    由包入口 `index.js` 统一 import，样式自己并不声明。
- **证据**：`index.js` 的三行 CSS import；`internal/skins` 的 `Styles` 字段；
  `playerhost.js#injectSkinStyles`。
- **影响**：一款使用 `createFxLyrics()` 的第三方样式**拿不到 `fx-lyrics.css`**，
  歌词会退化成一列不可滚动的纯文本（这个坑在本仓库里真实发生过，注释还留在
  `index.js` 里）。也就是说：SDK 提供的能力与 SDK 提供的样式不是一套。
- **方向**：骨架样式随 SDK 一起暴露（皮肤声明 `requires: ["fx-lyrics"]`，
  由宿主注入，或干脆把骨架样式做成 SDK 的 CSS 入口由皮肤自己引入）。

### C4 样式卡片图标依赖宿主的 SVG sprite

- **现象**：皮肤里的 `icon: "minimal" | "anime" | "arcanum"` 是**宿主 sprite 的
  符号 id**；宿主渲染成 `<svg><use href="#i-<id>"></use></svg>`。
- **证据**：`frontend/src/index.html` 的 `<symbol id="i-minimal">` /
  `<symbol id="i-anime">` / `<symbol id="i-arcanum">`；`ui/settings-view.js`
  里 `icon(s.icon || "disc")`；模板 `_template/skin.js` 也写着 `icon: "disc"`。
- **影响**：第三方样式**只能从宿主已有图标里挑**，且写错 id 不会报错 ——
  卡片上直接是空白图标。被移除的四款样式备份里仍写着这些 id，主程序里也还留着
  这三个 symbol（本次没删，删了备份就更搬不回去）。
- **方向**：`icon` 支持内联 SVG / data URI（皮肤自带），宿主 sprite 只作为可选项。

### C5 辅助模块事实上成了"公共 API"，但没有版本与使用边界

- **现象**：`index.js` 把 `arcanum-timing` 的三十多个纯函数、`arcanum-scene` /
  `arcanum-stage` / `arcanum-audio`、`fx-*` 等一并 `export` 出去。
- **证据**：`index.js` 第 50 行往后的一长串 `export { … }`；单测
  `frontend/tests/player-skins.test.js` 就是按这些导出写的。
- **影响**：星阵样式被移除后，这些模块**在包内已无调用方**，却仍是导出面
  （本次按「先不做解耦」的决定保留原样）。它们既是死代码，又是别人可能依赖的
  API —— 两个身份冲突，正是耦合的典型症状。
- **方向**：给 SDK 划一条明确的线（哪些是契约、哪些是实现），把纯逻辑模块
  移进 `internal/` 或者随样式一起搬走；契约部分加 `apiVersion` 兼容承诺。

### C6 内置样式不可注销 + 同名第三方直接报错

- **现象**：`unregisterSkin()` 对内置 id 直接返回 false；
  `loadExternalSkin()` 遇到与内置同名的 id 会**抛错并忽略该目录**。
- **证据**：`index.js` 的 `BUILTIN_SKINS.some(...)` 分支；这条规则来自真实事故
  （`magia` 曾是第三方样式，并入内置后数据目录里的旧副本长期顶替内置版本）。
- **影响**：规则本身是对的（避免静默顶替），但它把"内置 vs 第三方"固化成了
  **两种不同的东西**：用户没法用"我自己的版本"覆盖一个自带样式，也没法卸载它。
- **附带（本次已修）**：内置样式**被移除**后，老配置里的 `playerViewMode` 会永远
  指向一个不存在的 id。以前只会在打开详情页时静默回退到默认样式，设置页里
  没有任何卡片是选中态。本次在启动时补了一次归一化
  （`main.js` → `setPlayerViewMode(state.config.playerViewMode)` 会把真正生效的
  id 写回配置）。

### C7 宿主工具、测试、文档与"内置清单"逐款耦合

- **现象**：内置清单被至少 6 处硬编码/强断言：
  - `frontend/tests/player-skins.test.js`：断言六款 id 与顺序；
  - `tools/check-player-host.mjs`：整段整段的**每款样式的 DOM 断言**
    （窗口适配比例、星阵纵深舞台、减少动态效果…约 400 行）；
  - `tools/check-app.mjs` / `tools/cdp-check.js` / `tools/perf-skins.mjs`：
    清单、按样式跑的验收与性能基线；
  - `README.md` / `README.en.md` / `docs/19-开发说明.md`：样式清单与截图。
- **影响**：删一款样式要同步改 6+ 处，一处漏掉就是"构建绿、文档/工具错"。
  本次改动的实际代价就是这一串 —— 而这本不该由"删一个样式"引起。
- **方向**：把"内置样式清单"收敛成**唯一一处数据源**（构建时生成），
  工具与测试从那份数据源取；每款样式的宿主验收脚本随样式一起走（放在样式目录里，
  由宿主工具按清单发现并执行）。

### C8 构建节奏不一致：改自带样式要发版，改第三方样式只要丢目录

- **现象**：`dist` 进 `go:embed`，所以内置样式任何一行 CSS 改动都需要
  重建前端 + 重编 exe；第三方样式则 `no-store` 直出，重扫即生效。
- **影响**：同样是"样式"，两类改动的验证回路相差一个数量级（几分钟 vs 几十秒），
  这会持续把新样式往"第三方"那边推 —— 与"内置样式也是插件"的目标相反。
- **方向**：与 C1 同一个解 —— 让内置样式也走运行期加载（随包分发到资源目录），
  宿主只负责"发现 + 注册"。

### C9 一份样式要同时服务多个宿主舞台（这条是设计优点，但要写进契约）

- **现象**：同一个样式会被挂到主窗口详情页，也会被挂到**桌面背景歌词窗口**
  （`desktop-wallpaper-window.js` 里 `mountSkin` 同一份实现）。
- **影响**：样式必须假设"我可能被挂在不止一个舞台、且宿主不保证只有一个实例"，
  不能依赖单例、全局 id、`document.querySelector` 取宿主元素。
  现有内置样式基本做到了（皮肤里没有直接摸宿主 DOM，只有 `fit.js` /
  `fx-camera.js` 读 `window.matchMedia`），但这条约定**没有写进第三方样式的契约文档**。
- **方向**：写进契约（并在 `_template` 里给一个"两个实例"的自检开关）。

## 4. 改造方向（建议顺序）

不做"大爆炸重写"，按收益/风险排：

1. **（低成本，收益大）把内置样式清单收敛成一份数据**：`skins/manifest.json`
   列出内置样式的 id / 文件 / order；`index.js` 不再逐款 import。
   好处：删样式只改这一处（C7 直接消掉一半）。
2. **给样式一个稳定的 SDK 入口**（C2/C5）：`defineSkin`、歌词渲染器、
   背景层、fit、工具函数进 `sdk` 子路径；包内部实现文件不再是样式的 import 目标。
3. **让每款样式自包含**：自己的 js / css / 依赖（本地相对路径）+ 可选图标，
   放一个目录就是一款样式 —— 于是"内置样式"可以原样丢进数据目录复用（C1/C2/C3）。
4. **骨架样式随 SDK 暴露**（C3）：彻底消掉"渲染器有、骨架样式没有"的错位。
5. **图标自包含**（C4）：`icon` 允许内联 SVG。
6. **内置样式改为随包分发的数据目录**（C1/C8）：宿主启动时把只读资源目录里的
   样式注册进同一个注册表；"内置"只是"默认随包附带"，不再是特殊公民（C6 也随之简化）。

做完 1~6 之后，本次这四款样式就能**整目录直接丢回数据目录**用起来，
不需要改程序、不需要重新构建 —— 这才是"样式插件系统"该有的样子。

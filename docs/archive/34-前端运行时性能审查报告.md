## P1 — High impact

### P1-1. `mp-lyrics-panel` re-renders its entire template on every 250 ms progress tick

`frontend/src/js/ui/lyrics.js:65-73`

```js
static deps = (s) => [
  s.lyricsOpen,
  s.currentId,
  s.position,
  s.playing,
```

Cost: `s.position` climbs ~4×/s during playback (250 ms quantization, `audio.js:340`), so `revalidate()`
(`base.js:100`) fires a full `requestUpdate()` on the lyrics component **every 250 ms for the whole session**.
`render()` (`lyrics.js:152-219`) rebuilds the header, tabs, notice, and — critically — dispatches to
`onlinePane()`, `nudgePane(info)`, `editPane()`. `editPane()` → `draftList()` (`lyrics.js:556-560`) is a
`repeat()` over **every draft line**, and `nudgePreview` (`lyrics.js:401-426`) walks lines; the panes are
all in the DOM simultaneously (only `?hidden`-toggled, `lyrics.js:474`).

Frequency: per 250 ms tick, for the entire playback session, while the panel is open.

Scale impact: for a 1000-line lyric draft this is a 1000-item `repeat` template construction + Lit diff
4×/s. Even with only the `draftList` sub-tree stable, the surrounding template literals (`formatLrcTime`
at `lyrics.js:520`, `fmtTime`/labels, the tab array `.map` at `lyrics.js:199`) are recreated each time.
The file itself acknowledges the panel is expensive enough to need manual sub-updates — `paintNudgeFollow`
(`:432-452`) and `paintEditorFollow` (`:980-983`) exist precisely to avoid re-rendering for highlight
changes — yet `s.position` in `deps` forces the full path anyway.

Fix sketch: drop `s.position` from `deps` and drive the position-dependent parts the way `playerbar.js`
does (a direct `subscribe()` calling `paintNudgeFollow` / `paintEditorFollow` / `paintEditorClock`), or
gate the whole panel on `s.lyricsOpen && songChanged` plus the existing `lyricsPanelTick`.

Confidence it's hot: **high** — the deps entry is unambiguous and the tick is unconditional during playback.

### P1-2. `MpPlayerview.updated()` runs `renderPlayerView()` on every position tick, and that path allocates a full media snapshot + does a DOM query

`frontend/src/js/ui/playerview.js:28-46`

```js

  renderPlayerView();

```

`frontend/src/js/playerhost.js:1157-1158`

```js
pushOptions();
syncPlaybackState();
```

and `frontend/src/js/playerhost.js:1174-1183`

```js
export function syncPlaybackState({ force = false } = {}) {
  if (!state.playerOpen || !host.skin) return;
  const playback = playbackSnapshot();
  …
  push({ type: "progress", ...playback, lyricIndex: lyricsSnapshot(currentSong()).index });
```

Cost: each 250 ms tick (with the detail view open + a skin mounted) runs:
- `playbackSnapshot()` — fresh object (`playerhost.js:574-582`);
- `lyricsSnapshot(currentSong())` — **and this one is not free**: `linesForSong` (`:259-268`) hits the
  `lyricsCache` Map, and `findLyricIndex` is called (`:607`); the returned object is allocated even though
  only `.index` is consumed, and `mediaSnapshot()`'s `lyrics:` field is thrown away;
- `push()` → every skin subscriber `fn(patch)` (`playerhost.js:740-747`) with an object spread.
- Plus the full `render()` template rebuild of the playerview shell + `availableSkins()` and `repeat()`
  over skins (`playerview.js:54, 98-115`).

Frequency: per 250 ms tick while the player view is open.

Scale impact: moderate per-tick but continuous for an entire listening session; the real cost is that
`renderPlayerView()` is an `async` function (`playerhost.js:1059`) invoked from `updated()` with no
await — so overlapping invocations are possible if it ever awaits (`:1100 await ensureSkins()`,
`:1137 await getLyrics(song)`), which can interleave pushes.

Fix sketch: keep the tick, but split the shell render from the skin push — move the `renderPlayerView()`
call out of `updated()` into a `subscribe()` handler (mirroring `playerbar.js:110-115`), and pass the
already-computed `lyricIndex` into `syncPlaybackState` instead of recomputing `lyricsSnapshot` there.

Confidence it's hot: **high** for the call path; the per-tick magnitude depends on skin subscriber count
(skin-internal, out of my scope).

### P1-3. `content.js` filter input re-filters the whole library and rebuilds the whole DOM list on every keystroke (no debounce)

`frontend/src/js/ui/content.js:87-99`

```html
<input
  class="content-filter__input"
  id="content-filter-input"
  …
  .value=${state.query}
  @input=${(e) => {
    state.query = e.target.value;
    commit();
  }}
```

`frontend/src/js/store.js:697-708`

```js
const q = state.query.trim().toLowerCase();
if (q) {
  out = out.filter(
    (s) =>
      s.title.toLowerCase().includes(q) ||
      s.artist.toLowerCase().includes(q) ||
      s.album.toLowerCase().includes(q) ||
      s.ext.toLowerCase().includes(q)
  );
}
```

Cost: each keystroke → `commit()` → `visibleInputs()` (`store.js:649`) differs on `state.query` →
`computeVisible()` does a **linear scan over the entire library** with 4 × `toLowerCase()` allocations
per song, then `computeSorted()` (`:729-744`) does `list.slice().sort(...)` with the `Intl.Collator`
comparator (≈ n·log₂n collator calls, the file's own comment at `store.js:519-526` measures 13.2 ms for
5,000 songs). Then `visibleFingerprint()` walks all results (`:807-822`), and `visibleVersion` bumps →
`MpTrackTable.render()` (`track-table.js:145-170`) runs `repeat()` over the new list → **all DOM rows are
diffed/replaced**.

Frequency: **per keystroke**. Fast typing ≈ 8–12 events/s.

Scale impact: severe. At 10,000 songs: 10k × 4 `toLowerCase` calls + a full collator sort + a 10k-entry
`repeat` reconciliation, several times per second. Also note there is **no index or prefix map** — it is
a pure linear scan per keystroke, and `s.title.toLowerCase()` is recomputed on every keystroke for every
song (nothing caches a lowercased haystack).

Also relevant: the `?hidden`/`.value` bindings mean the *input itself* is not re-created, but the
keystroke handler's synchronous `commit()` still blocks the keystroke's own frame.

Fix sketch: debounce the filter commit ~120–150 ms (there is already a `debounce` helper at
`utils.js:123-129`), write the input's local value immediately for responsiveness, and precompute a
lowercased search haystack per song at scan time (`state.songs` is wholesale-replaced, so a parallel
`Map<id, haystack>` is cheap to maintain in `recalcVisible`).

Confidence it's hot: **high** — the handler and the linear scan are both explicit.

### P1-4. Catalog-size-linear work runs inside `settings-view`'s `render()`

`frontend/src/js/ui/settings-view.js:356`

```js
const count = state.songs.filter((s) => s.path.startsWith(f.path)).length;
```

`frontend/src/js/ui/settings-view.js:594`

```js
const { kept, excluded, total } = applyRules(state.allSongsRaw, state.filterRules);
```

`frontend/src/js/ui/settings-view.js:1337-1338`

```js
const total = state.songs.reduce((sum, x) => sum + x.duration, 0);
const bytes = state.songs.reduce((sum, x) => sum + x.size, 0);
```

Cost: `foldersCard()` is O(folders × songs) (the `startsWith` scan runs once per folder — with F folders
it is F full passes); `filtersCard()` runs `applyRules` over the **entire raw library**, including regex
`test()` per song per rule; `aboutCard()` does two more full passes. All three run on **every render of
the settings layer**, which is a 88 KB component whose `deps` include `s.songs`, `s.allSongsRaw`,
`s.filterRules`, `s.folders`, `s.updateRev`, `s.config`, … (`settings-view.js:182-215`).

Frequency: every `deps`-signature change while settings is mounted. Note `s.updateRev` is bumped on
**every** `commit()` (`store.js:376`), so any store mutation while the settings layer is open re-runs it.

Scale impact: severe at 10k+ songs. That is ~10k×4 (folders) + 10k regex tests + 20k reduces per render.
The component's own comment (`settings-view.js:211-214`) shows the author already reasoned about this —
they removed `s.volume` from deps *specifically* because *"render() 会无条件重算三处随曲库规模线性增长的
派生值"* — but the remaining triggers (`updateRev` on every commit) still fire it.

Fix sketch: memoize the three derived values behind a signature (e.g. `s.songs`/`s.allSongsRaw`/
`filterRules`/`folders` identity) and reuse the result across renders, exactly as `recalcVisible` does in
the store; and/or stop using the always-bumping `s.updateRev` as a blanket dep (scope it to the update card).

Confidence it's hot: **high** for the cost; **medium** for real-world frequency, since it requires the
settings layer to be open — but when it is open, `updateRev` makes it fire on every commit.

### P1-5. `MpSearchOverlay.render()` re-reads and re-parses localStorage history on every keystroke of the search box

`frontend/src/js/ui/search.js:114-117`

```js

  const s = searchState;
  const history = loadHistory();
```

`frontend/src/js/ui/search.js:32-40`

```js

  try {
    const raw = localStorage.getItem(HISTORY_KEY);
    const list = raw ? JSON.parse(raw) : [];
```

Cost: synchronous `localStorage.getItem` + `JSON.parse` of the history array on **every render**. The
search input's `@input` handler calls `bump()` → `searchState.rev += 1` → `requestAppUpdate()`
(`search.js:62-66`) which, per `base.js:56-58`, calls `revalidate()` on **every mounted element**:

```js

```

So a keystroke in the search overlay triggers a `deps()` evaluation across all ~18 mounted components,

Frequency: **per keystroke** in the search box (and also on every `bump()` from history add/remove).

Confidence it's hot: **high** for the mechanism; **low** for user-visible impact given the 20-item cap.

## P2 — Medium impact

### P2-1. `MpQueuePanel.item()` does a linear `indexOf` per row → O(n²) for long queues

`frontend/src/js/ui/panels.js:255-257`

```js
item(song) {
  const index = state.queue.indexOf(song.id);
  const current = song.id === state.currentId;
```

Cost: `indexOf` is O(queue length); `item()` is called once per row by `repeat()` (`panels.js:243-247`),
so rendering the queue is **O(n²)**. Additionally `Uint8Array`-style `songById` lookups happen in
`render()` (`panels.js:187`: `state.queue.map((id) => songById(id)).filter(Boolean)`) → one Map lookup
per id (that part is O(n), fine).

Frequency: every render of the queue panel. `deps` includes `s.currentId` and `s.playing`
(`panels.js:128`), so **every song change and every play/pause re-renders the whole queue panel**.

Scale impact: a 5,000-song queue = 12.5M comparisons per render; even a 500-song queue = 125k per render,
repeated on every track change. This is a genuine O(n²).

Fix sketch: build `const posById = new Map(state.queue.map((id, i) => [id, i]))` once in `render()` and
pass the index down into `item()`, or pass the `repeat` index.

Confidence: **high** — the pattern is unambiguous.

### P2-3. `settings-view` scroll handler does layout reads in a loop, and the scroll event is not throttled

`frontend/src/js/ui/settings-view.js:1935-1940`

```js
const top = scroll.getBoundingClientRect().top + 80;
let current = SECTIONS[0].id;
for (const s of SECTIONS) {
  const node = this.querySelector(`[data-section="${s.id}"]`);
  if (node && node.getBoundingClientRect().top <= top) current = s.id;
}
```

Cost: **forced layout** — `getBoundingClientRect()` per section (SECTIONS is ~10 entries) inside the
scroll handler, interleaved with `paintNav()`'s attribute writes on the previous invocation
(`settings-view.js:1955-1959`). Classic read-after-write thrash across events: each `scroll` event reads
layout after the last paint wrote `aria-selected`.

Frequency: **per scroll event** — unthrottled. There is a `rafThrottle` helper available
(`utils.js:132-144`) and it is not used here.

Scale impact: moderate. Scroll handlers can fire at frame rate and more (trackpad), and each firing
forces ~10+ `getBoundingClientRect()` calls. `scrollTop`/`scrollHeight` reads at `:1943-1945` add more.

Fix sketch: wrap `onScroll`'s body in `rafThrottle`, and cache the section offsets once per layout
instead of calling `getBoundingClientRect()` per section per event.

Confidence: **high** for the code path; **medium** for magnitude (depends on section count and scroll rate).

### P2-5. `store.notify()` invokes every subscriber with `try/catch` per subscriber, from a per-tick path

`frontend/src/js/store.js:347-358`

```js
export function notify() {
  for (const fn of listeners) {
    try {
      fn(state);
    } catch (err) {
      console.error("[store] 订阅者抛出异常（已跳过，其余订阅者继续）", err);
    }
  }
}
```

Cost: each subscriber is called inside a `try/catch`. Modern V8 handles this reasonably, but every
`MpElement` mounted pushes a `subscribe` listener (`base.js:75`) that calls `revalidate()`, which
allocates a fresh `deps()` array per element per notify (`base.js:94-95` → `deps()` at `:88-91`).
With ~18 components mounted that is 18 array allocations + 18 `sameDeps` comparisons per notify.

Frequency: per 250 ms tick during playback (`audio.js:351` `notify()`), and per `commit()`.

Scale impact: modest but continuous. The `try/catch` itself is defensible (the comment explains the
"one subscriber kills the rest" failure); the array allocation per element is the avoidable part.

Fix sketch: leave the isolation, but let components pass a cheap version-stamp getter to `subscribe` so
`revalidate()` can short-circuit before allocating `deps()`. Low priority — note that this is a
deliberate robustness tradeoff, not an oversight.

Confidence: **medium**; **low** magnitude.

### P2-7. `main.js` `scan:done` builds three full-library Sets and two element-wise scans on every scan

`frontend/src/js/main.js:266-281`

```js
const prev = new Set(state.songs.map((s) => s.id));
state.allSongsRaw = songs;
const { kept, excluded } = applyRules(songs, state.filterRules);
state.songs = kept;
const nowIds = new Set(kept.map((s) => s.id));
…
added: kept.filter((s) => !prev.has(s.id)).length,
removed: [...prev].filter((id) => !nowIds.has(id)).length,
```

Cost: on every `scan:done` this allocates a Set of the old ids, runs `applyRules` over the whole raw
library (regex tests per song per rule), builds a Set of the new ids, then does two more full passes plus
a spread of `prev` into an array. That is ~5 full-library passes plus a full array materialization.

Frequency: per scan completion. During a scan the backend pushes `scan:progress` every ~40 files
(documented at `store.js:752-753`), and each of those calls `commit()` (`main.js:259`) — but the
expensive block above is only on `scan:done`.

Scale impact: at 20,000+ songs this is a several-hundred-millisecond synchronous block on the main
thread at the exact moment a large scan finishes. The comment at `main.js:278-280` shows the author
already fixed the worse O(prev × kept) `some()` here; the remaining cost is inherent but could be
reduced.

Fix sketch: compute `added`/`removed` from a single pass over the symmetric difference, and skip the
`[...prev]` materialization by tracking removals during the `kept` build.

Confidence: **high** for the cost, **medium** for whether it is user-visible (one-shot per scan).

```js

  document.addEventListener("keydown", onKey);
```

Cost: correctness/hygiene, not perf. If `menuCloser()` runs **before** the `setTimeout(…, 0)` callback
fires (a menu opened and closed in the same task), the listeners are removed while not yet added, and
then added afterwards with nothing left to remove them → **a permanent document-level listener leak**.
`menuCloser` is set to `null` right after, so a later `closeMenu()` will not re-run the removal.

Frequency: rare (requires immediate open+close), but permanent when it happens.

Scale impact: a leaked `pointerdown` capture listener on `document` that calls `render(nothing, m)` on a
stale element forever.

Fix sketch: attach the listeners synchronously inside a `requestAnimationFrame` that is cancelled by
`menuCloser`, or set an `cancelled` flag checked by the deferred callback (the same pattern
`bridge.js:146-155` already uses for `on()`).

Confidence: **high** on the race; **low** on frequency.

### P3-5. `ui/lyrics.js:1105-1111` — `activeLineIndex` is a linear scan, called from the position-driven path

`frontend/src/js/ui/lyrics.js:1105-1111`

```js
function activeLineIndex(lines, offset) {
  let idx = -1;
  for (let i = 0; i < lines.length; i += 1) {
    if (lines[i].time + offset <= state.position) idx = i;
    else break;
  }
  return idx;
}
```

Cost: O(n) with an early `break`, so it is O(active index) not O(n) in practice. Called from
`nudgePreview` (`:406`) and `paintNudgeFollow` (`:439`).

Frequency: per panel render / per follow paint — i.e. the **same cadence as P1-1** (per 250 ms tick via
`updated()` at `:133`), which multiplies the P1-1 cost.

Scale impact: bounded by the early break, so it is the lesser half of P1-1. Fixing P1-1 removes most of it.

Fix sketch: pass `state.position` explicitly and use binary search (`findLyricIndex` already exists in the
skins package and is imported nowhere in this file — the file defines its own linear version). Note the
duplication itself is a maintenance risk given `utils.js:104-106` explicitly says the LRC helpers were
consolidated into the package to avoid two implementations drifting.

Confidence: **medium** — real duplication, small cost.

## Explicitly NOT reported as issues

- **`store.recalcVisible` / `visibleFingerprint` on the progress path.** `commit()` calls `recalcVisible()`
  unconditionally (`store.js:377`), but the signature memo at `:767-772` and the reference-guarded
  `songIndex` at `:762-765` reduce the steady-state cost of a position-only commit to: `visibleInputs()`
  (13 array slots), `sameVisibleInputs()` (13 `===`), then `visibleFingerprint(out)` — **which still walks
  the whole visible list every commit** (`:807-822`, `for (let i = 0; i < list.length; i += 1)`).
  At 10,000 songs that is a 10k-iteration FNV loop ~4×/s. It is not O(n²) and the file justifies the
  design (`:794-796`), but it *is* the one remaining O(n) pass per commit. I am flagging it here rather
  than as P2 because it is single-pass integer work with no allocation — but if you want to shave the last
  bit off the tick path, **this is where it is**. Worth measuring before touching.
- **`base.js` `requestAppUpdate()` fan-out** is documented and used deliberately for store-external state;
  only P1-5 calls it from a keystroke path.
- **CSS/style churn**: `playerhost.mirrorPlayerSurface()` (`:1024-1053`) writes ~17 custom properties per
  panel but guards each with `if (panel.style.getPropertyValue(out) !== value)`
  (`playerhost.js:1047`) — this is a correct, idempotent implementation, not a per-frame style storm.
  It only runs on panel open / skin mount, not per tick.
- **`view.offsetHeight` at `playerhost.js:1118`** is a deliberate forced reflow to make the open
  transition fire; it runs on state *change* only (`if (view.dataset.state !== "opened" || remounted)`),
  not per frame. Correct as written.
- **`tracks.js` scoped queries** (`:306`, `:313-314`) are single-shot user actions (locate), not hot paths.

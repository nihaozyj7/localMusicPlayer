## 一、最重要的订正：审查报告里有一条结论是错的

> 审查的价值不只在于发现问题，也在于**不把不存在的问题留在报告里**。
> 下面这条是我自己写进报告、又在动手修复时被自己推翻的，必须显式更正。

### C-01「畸形 box 长度 → slice 越界 panic」：**结论错误，已降级**

**报告原话**：`embed.go:190-191 / 204-205` 未 clamp box 长度，畸形文件可触发 panic，调用链无 `recover()`。

**复核过程**：我确实用一个 64 字节的缓冲区 + `udtaSize=0x0FFFFFF0` 复现出了 `slice bounds out of range`。但那只验证了「**单独执行那一行切片**会越界」，**没有验证这条路径在真实代码里可达**。回源读完整调用链后发现：

```go
udta := findChildAbs(raw, moovStart+8, moovEnd, "udta")   // ← 先经过这里
if udta < 0 { /* 走「追加新 udta」分支，根本不读 udtaSize */ }
udtaSize := int(binary.BigEndian.Uint32(raw[udta : udta+4]))
udtaEnd := udta + udtaSize                                 // ← 报告说这里会越界
```

而 `findChildAbs` **原本就有**边界检查：

```go
if size < 8 || off+size > to { return -1 }   // off+size > moovEnd 直接放弃
```

也就是说：**能返回一个合法的 `udta` 偏移，就已经蕴含 `udta+udtaSize <= moovEnd`**，`udtaEnd` 不可能越界。我用修复前的代码（`git show HEAD:...`）实测确认：恶意超大 `udtaSize` 会让 `findChildAbs` 返回 `-1`，代码走「追加」分支，**不会 panic**。`meta` 同理。

**订正后的定性**：这是**纵深防御缺失**，不是线上崩溃。写法本身不安全（裸读 4 字节长度就用于切片，一旦将来有人改了 `findChildAbs` 的检查、或在两行之间插入新逻辑，立刻变成崩溃），所以修复保留，但**严重度从 P0 降为「健壮性加固」**。

### C-02「findChildAbs 缺 size==0/1 → 错写用户文件」：**确认成立**

这条**经实测确认是真的**。用修复前的 `findChildAbs` 跑一个 `size==0` 的合法 `meta`（MP4 规范允许，表示「延伸到容器末尾」）：

```
udta offset = 8 (期望 8)
meta offset = -1  (期望 16)
```

合法 box 被判成「不存在」→ 走 `newMeta` 追加分支 → 在已有 `meta` 的 `udta` 里再塞一个 → `stco` 记录的绝对偏移失效 = **用户音频文件被永久写坏**。同文件 `findTopLevelBoxAbs` 却正确处理了 `size==0/1` —— 典型的**子集实现漂移**。

### C-18「ffmpeg.Probe 缺 `-t 0`」：**已在 HEAD 修复，属于陈旧信息**

报告与性能子报告都说它「前两轮提过两次未修」。实测 `ffmpeg.go` 的 `Probe` **已经有 `-t 0`**，且注释里写明了「48 个文件批量探测」的考量：

```go
// -t 0：只读容器头、不解码音频。…少了这个参数就会把整首歌解码到 null
// —— 耗时与曲目长度成正比，而批量扫描（library.enrichDurations）一次要探最多 48 个文件。
"-t", "0",
```

**该条不成立**。这说明**子代理结论必须回源复核**（本次 4 条高危结论中，1 条错、1 条已修、2 条成立）。

## 三、修复过程中发现并修掉的**新**问题

### 我自己的改动引入了一个数据竞争（`go test -race` 抓到）

给 `watcher.Stop()` 加「停止后再启动」支持时，我在 `Stop()` 里替换 `w.fsw`，而旧的事件循环 goroutine 仍在读它：

```
WARNING: DATA RACE
Write at 0x... by goroutine 9:
  library.(*Watcher).Stop()   watcher.go:116
Previous read at 0x... by goroutine 15:
  library.(*Watcher).loop()   watcher.go:182
```

**这正是 `-race` 门禁存在的意义** —— 如果没有它，这个竞态会以「偶发收不到文件变化」的形态流到用户那里。

修法：`loop(done chan struct{})` 在**启动时把本代的 `fsw`/`ctx` 捕获成局部变量**，之后不再读字段；`Stop()` 通过 `done` 通道**等 loop 确认退出**之后再替换实例（2 秒超时兜底，避免界面线程被永久阻塞）；`add`/`remove`/`SetRoots` 也改为锁内取 `fsw`。

### 审查报告的其它订正

- **UX「保留 NaN 首」**：报告已订正为「陈旧截图」。本次实测：截图属初始提交（2026-09-12），比 HEAD（2026-09-19）旧 7 天；用截图里的规则在当前代码复跑输出 `保留 0 首`（数字），**不复现**。
- **`data-time` 未转义 XSS 嫌疑**：确认**不可利用**（`lrc.js` 的 `time` 恒为 `Number` 运算结果），保留为一致性建议。

## 六、给后续维护者的三条提醒

1. **`embed.go` 的 `writeFileAtomic` 不要「顺手统一」成 `atomicfile.Write`。**
   后者的失败回退是 `os.WriteFile`（`O_TRUNC`，**非原子**）。对配置文件没问题，但 `embed.go` 写的是**用户的音乐文件** —— 覆盖中途失败会留下一个被截断、无法播放且原内容不可恢复的文件。修复时宁可「这次写不进去」。

2. **`mock.js` 的预览守卫依赖 `__LM_PREVIEW__` 这个编译期常量。**
   新增 mock 数据时必须写进 `!PREVIEW ? 空 : 数据` 的分支里，否则又会漏进生产包。判断标准很简单：`npm run build` 之后在 `frontend/dist/assets/*.js` 里 grep 假歌名，应当搜不到。

3. **`/skins/` 现在需要 token。**
   新增任何「从用户数据目录取资源」的宿主页面，都要走 `backend.skinsToken()` 拼 `?t=`，否则会拿到 403 而样式静默不生效。

## P1 级问题

### P1-1 · 取播放地址失败后不回收状态：界面在放 A，声音还是 B，且永不重试

- **位置**：`frontend/src/js/audio.js:398-416`（配合 `audio.js:174-184`、`audio.js:331-350`）
- **现象**：点一首后端取不到播放地址的歌（最典型：`.ape/.wma` 且没装 ffmpeg，`services.go:959-962` 会直接返回错误），只弹一条 toast，**上一首会继续出声**，而标题/封面/歌词已经换成新歌；这首之后也不会再被重试。
- **根因**：`loadedFor = song.id` 在 `await backend.mediaUrl()` **之前**就写入（`audio.js:399`），失败分支只复位 `switchPhase` 就 `return`（`406-410`、`412-416`）：既不清 `loadedFor`，也不清 `node.src`。下一次 `syncAudio()`（runtime 每 250ms 一档）看到 `loadedFor === song.id` 直接跳过换源，落到 `reconcilePlayback(node)`；而 `state.playing` 仍是 `true`（`playSong` 写的，失败路径从没改回 `false`），元素上还是**上一首**的 src 且在播 → 什么都不做，旧音频继续放、进度条继续走。
- **证据**：

```js
// audio.js:398-416
if (loadedFor !== song.id) {
  loadedFor = song.id;                 // ← 先置位
  beginSwitch();
  const seq = ++requestSeq;
  let url = null;
  try { url = song.streamUrl || (await backend.mediaUrl(song.id)); }
  catch (err) { switchPhase = SWITCH_IDLE; toast(...); return; }   // ← 不回滚 loadedFor / 不清 src
  if (seq !== requestSeq) return;
  if (!url) { switchPhase = SWITCH_IDLE; toast(...); return; }
```
- **附带**：同一路径下 `state.playing` 一直为 `true`；若该媒体仍能推进 `currentTime`（例如中途码流损坏，error code 2/3），runtime 的依赖键每 250ms 变一次 → 每个 tick 都 `reconcilePlayback` → `node.play()` 被拒 → `isBenignPlayError()`（`audio.js:449-454`）只放过 Abort/NotAllowed → 每 tick 一条「播放失败」toast。
- **建议修法**：两个失败分支调用同一个收尾函数：`loadedFor = null; switchPhase = SWITCH_IDLE; state.playing = false; node.pause(); node.removeAttribute("src"); node.load(); notify();`（`stopAudio()`（`624-632`）已经是这个形状，抽出来复用），并顺手 `clearTimeout(switchTimer)`（见 P3-2）。

### P1-2 · 曲目表无虚拟化 + 依赖数组含 currentId/playing/selectedIds/coverVersion → 每次状态变更 O(N) 全表重跑

- **位置**：`frontend/src/js/ui/track-table.js:74-89`（deps）、`162-167`（repeat 全量）、`210-258`（行模板）
- **现象**：40 行时切歌很轻；1000 行时同一次点击明显卡顿；播放/暂停、勾选一首歌、任意一首歌换封面都会触发同样的全表开销。
- **根因**：`repeat(songs, id, rowTemplate)` 每次 update 都会**为每一行重新调用** `rowTemplate`（lit 的 `repeat.update` 内部用 `this.dt(items, keyFn, template)` 遍历全部 item 调模板，见 `node_modules/lit-html/development/directives/repeat.js`），Lit 只靠 part 级 diff 避免**写 DOM**。而 deps 里放了 `s.currentId`、`s.playing`、`s.selectedIds`（每次 toggle 都是新 Set）、`coverVersion()`（任意一首歌换封面都 +1），于是这些高频动作全部变成 O(N) 模板求值 + O(20N) part 提交。
- **证据**（`.task/perf-lit.json` 的 bigLibrary 段；同一脚本、同一视口、同一假曲库）：

| 项 | 40 行 | 1000 行 | 备注 |
| --- | --- | --- | --- |
| `switchSong.ms` | 91.6 | 265.9 | 两者固定等待不同（小库 60ms，大库 raf2=120ms），扣掉 60ms 差仍有约 +114ms |
| `clickRow.ms` | 76.5 | 140.1 | 同为 raf2 口径，大库 +64ms |
| 行数 / DOM 节点 | 40 / 2466 | 1000 / 28387 | `boot.domNodes` vs `bigLibrary.domNodes` |
| 首屏建表（1000 行） | — | `firstPaint.ms` 634.8（含 120ms 固定等待），`nodesAdded: 29764` | `.task/perf-baseline.json` 同项为 641.8 / 25967 |

  `tracktable.css:160-166` 已用 `content-visibility: auto` 省掉视口外行的布局/绘制，注释自己也写明「真正的修法是对 visibleSongs 做窗口化渲染」。
- **影响面外推（推测）**：5000 首时一次切歌/勾选约 0.5s 级主线程占用（按 114ms/1000 行线性外推，未实测）。
- **建议修法**：在 `MpTrackTable` 里对 `state.visibleSongs` 做窗口化（滚动容器 `.content-body` + 固定 `--row-h` 已具备条件，`tracktable.css:159`），只渲染 `[first-overscan, last+overscan]`；同时把「当前行/播放态」从行模板里拆出去（渲染后只对旧行与新行 toggle `aria-current`/`data-playing`），这样 `currentId`/`playing` 不必进 deps。

### P1-3 · 歌词面板：关闭时也按播放进度整块重绘；打开时三个 pane 全建；微调跟随是死代码

- **位置**：`frontend/src/js/ui/lyrics.js:64-72`（deps）、`148-212`（render）、`208`（三个 pane 无条件构建）、`404-443`（nudgePreview / paintNudgeFollow）
- **现象 1**：面板没打开时也每 250ms 重绘一次面板骨架；打开「手动编辑」时，200 行歌词每秒重跑 4 次 `repeat`（每次调用 200 次行模板）。
- **根因 1**：deps 含 `s.position`；`render()` 在 `this.open` 为真时同时构建 `onlinePane()`、`nudgePane()`、`editPane()`（三者只是用 `?hidden` 藏起来），所以无论当前在哪个 tab，`editPane()` 都会走 `draftList()` 的 `repeat(draft.lines, …)`（`551-594`）。
- **现象 2**：微调预览的高亮/跟随滚动逻辑永远不执行。
- **根因 2**：`paintNudgeFollow()` 用 `rows[0].dataset.index` 判断窗口起点（`434`），但 `nudgePreview()` 生成的行只有 `data-act` / `data-ms`（`404-414`），**从未写 `data-index`** → `firstIdx` 恒为 `-1` → `435` 直接 return。看起来「能跟随」只是因为 `s.position` 在 deps 里，整块重绘时 `from = active - 5` 的窗口被重建了。
- **证据**：

```js
// lyrics.js:431-435
const rows = box.querySelectorAll(".nudge__line");
if (!rows.length) return;
const firstIdx = Number(rows[0].dataset.index ?? -1);
if (firstIdx < 0) return;              // ← 恒真，下面全是死代码
```
- **建议修法**：deps 去掉 `s.position`，改用已有的 `lyricsPanelTick` + 200ms 节流（`paintNowRow()` 里的 `_lastNowPaint` 可复用）；`nudgePreview()` 的行补 `data-index=${i}`；`render()` 只构建当前 tab 的 pane。

### P1-4 · 队列面板每行 `state.queue.indexOf()` → O(n²)，且任意封面变化就重跑

- **位置**：`frontend/src/js/ui/panels.js:242-244`（`item()`）、`121-122`（deps）
- **现象**：队列很长时打开/更新播放列表面板明显卡住；任意一首歌换封面（`coverVersion()` 在 deps 里）都会再整块重算一次。
- **根因**：`const index = state.queue.indexOf(song.id)` 写在每行的模板函数里，而 `render()` 已经为 `list` 的每个元素调过一次 `item()` → O(n²)。deps 含 `s.queue`、`s.currentId`、`s.playing`、`coverVersion()`，四种动作都会触发全量重跑。
- **证据**：`panels.js:181` 先 `state.queue.map(id => songById(id))`，`242` 再对每个元素 `indexOf`；`122` 的 deps 里确有 `coverVersion()`。
- **量级（推测）**：5000 首队列 = 每次重绘约 1250 万次 `indexOf` 比较。
- **建议修法**：`render()` 里先建一次 `const pos = new Map(list.map((s, i) => [s.id, i]))`，`item(song, i)` 直接收下标；并把 `coverVersion()` 从 deps 去掉（缩略图由 `coverSrc` 指令自己处理，见 P2-5），只对变更行做局部更新。

### P1-5 · 设置层的 `s.config` 依赖是恒定引用（永不生效）→ 走非 settingsRev 路径改配置时设置界面不更新

- **位置**：`frontend/src/js/ui/settings-view.js:178-202`（deps 第 `191` 行 `s.config`）
- **现象**：设置弹层开着时点标题栏的「切换深浅色」（`.settings-layer` 的 `inset` 从 `--h-titlebar` 开始，标题栏仍可点，见 `layers.css:16-31`），主题实际换了，但「外观 → 深浅色模式」分段控件仍高亮旧值；主题卡片的 `data-active` 也可能停在旧主题。
- **根因**：`state.config` 从初始化起就是**同一个对象**（`store.js:217`，之后全是 `Object.assign(state.config, …)` / `state.config.x = y`，见 `store.js:1458`、`1578`），而 `sameDeps()`（`ui/base.js:38-45`）逐项 `===` 比较 → 这一项永远相等，等于没写。`theme.js#toggleTheme()`（`353-360`）只做 `state.config.themeMode = nextMode` + `applyResolvedTheme()` + `commit()`，既不 `++settingsRev` 也不 `requestAppUpdate()`；`applyResolvedTheme()` 里的 `config.theme = themeId`（`theme.js:279`）同样没人告知设置层。其它 deps（`themeRegistryVersion()`、`s.songs`、`s.folders`…）在这条路径上都不变。
- **证据**：

```js
// settings-view.js:191（依赖项）
s.config,
// store.js：config 的引用从未被替换
Object.assign(state.config, cfg);        // store.js:1578
state.config.themeMode = nextMode;       // theme.js:356（原地改）
```
- **建议修法**：把 `s.config` 换成一串**原始值**（`s.config.theme`、`s.config.themeMode`、`s.config.glassBlur`、`s.config.glassAlpha`…），或在 store 里加 `configVersion`，由每个改配置的入口自增、deps 用它。注意别让「音量」进 deps——`settings-view.js:198-201` 已解释过这条禁忌。

### P1-6 · 过滤规则输入框每敲一个字 → 全库重跑 `applyRules`；文件夹卡片每渲染一次 → O(文件夹数 × 曲库数)

- **位置**：`frontend/src/js/ui/settings-view.js:1484-1493`（`onInput` → `requestUpdate()`）、`478-479`（`rulesCard()` → `applyRules(state.allSongsRaw, state.filterRules)`）、`343`（`foldersCard()` → `state.songs.filter(s => s.path.startsWith(f.path))`）
- **现象**：在设置里改过滤规则（逐字输入）会明显掉帧；文件夹多、曲库大时打开设置或改任意控件都会卡一下。
- **根因**：`onInput` 直接 `this.requestUpdate()` → 整个设置层重渲染 → `rulesCard()` 里的 `applyRules`（`store.js:395-404`，含正则编译 + 全库逐首匹配）重新执行；`foldersCard()` 再对每个文件夹全库扫一遍 `startsWith`。
- **证据**：

```js
// settings-view.js:1484-1493
onInput(e) {
  if (e.target.dataset.act !== "rule-value") return;
  ...
  commit();
  this.requestUpdate();     // ← 每个字符一次全设置层重算
}
// settings-view.js:343
const count = state.songs.filter((s) => s.path.startsWith(f.path)).length;
```
- **量级（推测）**：20 个文件夹 × 20000 首 = 每次渲染 40 万次 `startsWith`；`applyRules` 是 2 万次 `matchCompiled`（每条启用规则一次正则 `test`）。
- **建议修法**：规则值用 300ms 去抖（`utils.js:123` 的 `debounce` 已有）再 `requestUpdate`；文件夹计数改成一次遍历同时累加（模块级缓存，`s.songs` 引用变化时才重算）；`applyRules` 的统计结果按 `(allSongsRaw, filterRules)` 引用缓存。

## P2 级问题

### P2-1 · `recalcVisible()` 每次都做一次 O(可见歌曲数) 指纹遍历（注释承诺「只在输入变化时重算」）

- **位置**：`frontend/src/js/store.js:543`（调用）、`573-589`（实现）、`519-526`（注释）
- **现象**：每次 `commit()` 都对全部可见曲目做一次 FNV 迭代（每首还要 `String(id)` 并逐字符异或）。扫描期间后端每 40 个文件推一次进度（注释 `522-523`），2 万首就是 500 次。
- **根因**：`visibleFingerprint(out)` 在 `if (!sameVisibleInputs(...))` 块**之外**被无条件调用（`532-543`）。注释 `526` 写的是「指纹只在输入变化时才重算」，与代码不符。
- **证据**：

```js
// store.js:527-547
const inputs = visibleInputs();
if (!sameVisibleInputs(inputs)) { visibleInputsCache = inputs; visibleResultCache = computeVisible(); }
const out = visibleResultCache;
state.visibleSongs = out;
const fingerprint = visibleFingerprint(out);   // ← 无条件
```
- **建议修法**：把指纹也放进 `if (!sameVisibleInputs(inputs))` 分支（内容只由输入决定），或在 `visibleInputs` 里用更便宜的判据短路。

### P2-2 · 歌词缓存 / 偏移表 / 种子色缓存无上限，失效入口是死代码

- **位置**：`frontend/src/js/playerhost.js:70-73`（`lyricsCache`/`autoMatched`/`lyricsPending`）、`192`（`lyricsOffsets`）、`166-178`（`invalidateLyrics`）；`cover-accent.js:29`（`seedCache`）；`store.js:1177-1183`（`state.progress`）
- **现象**：长时间使用（配合桌面歌词时 `ensureLyricsLoaded()` 每首切歌都预载）内存只增不减：每首歌的整份 LRC 文本 + 解析后的行对象常驻。
- **根因**：三个 Map/Set 从不清空；唯一清理函数 `invalidateLyrics` 全仓**只有定义、没有调用**（`grep -rn "invalidateLyrics" frontend/src` → 1 条 = 定义行）。`state.progress` 只有落盘副本被 `pruneProgress` 裁剪（`store.js:1186-1195`、`1353`），内存里那份无上限。
- **建议修法**：给 `lyricsCache` 加 LRU（例如最近 200 首，用 Map 插入序淘汰）；`clearQueue()`/`pruneOnlineSongs` 附近顺手清 `lyricsOffsets` 的孤儿项；`noteProgress` 里定期 `pruneProgress`。

### P2-3 · `pruneOnlineSongs()` 是死代码 → 在线试听登记表只增不减

- **位置**：`frontend/src/js/store.js:1011-1017`（定义）、`856-864`（`clearQueue` 里的 `onlineSongs.clear()` 是唯一清理点）
- **现象**：每点一次「试听」就在 `state.onlineSongs` 留一条完整曲目对象（含 `coverUrl`/`streamUrl` 字符串），离开队列后也不回收。
- **根因**：`pruneOnlineSongs` 从未被调用（`grep -rn pruneOnlineSongs frontend/src` → 1 条 = 定义行）。
- **建议修法**：在 `playSong()` 与 `removeFromQueue()` 末尾调用它（本身幂等），或在持久化分支里按 `queue + currentId` 修剪一次。

### P2-4 · 「待应用歌词偏移」只对当前歌丢弃：切歌后关面板，上一首的未应用偏移仍然生效

- **位置**：`frontend/src/js/ui/lyrics.js:1037-1046`（`closePanel`）、`frontend/src/js/playerhost.js:224-233`（`linesForSong`）、`192-208`（偏移表）
- **现象**：在 A 上微调 +1s（未点「应用到歌词」）→ 切到 B → 关面板，提示「未应用的微调已丢弃」，但 A 的歌词在详情页/桌面歌词里**仍然是 +1s**，界面上没有任何地方显示「未应用」。重启后归零，所以更难查。
- **根因**：`closePanel()` 只处理 `currentLyricsInfo().songId`（当前歌）的偏移，而 `linesForSong()` 对所有歌都无条件叠加 `lyricsOffsets.get(id)`。
- **建议修法**：把「待应用偏移」做成带 songId 的单一槽位（同一时刻只允许一首歌有待应用偏移，切歌即丢弃并提示），或 `closePanel()` 遍历 `lyricsOffsets` 全部清零（并清 `shiftedCache`）。

### P2-5 · 封面预加载没有负缓存：坏地址会在每次重绘时重新发请求

- **位置**：`frontend/src/js/ui/track-table.js:54-64`（`probe`/`swap`）、`frontend/src/js/ui/overlays.js:362-373`（`bindCoverFallback`）
- **现象**：曲库里存在失效封面地址时（缓存目录被手动删过、后端 `/cover/<hash>` 404），播放/暂停、切歌、拖动列表都会让该行重新走一遍「新建 Image → 请求 → error → 换 default → 下次重绘再请求」。
- **根因**：`probe` 的 `load`/`error` 都调 `swap`，把 `img.src` 换成失败的 `want`（`59-64`）；随后 `img` 的 error 事件又把 src 换成 `DEFAULT_COVER`。下一次该行重绘时 `img.getAttribute("src")`（=默认封面）`!== want`，于是再建 probe（`49-64`）——**没有「这个地址失败过」的记忆**。
- **建议修法**：模块级 `const failedCovers = new Set()`；`update()` 开头 `if (failedCovers.has(want)) { img.src = DEFAULT_COVER; return noChange; }`，`probe.onerror` 时 `failedCovers.add(want)`（可带 TTL/上限）。

### P2-6 · 「添加歌曲到歌单」弹窗整库一次性 repeat，筛选逐字重建全部行

- **位置**：`frontend/src/js/ui/add-songs.js:32-41`、`80-101`；`frontend/src/js/playlists.js:99-121`
- **现象**：2 万首曲库下点歌单「添加」会一次性插入约 10 万个 DOM 节点（每行 5 个）；筛选框每敲一个字重跑一遍 `filter` + 全部行模板；点「加入歌单」还要 `querySelectorAll` 全表。
- **根因**：`render()` 里 `repeat(songs, s => s.id, …)` 用的是**全部** `state.songs`（只有关键词过滤，没有分页/窗口化），`.addsongs__row`（`overlay.css:881`）也没有 `content-visibility`。`already` 与 `filtered` 是 getter，`render()` 里各被求值多次（`39`、`40`、`65`、`67`）。
- **建议修法**：加窗口化，或「最多渲染前 N 条 + 提示继续输入关键词」；`filtered` 用 `_query` 缓存；`.addsongs__row` 补 `content-visibility: auto; contain-intrinsic-size: auto 44px`。

### P2-7 · 每次设置层重绘都重建整张 swatch 样式表（全文档样式失效）

- **位置**：`frontend/src/js/ui/settings-view.js:274-276`（render 里调 `ensureSwatchStyles()`）、`frontend/src/js/settings.js:128-138`、`frontend/src/js/runtime-tokens.js:117-137`
- **现象**：设置层每重绘一次（拨开关、敲规则、扫描状态变化…）都会 `deleteRule` 掉全部规则再 `insertRule` 回来。
- **根因**：`replaceStyleRules` 先倒序删光 `swatch-styles` 的所有规则再逐条插入（`runtime-tokens.js:126-133`）；`ensureSwatchStyles()` 只在「主题清单变了」时才有必要重建，却被放在 `render()` 里（`settings-view.js:275`）。
- **建议修法**：把 swatch 表重建挪到 `themeRegistryVersion()` 变化时，或让 `ensureSwatchStyles` 自己缓存 `listThemes()` 的签名，签名不变直接返回现成的 index 函数。

### P2-8 · 滚动期每帧重新模糊：3 处 sticky + backdrop-filter，另有 12+ 处常驻 backdrop-filter 表层

- **位置**：`frontend/src/styles/components/tracktable.css:53-58`（`.tracks__head` sticky + `var(--panel-blur)`）、`components/content.css:5-15`（`.content-header` sticky + blur）、`components/settings.css:27-32`（`.settings__nav` sticky + blur）
- **现象**：列表滚动时表头与内容头下方的像素每帧都在变，两张 backdrop 面就要每帧重新采样 + 模糊；`--panel-blur` 默认是 `blur(22px) saturate(...)`（`tokens.css:192`），用户在「模糊程度」里拉到 48px 后成本线性上升。侧边栏（`sidebar.css:11`）与底栏浮层（`overlay.css:18,253,347,494,515,647,749,837`）是同一机制。
- **根因**：`.track` 有 `content-visibility: auto`，但表头不是；模糊层叠在滚动内容之上，浏览器无法缓存结果。
- **建议修法**：表头改为不透明底色，或加「滚动中 `backdrop-filter: none`」的 `data-scrolling` 状态（滚动停止 120ms 后恢复）；也可给 sticky 头单开一档更小的令牌（如 `--blur-head: blur(8px)`）。

## P3 级问题

1. **未清理的定时器/观察者（playerhost.js）**：`ensureCarouselTicker()` 的 1Hz `setInterval`（`819-824`）在首次打开详情页后永不 `clearInterval`，详情页关闭后仍在跑（`tickCarousel` 会提前 return，但时钟一直存在）；`observeTheme()` 的 `MutationObserver`（`1050-1064`）也从不 `disconnect()`。另外 `main.js:509` 在 Wails 下也无条件 `startMockTicker()`（`store.js:1243-1266`），一个 250ms interval 长期空转（靠 `audioEngineActive()` 提前返回）。
2. **`switchTimer` 悬挂 12 秒**：`audio.js` 的换源失败/元素 error 分支只写 `switchPhase = SWITCH_IDLE`（`332-333`、`407`、`412-413`），不清 `beginSwitch()` 起的 12s 兜底定时器（`199-203`）；它到点后 `endSwitch()` 因 phase 不是 LOADING 而早退。无害，但属于未取消的定时器。
3. **resize 推 0×0**：`watchResize()`（`playerhost.js:780-787`）观察 `#playerview-stage`；详情页关闭时该元素 `display:none`，`ResizeObserver` 会把 `{width:0,height:0}` 推给皮肤（`784`）。按宽高做等比布局的皮肤会拿到 0。建议 `open` 为 false 时跳过推送。
4. **`resizeObserver` 只在 `unmountSkin()` 里断开**（`774-777`），而 `unmountSkin` 只在关闭动画结束后触发；「关闭→立即打开」靠 `renderPlayerView` 的 `clearTimeout(host.closeTimer)`（`902-905`）兜住。逻辑正确但很依赖时序，建议 `mountSkin` 开头也 `disconnect` 一次。
5. **`MpQueuePanel.deps` 缺 `s.songs`**（`panels.js:122`）：面板打开时重扫曲库（`state.songs` 整体替换、id 不变）不会再触发面板重绘，队列行会继续显示旧对象里的标题/歌手/封面，直到别的依赖变化。建议把 `coverVersion()` 换成/补上 `s.visibleVersion`。
6. **导出但无人调用的 API（死代码）**：`store.js#stopMockTicker`（`1268`）、`runtime.js#invalidateRuntime`（`85`）、`playerhost.js#invalidateLyrics`（`166`）、`store.js#setCoverOverride`（`966`）、`slider.js#setBuffer`（`139`）。其中 `setBuffer` 对应 `ui/playerbar.js:179` 的 `#progress-buffer`，它的默认样式是 `transform: scaleX(0)`（`playerbar.css:334-342`）→ 缓冲进度条永远是 0 宽，是一条「画了但从不更新」的装饰（`grep -rn "setBuffer" frontend/src` 只有定义一处）。
7. **`search.js` 每次重绘都读一遍 localStorage**：`render()` 里 `const history = loadHistory()`（`ui/search.js:116`）+ `loadHistory` 里的 `JSON.parse`（`32-40`）；deps 含 `searchState.rev`（`69`），输入框每敲一个字 `bump()` 一次（`141-144`）→ 每字一次同步 localStorage 读 + 反序列化。建议在 `addHistory/removeHistory/clearHistory` 时维护模块级缓存。
8. **封面回填 200 首上限对前端不可见**：`services_cover.go:876-881` 的 `maxCachedPreviews = 200` 决定 `CachedSets()`（`909-928`）只回填前 200 首；`main.js:151-162` 直接 `setCoverSets(map)`，超出部分的「用户换过的封面」重启后静默消失。建议后端返回 `{sets,total,truncated}`，或前端给一行提示。
9. **`ui/sidebar.js` 没有 `disconnectedCallback`**：`firstUpdated()` 里创建的 `Sortable`（`27-39`）没有销毁路径（对比 `track-table.js:108-112`、`panels.js:169-174` 都销毁了）。当前 `mp-sidebar` 常驻不移除，属潜在泄漏。

## 补充：每帧 / 每次更新的无谓 DOM 写入

- `slider.js:27-38` 的 `paint()` 无条件写 `fill.style.transform`、`thumb.style.left`、`bubble.textContent`、`setAttribute("aria-valuenow")` 四处；而 `set(v, {silent:true})`（`129-135`）**故意绕过等值判断**，所以底栏每次 `updated()`（`ui/playerbar.js:128-147`）都会重画一次进度条与音量条，即便值没变。`.task/perf-lit.json` 的 `playing` 段 3 秒内 84 次 attributes 变更与此一致。
- `playerhost.js#pushOptions()`（`857-863`）每次调用都 `JSON.stringify(options)` 做去重，而它挂在每次 `renderPlayerView()`（`961`）上——即每个播放进度 tick。对象很小，成本可忽略，但属于固定分配。
- `spectrum()`（`audio.js:646-660`）每次调用新建 `Float32Array`，`pushSpectrum()`（`playerhost.js:1043`）再 `Array.from(...)` 一次；30Hz 下每秒 60 次小块分配 + 2 次 32 元素数组构造。建议复用两个模块级缓冲区。

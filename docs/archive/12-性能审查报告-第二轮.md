## 2. P0 级问题

### P0-1 整个曲库（含 base64 封面）在**每次** `scan:done` 全量走 IPC

**证据链**

1. `internal/bootstrap/config.go:50` —— `Cover string \`json:"cover"\` // data URL`
2. `services.go:84-86` —— `Songs()` 直接返回 `s.lib.Songs()`，不做裁剪
3. `frontend/src/js/main.js:256-273` —— `scan:done` 回调里 `await backend.songs()`
4. `internal/library/library.go:449-545` —— `RescanPaths`（**文件夹监听触发的增量重扫**）末尾也走 `m.notifyChanged(out)`
5. `services.go:55-59` —— `SetChangedFunc` 把它转成 `emit("scan:done", res)`

也就是说：**用户往被监听的文件夹里丢进一首歌，就会重新传一次整库的 base64 封面**。
按 §1.1 的比例，5,000 首曲库每次约 484 MB 过 IPC，且这份数据随后在渲染进程里再被复制到
`state.allSongsRaw` 与 `state.songs`（两个引用指向**同一个数组**，见 §3 的代码质量报告）。

**修法（按性价比排序）**

- 列表接口不再下发 `cover`：新增轻量 DTO（去掉 `Cover` 字段）或给 `Song` 加 `CoverURL`（同源 HTTP 地址）。
  项目里已经有成熟的同源静态托管范式可复用（`internal/media/server.go:179-192` 的 `AudioPrefix` 中间件）。
- 封面走 `/cover/<songID>` 同源端点 + 浏览器缓存头；列表里只放 URL，`<img loading="lazy">` 天然按需拉取。
- 前端 `utils.js:262-268` 的 `coverOfRaw()` 已经支持 `song.coverUrl` 优先于 `song.cover`，
  所以**前端几乎不用改**——只要后端把 data URL 换成 URL。

### P0-2 曲目表零虚拟化

**证据**：`frontend/src/js/ui/track-table.js:167-173`

```js
<div class="tracks__body">
  $
  {repeat(
    songs,
    (song) => song.id,
    (song, index) => this.rowTemplate(song, index, mode)
  )}
</div>
```

`repeat` 对**全部** `state.visibleSongs` 建行，没有窗口化。实测 5,000 首 = **136,389 个 DOM 节点**，
单次提交新增 **153,762** 个节点，首帧 **2,882 ms**。项目自己也承认了量级——`main.js:433-446`
的压测参数上限写的是 `?songs=1000`，而 1,000 首就已经是 28,386 个节点 / 656 ms 了。

**影响**：任何触发列表重建的操作（重扫、切视图、改密度、改专辑列显隐）都会重新付这笔钱；
且 13 万节点的树会让后续每一次样式失效都变贵（`albumToggle` 净耗时约 1,086 ms 就是证据）。

**修法**：固定行高的窗口化渲染（只渲染视口 ± 缓冲区）。行高由 `data-density` 决定，是常量，改动量可控。
若暂不做虚拟化，至少把「改专辑列 / 改密度」从「重建列表」降级为纯 CSS 类切换（目前已在用 `data-album`/`data-density` 属性，
方向是对的，但 `deps` 里带了 `s.visibleSongs.length` 之外的东西仍会触发重渲染）。

### P0-3 `commit()` 无条件重算 `recalcVisible()`

**证据**：`frontend/src/js/store.js:232-245`

```js
export function commit(mutator, options = {}) {
  if (typeof mutator === "function") mutator(state);
  recalcVisible();          // ← 无条件
  if (options.persist !== false) persist();
  ...
}
```

而 `recalcVisible()`（`store.js:406-447`）每次都做：

- `currentSongList()` → `new Map(songs.map(...))`（`store.js:392`）—— **一次全量 Map 分配**
- `out.slice().sort(...)` 带 `localeCompare` 的全量排序（`store.js:427`）
- `visibleFingerprint()` 全量遍历（`store.js:465-481`）
- `songIndex = new Map(state.songs.map(...))`（`store.js:446`）—— **又一次全量 Map 分配**

实测一次等价重算 ≈ **20.6 ms**（5,000 首）。这不是理论值：`commit()` 的调用点遍布 UI
（`setVolume` 每次 `pointermove`、`seek`、切换开关、收后端事件……），而**扫描期间的代价最集中**：

`internal/library/library.go:585`

```go
if n%40 == 0 {
    m.report("meta", n, len(items))
}
```

每 40 个文件一次进度事件 → `main.js:249-254` 每次都 `commit()`。20,000 首曲库 =
**500 次 × 20 ms ≈ 10 秒**的额外主线程占用，纯粹为了让进度条上的数字动。

**修法**

1. 给 `recalcVisible` 加 memo key（`view / playlistId / query / sortKey / sortDir / state.songs 引用 / queue 引用`），
   命中就 `return`。绝大多数 `commit()` 根本不改这四个输入。
2. `songIndex` 只在 `state.songs` 引用变化时重建（代码里已经有 `lastFingerprintSongs` 这套引用比较的先例）。
3. `SORTERS` 改用缓存 `Intl.Collator`（实测 23.4 ms → 13.2 ms，省 44%）。
4. 扫描进度节流到 `requestAnimationFrame` 或 200 ms 一档（后端已经 40 文件一档，前端再合并一次即可）。

### P0-4 `scan:done` 里的 O(n²)

**证据**：`frontend/src/js/main.js:271`

```js
removed: [...prev].filter((id) => !kept.some((s) => s.id === id)).length,
```

`filter` 里套 `some` = O(prev × kept)。5,000 首就是 2,500 万次比较，20,000 首是 4 亿次。
**同一个功能在 `store.js:1484-1486` 已经写对了**（先建 `Set`），这里是漏改的一处：

```js
const nowIds = new Set(kept.map((s) => s.id));
const removed = [...prevIds].filter((id) => !nowIds.has(id));
```

**修法**：直接照抄 `store.js` 的写法（两处逻辑应当合并成一个函数，见代码质量报告）。

## 3. P1 级问题

### P1-1 `SaveCache()` 用 `MarshalIndent` 重写 5.6 MB JSON

`internal/library/library.go:239-256`

```go
m.cacheMu.RLock()
cf := cacheFile{Version: cacheVersion, Entries: m.cache}
m.cacheMu.RUnlock()
raw, err := json.MarshalIndent(cf, "", "  ")   // ← 缩进 = 额外 ~15% 体积 + 额外 CPU
```

每次全量扫描结束（`library.go:435`）和退出（`main.go:386`）都会跑一遍。
文件本体实测 5.59 MB，其中 **99.6% 是 base64 封面**——对 base64 做缩进排版毫无可读性收益。

**修法**：`json.Marshal`（去掉缩进）；更彻底的做法是把 `Cover` 从缓存索引里拆出去，
索引只留元数据（`library.go:41-54` 的 `cacheEntry.Cover` 字段）。

**附带问题**：`library.go:243-247` 在 `RUnlock()` **之后**才 `json.Marshal(cf)`，
而 `cf.Entries` 与 `m.cache` 是**同一个 map 引用**。并发写会直接触发 Go 运行时的
"concurrent map iteration and map write" 致命错误（不是普通的 race 警告）。
当前靠「扫描被 `beginScan/endScan` 串行化」侥幸不触发，但这是个结构性隐患。

### P1-2 文件夹曲目数统计是 O(folders × songs)，且持写锁 + 每对一次 `filepath.Rel`

`internal/library/library.go:418-432`

```go
m.mu.Lock()
for i := range m.folders {
    ...
    count := 0
    for _, s := range res.Kept {
        if isUnder(s.Path, m.folders[i].Path) {   // 内部是 filepath.Rel（字符串处理 + 分配）
            count++
        }
    }
    m.folders[i].TrackCount = count
}
foldersCopy := append([]bootstrap.Folder(nil), m.folders...)
m.mu.Unlock()
```

`RescanPaths` 里同样一份（`library.go:522-533`），而且那边遍历的是**整个 `m.songs`**。
20 个文件夹 × 100,000 首 = **200 万次 `filepath.Rel`**，全部在写锁内完成，阻塞所有
`Songs() / SongByID()` 调用。

**修法**：一次遍历把每首歌按「最长匹配的文件夹前缀」归到桶里（`strings.HasPrefix` + 目录边界判定，
或先对文件夹路径排序后单遍扫描），复杂度降到 O(songs × folders) 但常数极小，且不必持锁。

### P1-3 封面缓存的每次单张变更都重写整份索引

`internal/metacache/store.go:822-855`（`saveIndexLocked`）

```go
payload = map[string]any{"version": 2, "entries": s.covers}
raw, err := json.MarshalIndent(payload, "", "  ")   // ← 整个封面索引
```

而 `AddCover` / `SetActiveCover` / `RemoveCover` / `DeleteCover` / `SaveLyrics`
全部**持着同一把 `s.mu`** 调它，并且锁内还包括图片字节的落盘（`store.go:333-374`）。
单张封面的增删 = O(整个索引) 的 CPU + 一次落盘，且期间所有读接口（`CoverDataURLs`、`CoverIDs`）阻塞。

**这一点在批量场景会放大成 O(n²)**——`services_cover.go:1100-1114`：

```go
for _, id := range s.cache.CoverIDs() {
    if err := s.cache.DeleteCover(id); err == nil { covers++ }   // 每次都重写整份索引
}
```

「清空封面缓存」在有 500 首歌有封面时 = **500 次全量索引 `MarshalIndent` + 500 次落盘**。

**修法**：索引写入去抖/合并（标脏 + 退出/空闲时统一写）；或把 `entries` 拆成一歌一文件。
清空场景提供批量接口（一次 `Clear()`，只写一次索引）。

### P1-4 `CoverDataURLs` 持锁读盘并 base64 编码

`internal/metacache/store.go:436-451`（`readItemLocked` → `os.ReadFile` 在 476 行）
配合 `maxCoverCount = 12`、`maxCoverBytes = 6<<20`（`store.go:106,112`），
一次调用可能持锁读 72 MB、生成约 96 MB base64 字符串。

**修法**：锁内只取文件路径，读盘与编码放到锁外（`CoverPathAt` 已经有这个能力，见 `store.go:415`）。

### P1-5 `ffmpeg.Probe` 没有 `-t 0`，每次探测都全量解码

`internal/ffmpeg/ffmpeg.go:347-353` 的注释说：

```go
// 加上 -t 0 可以在多数情况下提前结束，避免为拿时长而解码整首歌。
```

但 `ffmpeg.go:377-383` 的实际参数里**没有 `-t 0`**（对比 `SoundDurationMS` 的 `ffmpeg.go:420` 是有的）：

```go
cmd := executil.CommandContext(ctx, ffmpegPath,
    "-hide_banner", "-nostdin",
    "-i", path,
    "-vn", "-map", "0:a",
    "-c:a", "pcm_s16le",
    "-f", "null", "-",        // ← 全量解码到 null
)
```

配合 `internal/library/library.go:700` 的 `maxProbePerScan = 48`、并发 2、单次 8 秒超时：
最坏情况一次扫描要付 **48 / 2 × 8 = 192 秒**的墙钟时间，且这些 CPU 全花在解码上。

**修法**：补上 `-t 0`（探测元信息只需要 header），并把注释与代码对齐。

### P1-6 meta 层把整个音频文件读进内存

- `internal/meta/covers.go:47` —— `raw, err := os.ReadFile(path)`（无大小前置判断）
- `internal/meta/meta.go:396, 405-407` —— `mp4Duration` 先读 2 MB 头，必要时
  `whole := make([]byte, st.Size())` 把**整个文件**读进来

扫描并发为 `ScanConcurrency`（默认 4，`library.go:553-568`），
一份 100 MB 的 FLAC 在 4 并发下就是 400 MB 瞬时占用 + 400 MB 磁盘读。

**修法**：`os.Stat` 先判大小并在超限时跳过封面解析；mp4 的 `moov`/`mvhd` 用 box 长度
直接 `ReadAt` 定位（box 头部自带 length），不需要读全文件。

### P1-7 `sortFloats` 是 O(k²) 插入排序，但切片并不小

`internal/loudness/bs1770.go:384-395`

```go
// 小切片，插入排序足够；避免为一次测量引入额外依赖
for i := 1; i < len(a); i++ {
```

`short` 装的是全部通过门限的 400 ms 块；`stepSeconds = 0.100`（`bs1770.go:186`）
意味着约 **10 × 时长（秒）** 个元素：3 分钟的歌约 1,800 个，1 小时的 DJ set 约 36,000 个。
36,000² / 4 ≈ 3.2 亿次比较。注释里的「小切片」假设不成立。

**修法**：`sort.Float64s`（标准库，不引入新依赖——注释里的顾虑本身也不成立）。

### P1-8 `discoverThemes()` 串行 N+1 次 IPC，且卡在首帧之前

`frontend/src/js/theme.js:74-92`

```js
for (const t of res) {
  if (!t?.id) continue;
  const css = await backend.loadTheme(t.id); // ← 串行 await，每次一个 IPC 往返
  if (typeof css === "string" && css.trim()) injectTheme(t.id, css);
}
```

调用链：`main.js:466 await initTheme()` → `main.js:136 await discoverThemes()`，
而 `main.js` 直到 `main.js:500` 才 `hideBootSplash()`。所以**每个主题文件的读盘 + 注入
都串在首屏关键路径上**（内置 3 款起步，导入多款后线性变差）。

**修法**：`Promise.all` 并发；或后端一次返回全部 CSS（`ThemeService` 支持批量接口）。

### P1-9 `Store.Get()` 深拷贝 + `saveLocked()` 整份 `MarshalIndent` + 持锁重试

`internal/bootstrap/config.go:745-759` —— `Get()` 每次都深拷贝 `Folders / FilterRules /
Playlists（含每个 SongIDs）/ LikedIDs / LyricsSources`。100,000 首「我喜欢」= 每次都拷 10 万个 string。

`internal/bootstrap/config.go:777-811` —— `saveLocked()` 是 `json.MarshalIndent` 整份配置；
Windows 上 rename 失败时**持写锁**退避重试 8 次（`time.Sleep(5..40ms)`，累计最多 180 ms），
期间所有 `Get()` 全部阻塞。

调用密度：`services.go:64-81` 的 `ToggleLike` **每点一次「我喜欢」就重写整份配置**
（包括所有歌单的全部 songIds）；`library.go:434` 每次扫描也写一次。

**修法**：`ToggleLike` 走增量持久化（或与快照写盘一样去抖合并）；
重试循环挪出锁外（失败后用独立小锁重试 rename）；缩进用 `json.Marshal`。

## 6. 已检查、未发现问题的部分（避免重复排查）

- **媒体服务 Range / Seek**：`serveNative` / `serveFile` 全部委托给 `http.ServeContent`
  （`internal/media/server.go:316-347`），Range、If-Range、206、416、HEAD 由 `net/http` 正确处理，
  **没有**把整个音频文件读进内存。
- **路径穿越**：`id → song` 只经过曲库注册表（`server.go:261-270`），转码产物名由
  `bootstrap.StableID` 生成，未发现可利用路径。
- **HTTP 出站响应体**：全部包了 `io.LimitReader`（`coverfetch` 4MB/2MB、`lyricsfetch` 12MB、
  `bilibili` 16MB），且每个 `resp.Body` 都有 `Close`。**没有**无界读取，**没有** Body 泄漏。
- **HTTP 连接复用**：三个客户端都是包级变量 + 默认 Transport，没有逐请求新建客户端。
- **context 传播**：出站请求全部走 `NewRequestWithContext`，且各 provider 有独立超时。
- **Go 侧 goroutine / 文件句柄泄漏**：本轮审查范围内未发现。
  `library.go:568-603` 的 worker 池、`enrichDurations` 的信号量、`loudness.go:466-505`
  全部经由 `defer wg.Done()` / `defer func(){ <-sem }()` 收口。
- **前端定时器清理**：`panels.js:458-468`、`playerbar.js:76-89` 都在 `onDisconnected` 里
  `clearInterval`。封面指令的 `probe` Image 用完即弃，无监听器泄漏（`track-table.js:45-74`）。
- **`<audio>` 事件**：`audio.js:255-330` 的监听器在同一个元素上注册一次，无重复绑定。

## 7. 建议的修复顺序

按「收益 / 改动风险」排序：

1. **P0-1 列表不下发 base64 封面**（改后端 DTO + 一个同源封面端点；前端 `coverOfRaw` 已兼容 `coverUrl`）。
   这一条单独就能把增量监听事件的代价从数百 MB 降到几十 KB。
2. **P0-2 曲目表虚拟化**（固定行高窗口化）。5,000 首首帧 2.9 s → 目标 < 300 ms。
3. **P0-3 `recalcVisible` 加 memo + 缓存 `Intl.Collator`**（约 20 行改动，直接消掉扫描期间的 10 秒级卡顿）。
4. **P0-4 `main.js:271` 改 `Set`**（1 行，O(n²) → O(n)）。
5. **P1-5 补 `-t 0`**（1 行，把最坏 192 秒的探测降下来）。
6. **P1-1 `MarshalIndent` → `Marshal`**，并把封面从元数据索引里拆出去。
7. **P1-3 索引写入去抖 + 批量清除接口**（修掉 O(n²) 的封面批量操作）。
8. **P1-2 文件夹计数单遍归桶**、**P1-4 锁外读盘编码**、**P1-9 配置增量持久化**。
9. **P1-7 `sort.Float64s`**、**P1-8 `Promise.all`**、**P1-6 按需读取**。
10. P2 串按 §4 表格顺序处理；其中 **P2-3（`ClearCache` 删用户目录里的所有 WAV）建议优先**——
    它是数据破坏风险，不只是性能问题。

## 一、全局问题（跨模块，影响最大）

### G1. 每帧广播都重建整库 id 映射 —— O(n) 分配挂在 4Hz 热路径上 【性能 · 高】

**位置**：`frontend/src/js/store.js:472-486`（`currentSongList`）、`:558-597`（`recalcVisible`）

`currentSongList()` 里 `const byId = new Map(songs.map((s) => [s.id, s]));` 每次调用都
重建整库 Map。`recalcVisible()` 由 `commit()` **无条件**调用，而 `commit()` 又被
`<audio>.timeupdate`（约 4 次/秒）经 `notify()` 驱动。

**实测**（node，模拟同样分配量）：

| 曲库规模 | 单次 notify | 4Hz 下每秒 |
|---|---|---|
| 1,000 | 0.028 ms | 0.1 ms |
| 5,000 | 0.088 ms | 0.4 ms |
| 20,000 | 0.485 ms | 1.9 ms |
| 100,000 | 3.06 ms | **12.2 ms** |

**修复**：`currentSongList` 直接复用已有的 `songIndex`（`:593-596` 已经有正确的
「随 `state.songs` 引用变化才重建」逻辑），并把重建提到 `computeVisible` 之前。

### G2. 数据竞争：`snap := *task` 无锁拷贝正在被 worker 改写的工作任务 【稳定性 · 高】

**位置**：`services_download.go:274-279`

`task` 就是 append 进 `s.tasks` 的**同一个指针**（`:301`），worker goroutine 在
`updateTask` 闭包里改 `t.Done` / `t.Path` / `t.State`；而 `snap := *task` 这次
整结构体拷贝发生在锁外。标准 Go 数据竞争，`go test -race` 会直接报。

**修复**：把拷贝放进 `newTaskLocked` 那次持锁区间内（`:268` 之后、`:269` 解锁前）。

### G3. watcher 每次落盘触发都做 O(文件夹 × 曲目) 全场扫描 【性能 · 中】

**位置**：`internal/library/library.go:713-724`（`RescanPaths`）、`:604-616`（`Scan`）

`for i := range m.folders { ... for _, s := range m.songs { if isUnder(...) } }`
—— 整段在**写锁内**。`RescanPaths` 由**文件夹监听**触发。

**实测**（100,000 首 × 20 文件夹，go run）：单次 **17.3 ms**；10 次 watcher 落盘 **163 ms**。

**修复**：一次遍历按文件夹前缀归类计数（O(N) 而非 O(F×N)），结果算出锁外。

### G4. 元数据缓存「已探测」标记在扫描被取消时丢失 【稳定性 · 中】

**位置**：`internal/library/library.go:917-1010` 与 `:575-578`

`enrichDurations` 把 `Probed: true` 写进内存缓存（`:993`），但落盘只在 `Scan` 末尾的
`SaveCache()`。`ctx` 一取消，`:575-578` 直接 return，**不保存** —— 下次扫描会把
同样的最多 48 个文件再起一遍 ffmpeg 进程。

**修复**：取消分支里也调一次 `m.SaveCache()`（`cacheIsUsable` 已保证安全）。

### G5. `metacache` 批量清理是 O(n²) 的全量索引重写 【性能 · 中】

**位置**：`services_cover.go:1100-1117`

逐个调 `DeleteCover` / `DeleteLyrics`，而 `internal/metacache/store.go:591-613` 的
每次删除都会 `saveIndexLocked` —— **重新序列化并原子重写整个 index.json**。
500 首缓存 ⇒ 500 次全文件写入 + 500 次 fsync。

**修复**：给 `metacache.Store` 加 `ClearAll(kind)`，一次持锁内删文件 + 重写一次索引。

## 二、逐模块问题

### internal/library
- **L1**（稳定性 · 中）`RescanPaths` 在写锁内做 G3 的循环。
- **L2**（稳定性 · 低）`walkFolder`（`:1032`）单子目录 `d == nil` 时 `return nil` 会
  **静默跳过整个子树**，曲库被截断而状态仍是 `ok`。

### internal/metacache
- **M1**（性能 · 中）`Stats()`（`:739-754`）的 `dirSize(s.dir)` 是递归全目录遍历，
  封面目录可上万文件，且它在设置界面打开时同步执行。
- **M2**（稳定性 · 低）`quarantineIndexLocked`（`:788-798`）rename 失败时「以空索引继续」，
  随后任意保存都会把空表写成权威 —— 磁盘上的图全成孤儿。

### internal/media
- **D1**（性能 · 中）`evictIfNeeded`（`:440-477`）用选择排序挑最旧项，O(k²)。
- **D2**（稳定性 · 中）`CacheStats`（`:513-523`）只统计内存表，与磁盘实际占用不一致。

### internal/loudness
- **V1**（稳定性 · 低）`Save()`（`:213-240`）在锁内清 `dirty` 后才 Marshal + 落盘；
  期间新的测量写入会被本次 Save 吞掉（丢一次持久化）。

### internal/ffmpeg
- **F1**（性能 · 中）`Probe` / `SoundDurationMS`（`:383-389`、`:423-427`）把 ffmpeg stderr
  **全量缓冲进无上限 `bytes.Buffer`**，而消费方只需要前 ~2KB。`Probe` 刻意没加
  `-loglevel error`，默认级别逐帧打印进度行；`enrichDurations` 一次探 48 个文件。
  **修复**：加 `-nostats` + 限长 writer。

### internal/coverfetch / internal/lyricsfetch
- **C1**（性能 · 高）`aggregator.go:255` 的容量保护是 `a.cache = map[string]cacheEntry{}`
  —— **整体清空**，连带丢掉刚写入的有效项；512 首对正常曲库「浏览一遍就跨过」。
  **修复**：先淘汰过期项，再淘汰最旧的 ~64 条。
- **C2**（性能 · 高）`Find`（`:125-183`）**没有单飞**。列表页同时渲染 N 个缺失封面
  ⇒ N × 5 个来源 goroutine + N × 5 次外网请求。**修复**：加 `map[string]*inflight`。
- **C3**（稳定性 · 中）`resolve.go:134-150` 的 `break collect` 提前返回时，已在跑的
  下载 goroutine 不被等待（靠 `defer cancel()` 在函数返回后才中止）。`firstGood` 让
  grace 窗口在**第一个成功候选**时就启动，所以走的是**快路径**。
  **修复**：`dlCtx, dlCancel := context.WithCancel(perCtx)` + `defer dlCancel()`。
- **C4**（稳定性 · 中）`lyricsfetch/types.go:152-177` 同样的提前返回，另两个 provider
  的 goroutine 仍跑满 6 秒超时且无人读其输出。
- **C5**（性能 · 中）`services_cover.go:190-201` 的 `LookupAll` 把最多 8 张图 base64
  后经 IPC 返回（≈21MB 字符串）。项目里已有 `/online/cover?src=` 同源代理可直接用。

### 根目录服务层
- **S1**（稳定性 · 中）`services_online.go:418-459` 的 `proxyStream` 用 `http.DefaultClient`
  （Timeout 0）读 CDN body；CDN 中途卡住则 `io.Copy` 一直阻塞。`services_download.go:536-593` 同样。
- **S2**（稳定性 · 中）`bilibili/audio.go:181` 设 `ExpiresAt = now+90min`，而

- **S3**（性能 · 中）`services_download.go:574-583` 每 400ms 序列化**全部任务**经 IPC 推送；
  8 个并发下载 ⇒ 每秒 20 次全量面板序列化，而实际增量只是一个整数。

### frontend/src/js
- **A1**（性能 · 中）`theme.js:283-322` 的 `applyResolvedTheme` 每次都 `forceStyleRefresh()`
  （改 body 属性 → **整棵树**样式重算）+ `invalidateGlassBase()`；而
  `cover-accent.js:84-89` 的 `applySeed` 在**每次换歌**取色完成后都会调它。
  **修复**：种子色变化只需重下发令牌，`forceStyleRefresh` 仅在 `data-theme` 真变时需要。
- **A2**（稳定性 · 中）`runtime-tokens.js:27-39` 的 `flush()` **每次删除全部规则再插一条**；

- **A3**（稳定性 · 低）`playerhost.js:986-1001` 换歌分支 `await getLyrics` 期间再换歌则 `return`，

### frontend UI 组件

## 三、已确认**不是**问题的部分（避免误改）

- 所有 `http.Client` 都设了有限 `Timeout`（coverfetch 15s×2、lyricsfetch 15s、ai 20s、bilibili 20s）。
- HTTP 响应体在所有路径上都被 `Close`。
- ffmpeg 调用没有未排空的 pipe（`Stdout = nil`，只缓冲 stderr）。
- `ai_vendor.go` 是纯映射代码，无 I/O。
- `library.isUnder` 的字符串前缀快路径（`:1092-1099`）语义正确，已正确处理 `..hidden` 边界。
- `metacache.CoverDataURLs` 已把读盘与 base64 移出锁外（`:442-459`），是正确写法。
- `loudness.Save` / `library.SaveCache` 都已在锁内复制 map，避免并发 map 迭代崩溃。
- `frontend/src/js/dom.js` 是 25 行纯 re-export，无逻辑、不可能泄漏。

## 四、已实施的修复（全部经实验验证）

每条修复都先用最小实验证明「改前确实慢 / 确实错」，再改，再用**反证测试**
（把旧实现放回去 → 测试必须失败）确认测试不是空转。

### 已修复 G1 · 每帧重建整库 Map
**文件**：`frontend/src/js/store.js`

- `currentSongList()` 不再自建 `new Map(songs.map(...))`，改为复用 `songIndex`；
  曲库视图直接短路返回 `songs`。
- `songIndex` 的重建**提前到 `computeVisible()` 之前**（原来在之后，会读到上一轮
  索引 —— 曲库整体替换时可能漏歌）。
- `songIndex` 声明上移到 `currentSongList` 之前（消除 `let` 暂时性死区的隐性依赖）。

**实测（node，模拟真实分配量）**：

| 曲库 | 改前/次 | 改后/次 | 提升 |
|---|---|---|---|
| 5,000 | 0.558 ms | 0.047 ms | 12x |
| 20,000 | 2.386 ms | 0.234 ms | 10x |
| 100,000 | 22.45 ms | 1.358 ms | 17x |

**浏览器验证**（CDP + 真实 Edge，构建产物）：`queueVisible: 25` 正确。

### 已修复 G2 · `snap := *task` 数据竞争
**文件**：`services_download.go`

把结构体快照移进 `newTaskLocked` 那次持锁区间内，消除对 worker 正在改写的指针的
无锁拷贝。`go test -race ./...` 全部通过。

### 已修复 G3 · watcher 触发的 O(文件夹 × 曲目) 全场重算
**文件**：`internal/library/library.go`（`RescanPaths`）

只重算「与本次变更目录有包含关系」的文件夹，其余沿用旧值。

**实测（100,000 首 × 20 文件夹，单次 watcher flush）**：**10.21 ms → 0.58 ms（17x）**。

**回归测试**：`TestRescanPathsUpdatesAllAffectedFolderCounts`、
`TestRescanPathsStillUpdatesStatusForAffectedFolder`。
**反证**：把包含关系判断改成 `dir == folder.Path` → 测试失败（`fa:2，期望 3`）。

### 已修复 G4 · 取消扫描时丢失「已探测」标记
**文件**：`internal/library/library.go`

补时长阶段被取消的分支里补一次 `SaveCache()`，避免下次扫描对同一批无时长文件
（wma / ape / dsf）重复起 ffmpeg 子进程。

### 已修复 F1 · ffmpeg stderr 无上限缓冲
**文件**：`internal/ffmpeg/ffmpeg.go`

新增 `boundedBuffer`（上限 8KB，`Write` 仍返回 `len(p)` 以符合 `io.Writer` 契约）；
`Probe` 补上 `-nostats`（`SoundDurationMS` 本来就有），两处都改用它。

**测试**：`TestBoundedBufferCapsMemory`（4MB 输入 → 占用 ≤ 8KB）、
`TestBoundedBufferWriteContract`、`TestBoundedBufferKeepsHeader`
（灌入 5000 行进度后 `Duration` / `Stream` 仍可解析）。

### 已修复 C1 · 封面缓存整体清空
**文件**：`internal/coverfetch/aggregator.go`

`setCache` 的容量保护改为「先淘汰过期项，再按 `at` 淘汰最旧的 64 条」，
不再 `a.cache = map[string]cacheEntry{}`。

**测试**：`TestSetCacheKeepsOlderEntriesInsteadOfWiping`、`TestEvictPrefersExpiredEntries`。
**反证**：把旧的整体清空放回去 → 测试失败（`早期条目全部消失`）。

### 已修复 C3 / C4 · 提前返回时的孤儿 goroutine
**文件**：`internal/coverfetch/resolve.go`、`internal/lyricsfetch/types.go`

各自加一层可取消的子 ctx，并在「强命中 + grace 到点」/「ctx 取消」时**立刻**
`cancel()`，而不是等函数返回后的 `defer` 链。

**测试**：`TestSearchCancelsSlowProvidersOnEarlyReturn` + 反向的
`TestSearchWaitsForAllProvidersWithoutStrongMatch`。
**反证**：把 `scancel` 换成空函数 → 测试失败
（`慢来源没有观察到取消 —— 提前收工后它仍在跑满 providerTimeout`）。

### 已修复 G5 · 清空缓存是 O(n²) 的索引重写
**文件**：`internal/metacache/store.go`（新增 `ClearAll`）、`services_cover.go`

`ClearAll` 在**一次**持锁里清空内存表 + **只重写一次**索引；上层不再逐个删。
返回「条目数」而非「文件数」，保持与旧的 `DeleteCover` 语义一致
（一首歌多张封面时不会报出比歌曲数更大的数字）。

**实测（200 首封面，索引 JSON 55,825 字节）**：逐个删 **855.9 ms** →
`ClearAll` **208.0 ms**（4.1x），且差距随 n 继续拉大（O(n²) → O(n)）。

**测试**：`TestClearAllDeletesEverythingAndLeavesValidIndex`。

### 已修复 A2 · 运行时令牌每次全量删/插规则
**文件**：`frontend/src/js/runtime-tokens.js`

已有 `:root` 规则时改为**就地更新**（`rule.style.setProperty` / `removeProperty`），
不再 `deleteRule` 全部 + `insertRule`。

**浏览器验证**（CDP + 真实 Edge）：`sameRuleObject: true`、`a2: "9px"`（值确实更新）、
`b3: ""`（删除生效）。
**反证**：禁用就地分支 → `rules2: 2`、`sameRuleObject: false`，而且
**`a2` 停在 `"1px"`、`b3` 停在 `"2px"`** —— 说明旧实现不只是慢，
还**会残留旧规则导致更新不生效**（功能性 bug）。

### 已修复 U1 · 底栏每秒 4 次整模板重绘
**文件**：`frontend/src/js/ui/playerbar.js`

`deps` 移除 `s.position`；`#time-current` 的文本改由 `updated()` 直接写
（模板里不再绑定该节点，避免覆盖 Lit 的标记节点）。

**浏览器验证**：`depsHasPosition: false`；把 `position` 加 61 秒后
`#time-current` 正确变成 `"01:01"`，且**没有**触发模板重绘。

## 六、结论

- **确认并修复**：11 项（G1-G5、F1、C1、C3、C4、A2、U1）。
- **本轮实测收益**：
  - 曲库视图每帧广播开销 **降低 10-17x**（100k 首从 22.45ms → 1.36ms）；
  - 文件夹监听每次落盘的持锁重算 **降低 17x**（10.21ms → 0.58ms）；
  - 清空缓存 **降低 4.1x**（855.9ms → 208.0ms），复杂度从 O(n²) 降到 O(n)；
  - 底栏每秒少 4 次整模板重绘；令牌更新从「删 + 插」变成就地写。
- **附带修掉两个功能性缺陷**（不只是性能）：
  1. 运行时令牌的旧实现会残留规则，导致更新**不生效**；
  2. `songIndex` 重建位置在 `computeVisible` 之后，曲库整体替换时会读到旧索引。
- **质量门**：`gofmt` / `go build` / `go vet` / `go test ./...` / `go test -race` /
  `npm run lint` / `npm run typecheck` / `npm test` 全绿。
- **新增测试 8 个**，其中 4 个经过**反证**（旧实现放回去必然失败），确认不是空转断言。

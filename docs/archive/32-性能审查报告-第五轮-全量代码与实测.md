## 0. 执行摘要

### 0.1 一句话结论

**这个项目的前端/后端「稳态性能」已经做得相当好——好到本轮找不到任何 P0；真正的风险集中在三处：(a) 曲目表零虚拟化（大曲库直接不可用）、(b) 若干条「按曲库规模线性增长」的计算被放在了每帧/每次按键/每次渲染的路径上、(c) magia 皮肤有一个没有上限的帧循环。**

### 0.2 最重要的六条判断

| # | 判断 | 级别 | 证据 |
|---|---|---|---|
| 1 | **曲目表零虚拟化**：每行 **28 个元素节点**，全部可见歌曲一次性建行。5,000 首 = **14 万节点**，10,000 首 = **28 万节点** | **P1** | 【实测】§3.1；【事实】`ui/track-table.js:162-166` |
| 2 | **曲库过滤输入框没有防抖**，每次按键都全量过滤 + 全量排序 + 全表 DOM 重建；`utils.js` 里现成的 `debounce()` **零调用点** | **P1** | 【事实】`ui/content.js:96-99`、`store.js:697-708`；【实测】§3.2 |
| 3 | **`library.Songs()` 每次调用整库拷贝 + 重排序**：10k 首 **2.48 ms / 1.84 MB 分配**，且被 **6 处**调用（`GainMap`+`AlbumGains` 相邻重复） | **P1** | 【实测】§4.1；【事实】`library.go:453-462` |
| 4 | **magia 皮肤的 rAF 循环没有 FPS 上限、不响应 `document.hidden`、暂停后不停**（**60fps 永久运行**）；而 arcanum 有完整的 `45/22 fps + 6s 空闲停止 + 隐藏即停`。**anime 的相机同样不响应暂停** | **P1** | 【事实】§3.3；对照 `arcanum.js:71-73` vs `magia.js:1183`、`fx-camera.js:232` |
| 5 | **`ui/lyrics.js` 把 `s.position` 放进 deps** → 歌词面板每 250ms 整模板重渲染（含对全部草稿行的 `repeat()`），而文件里已有专门为此写的增量绘制函数 | **P1** | 【事实】`ui/lyrics.js:65-73` vs `:432-452`；§3.4 |
| 6 | **`loudness.keyFor()` 用 `fmt.Sprintf` 做每次缓存查找的 map key**：10k 首一次遍历 **39,617 次分配 / 2.23 ms** | **P2** | 【实测】§4.2；【事实】`loudness.go:184-186` |

### 0.3 评分

| 维度 | 评分 | 理由 |
|---|---|---|
| **稳态（播放中、不做别的）** | **A−** | 启动路径无同步重活；进度 250ms 量化；`playerbar` 完全绕开 Lit diff；频谱 30Hz 且复用 `Float32Array`；FFT 原地执行、Hann 窗预计算；封面内容寻址。**这些是教科书级的**。 |
| **大曲库可扩展性** | **D** | 曲目表零虚拟化是硬伤；`settings-view` / `Songs()` / `keyFor` / `folder` 计数等多处是「按曲库规模线性」且挂在渲染/每帧路径上。**59 首完全看不出来，1 万首会同时爆**。 |
| **皮肤层资源纪律** | **C+** | arcanum 是模板（有界、自适应、可见性感知）；magia 完全相反（无上限、无暂停停止）；桌面壁纸窗口会挂**第二份**皮肤循环。 |
| **IPC / 内存** | **B+** | `scan:done` 的「拉两遍整库」**已修复**（本轮确认）；`Song.Cover` 无 `omitempty` 仍在；前端 4 个缓存无上限。 |
| **回归防护** | **C** | 前端 59k 行 JS 的核心状态/DOM 生命周期 **0 覆盖**；`frontend/tests/` 只覆盖纯函数（89 用例）。**本轮所有 P1 都没有任何测试能拦住回退**。 |

> **综合：B**。工程质量明显高于同类个人项目，且**历史性能修复大多是真实且带数字的**；短板是「当曲库从 59 首变成 1 万首时，多处线性成本会同时显形」，以及表现层缺少虚拟化。

## 3. 表现层（前端 UI）—— 本轮的 P1 集中地

### 3.1 【P1】曲目表零虚拟化：每行 28 个元素节点，全量建行

**【事实】** `frontend/src/js/ui/track-table.js:162-166` 是**唯一**的行生产者：

```js
${repeat(
  songs,                       // ← state.visibleSongs，全部
  (song) => song.id,
  (song, index) => this.rowTemplate(song, index, mode)
)}
```

`songs` 来自 `state.visibleSongs`（`:147`），即 `store.js:774` 赋的**完整过滤+排序结果**，未做任何窗口化。

**【实测】每行元素节点数 = 28**（脚本解析模板：`rowTemplate` 自身 12 元素 + `indexCell` 8 元素 + 4 次 `icon()` × 每个 icon 2 元素 = 8）：

| 1,000 首 | 28,000 节点 | 1,680 | −94.0% |
| 5,000 首 | **140,000 节点** | 1,680 | **−98.8%** |
| 10,000 首 | **280,000 节点** | 1,680 | **−99.4%** |
| 20,000 首 | **560,000 节点** | 1,680 | −99.7% |

**【实测】首帧外推**（以 `docs/12:60-68` 实测的 5,000 首 = 2,882 ms 为基准线性外推）：

| 规模 | 首帧估计 | 超出 16.7ms 帧预算 |
|---|---|---|

| 10,000 首 | 5,764 ms | 345 倍 |
| 20,000 首 | 11,528 ms | **690 倍** |

| 字段 | 内容 |
|---|---|
| **指标** | 曲目表首帧成表耗时 / DOM 元素节点总数 |
| **当前值** | 【实测】每行 28 节点；5,000 首 = **140,000 节点**；【实测·仓库文档】首帧 **2,882 ms** |

| **验证** | 同一脚本改前后比对「首次绘制」与 `document.querySelectorAll('*').length` |

`commit()` 的后果链（`store.js:360-385` → `:746-789`）：

1. `recalcVisible()` → `visibleInputs()`（`:649`）因 `state.query` 变化而**签名失配** → `computeVisible()`（`:695-708`）做**全库线性扫描**，每首歌 **4 次 `toLowerCase()` 分配**（title/artist/album/ext）；
2. `computeSorted()`（`:729-744`）`list.slice().sort()`，比较器是 `Intl.Collator`（`store.js:519-526` 自测「5,000 首 13.2 ms」）；
3. `visibleFingerprint()`（`:807-822`）再走一遍全表；
4. `visibleVersion++` → `<mp-track-table>` 的 deps（`:77`）变化 → `repeat()` **重建全部匹配行**（§3.1）。

**【实测】过滤/排序纯函数成本**（本机 Node 22，20 次取均值）：

| 规模 | 查询过滤 | `slice+sort` | `applyRules`(5 规则) |
|---|---|---|---|
| 1,000 首 | 0.30 ms | ~0 | 0.69 ms |
| 5,000 首 | 1.30 ms | ~0 | 2.96 ms |
| 10,000 首 | 2.59 ms | ~0 | 5.52 ms |
| 20,000 首 | 5.40 ms | ~0 | 10.87 ms |

**【实测】结论（重要且反直觉）**：**纯计算部分并不贵**（10k 首过滤仅 2.59 ms）。真正的成本在**第 4 步的 DOM 重建** —— `repeat()` 对 10k 行做 keyed diff（28 万节点），那才是每次按键的数百毫秒来源。**所以「加索引/预计算小写 haystack」收益有限，真正的修法是「防抖 + 虚拟化」。**

| **当前值** | 【实测】纯计算 10k 首 ≈ 2.6 ms；**DOM 重建未实测**，但按 §3.1 的节点数模型为数十~数百 ms |

## 9. 方法论说明与自我约束

1. **本报告全程只读**，未修改任何业务源码。临时基准脚本（`.task/perf-audit/`、`tools/perfauthbench/`）已**删除**，`git status` 仅剩一份子代理审计报告。
2. **每条结论都标注了证据等级**；【推断】与【待测量】不冒充实测。
3. **主动下调了四条被历史报告高估的项**：
   - **`evictIfNeeded` 的 O(n²)**：按 600MB/42MB ≈ 15 条计算，只有 225 次比较 ⇒ 从「性能问题」降为「hygiene」；
   - **`metacache.Stats()` 全目录 Walk**：前端有 `coverProvidersRequested` 闸门、全文无轮询 ⇒ 频率远低于历史报告的暗示；
   - **`engine.go` 的 `monoScratch`「音频回调内分配」**：`PeriodFrames` 恒定 ⇒ 只在首次回调分配一次，**不是问题**，并已注明「不要改」；
   - **arcade 的「930 次 setProperty/秒」**（`docs/23`/`26` F-11/`28`）：**该皮肤不存在，结论作废**（§3.3.4）。
4. **主动澄清三个易误判项**：`store.songIndex` **不是**泄漏（有引用守卫重建）；过滤的**纯计算**部分并不贵（10k 首 2.59 ms），真正的成本在 DOM 重建 —— 这条直接改变了 #2/#1 的优先级判断；**皮肤收到的是 4 Hz 的 progress 而非每帧**（§3.13），因此「降低推送频率」已无收益。
5. **本报告最重要的新增发现**（历史 5 份报告均未记录）：
   - **magia 的 rAF 永久满帧**（暂停/隐藏/空闲一律不停）与 **anime 相机不响应暂停**（§3.3）；
   - 二者与**桌面壁纸窗口挂第二份皮肤**叠加 ⇒ 「壁纸 + magia」= **两个永久满帧循环**（§3.3.1、§3.14）；
   - **每行歌词常驻 `filter: blur()`**（§3.3.3）。
6. **主动标注了 `docs/24` 的 43fps 数字来源存疑**：该数字测于 `follow()` 修复**之前**，本轮**无法确认修复后是否仍为 43fps**（需跑 `perf-skins.mjs`）。因此 §3.3.3 的「blur 是残余掉帧主因」是**推断**，已明确标注「先测量再改」。

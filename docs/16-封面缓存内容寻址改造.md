# 16 · 封面缓存内容寻址改造

> 落实 `docs/12-性能审查报告-第二轮.md` 的 **P0-1**。
> 对应需求：「对封面做快速 hash 并命名，放在专用的封面缓存文件夹内；
> 元数据缓存里不应该直接存储 base64 的封面数据」。

---

## 1. 改造前的问题（实测数字，不是估算）

真实的 `%APPDATA%\\LocalMusicPlayer\\metadata-cache.json`：**5,867,147 字节**。

- 59 条记录，其中 **40 首有内嵌封面**；
- base64 封面字符合计 **5,845,340**（5.57 MB），**占整个文件的 99.6%**；
- 平均 **142.7 KB/首**。

于是三件事同时发生：

1. **每次扫描结束都要把 5.57MB 的 base64 重新序列化一遍并整份写盘**；
2. **同一张图被逐首重复存**（整张专辑共用一张封面是常态），完全没有去重；
3. 更严重的是 **IPC**：`LibraryService.Songs()` 把 `Song.Cover`（data URL）
   整库下发，而每次 `scan:done`（含文件夹监听触发的增量重扫）都要重拉一遍 ——
   按 5,000 首推算约 **484 MB/次**。

## 2. 改造后的结构

```text
%APPDATA%\LocalMusicPlayer\
├── metadata-cache.json      ← 只剩元数据 + 封面**文件名**（实测 18 KB）
└── cache\
    └── covers\              ← 专用封面缓存目录（内容寻址，一张一个文件）
        ├── 9f2a1c4b7d3e5081.jpg
        └── 3be07d5a1c9f4e26.png
```

元数据条目里存的是：

```json
{ "title": "…", "artist": "…", "coverFile": "9f2a1c4b7d3e5081.jpg", "size": …, "modTime": … }
```

（v1 的 `cover` 字段保留在结构体里，**只用于一次性迁移**，新写入的缓存永远是空的。）

### 命名规则

```text
<fnv1a64(字节 ‖ 长度) 的 16 位小写十六进制><扩展名>
```

- **快速 hash**：用非加密的 FNV-1a 64（每字节一次异或 + 一次乘法），而不是 sha256 ——
  这是纯内容寻址的**缓存名**，不是安全边界，要求的是「算得快」。143KB 的封面是微秒级。
- **长度混进摘要**：保证「长度不同必然不同名」，同长度不同内容碰撞概率约 2^-64
  （个人曲库量级可以忽略）。写入时还会比对已有文件的大小，碰撞也不会串图。
- **扩展名由内容嗅探得到**（`http.DetectContentType` 只看前 512 字节），
  **不是**采信标签里声明的 MIME。

  这一点是测试逼出来的：迁移时同一张 PNG 在不同条目里分别被声明成 `image/png`
  和 `image/jpeg`，若把声明值拼进名字，**同一张图会落成两个文件**，内容寻址就白做了。
  嗅探还顺带修掉「声明的 MIME 是错的 → 名字决定 Content-Type → 浏览器拒绝渲染」。

### 出参：同源 URL 而不是 base64

服务端把封面挂到已有的同源 asset server 上（与 `/audio/` 同一套做法）：

```text
GET /cover/<hash>.jpg?t=<本机随机 token>
Cache-Control: public, max-age=31536000, immutable
```

`Song` 新增 `CoverURL` 字段。前端的 `coverOfRaw` 本来就优先认 `coverUrl`，
所以这一侧几乎不用改。

**为什么必须一起改**：如果只把缓存改成 hash 命名、却仍在构建列表时把文件读出来重新
base64 编码，就是**用「每次列表请求都读盘 + 编码」换「缓存文件变小」** —— 列表路径
反而更差。hash 命名的文件本来就该按名字取用，URL 是这个设计的自然收口。

## 3. 迁移

v1 缓存里的 base64 必须**就地迁移**，不能「直接丢掉、等下次重扫」：

> 缓存命中路径只要 `ModTime`/`Size` 没变就认为记录有效，**不会再打开文件解析封面** ——
> 于是老用户会在文件毫无变化的情况下**永久失去封面**。

`migrateLegacyCovers()` 在元数据缓存首次加载时（`ensureCacheLoaded` → `loadCache`）
把每条 legacy `cover` 解码 → 写进封面缓存目录 → 记下文件名 → 清空 legacy 字段；
下一次 `SaveCache` 落盘就是瘦身后的形态。解码失败的坏数据直接清字段，不让它继续占体积。

实测迁移耗时 **197 ms**（59 条 / 40 张图，一次性）。

## 4. 回收（内容寻址目录的必备配套）

内容寻址的目录天然**只增不减**：用户在歌曲文件里换了内嵌封面、或删掉了歌，
旧图就成了没人引用的孤儿。

`SaveCache` 末尾调用 `pruneCoverCache()`：按「元数据缓存里还引用着哪些文件名」
回收孤儿。**1 小时的年龄门槛**是给「刚写完、还没登记进元数据缓存」的文件留的窗口 ——
那种文件此刻必然不在 keep 集合里，不该被当成孤儿删掉（这条有专门的测试）。

## 5. 实测效果

拿**真实的** 5.87MB 缓存跑一遍迁移（`go run ./tools/covermigrate <真实缓存>`）：

| 项目                             | 改造前                          | 改造后                      | 变化                    |
| -------------------------------- | ------------------------------- | --------------------------- | ----------------------- |
| `metadata-cache.json`            | 5,867,147 B                     | **17,986 B**                | **−99.69%（剩 0.31%）** |
| 封面数据                         | 内嵌在 JSON 里（5.57MB base64） | 40 个文件 / **4,383,270 B** | 去掉 base64 的 1/3 膨胀 |
| 列表接口封面载荷（5,000 首推算） | ~484 MB                         | ~250 KB（只有地址）         | **−99.95%**             |
| 迁移耗时                         | —                               | 197 ms                      | 一次性                  |

封面总字节从 base64 的 5.57MB 降到原始字节的 4.28MB —— base64 本身的 1/3 膨胀也一并省掉了。
浏览器侧因为 `immutable` 缓存头，**同一张封面只会下载一次**。

## 7. 明确**没做**的

1. **`CoverService.CacheStats` / `OpenCacheDir` 没纳入新目录**。
   那两个走的是 `internal/metacache`（「用户管理过的封面」：联网抓取、手动换、写回文件），
   与这里是两套生命周期。`<cacheDir>/covers` 目前**没有**暴露在设置界面的缓存统计里，
   「打开封面缓存目录」按钮打开的也仍然是 metacache 那个目录。要合并展示需要给
   `CoverService` 注入 `library.Manager`，属独立改动。
2. **`ClearCache` 不清这个目录**。它是「从文件标签派生」的数据，下一次扫描会自动重建，
   清掉反而会让封面在整个重扫完成前消失。孤儿由 §4 的 `Prune` 负责。
3. **`Song.Cover` 字段保留**。在线曲目等场景仍需要内嵌 data URL；
   本地歌曲现在一律走 `CoverURL`。前端 `coverOfRaw` 的兜底顺序不变。
4. **metacache 的 `covers/<songID>-<hash8><ext>` 命名没动**。
   它用 8 位十六进制（32 位）前缀做文件名 —— 比本包的 64 位弱，
   而且 32 位前缀在万级封面下有约 1% 的碰撞概率。它另有 `index.json` 存完整 hash 兜底，
   所以不影响正确性，但**值得后续统一**。

## 附：一处需要你确认的设计决定

改造前我问过「`Song.Cover` 要不要顺势改成同源 URL」，但没等到回复（问题超时）。
我按 **URL** 做了，理由是：hash 命名的缓存文件本来就该按名字取用；只改缓存会让列表
路径多出「每次读盘 + base64 编码」的开销，反而更差。

如果你更希望**只改缓存、`Cover` 仍是 data URL**（不碰对外契约），回退很小：
把 `library` 里两处 `song.CoverURL = m.covers.URL(...)` 换成
「读文件 → 拼 data URL」，并去掉 `main.go` 的 `/cover/` 分支即可，
封面缓存与元数据瘦身的部分完全不受影响。

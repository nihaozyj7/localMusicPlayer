# 播放失败：提示一次 + 自动跳下一首

> 用户反馈原文：
> 「播放歌曲会出现无法播放转码失败的情况，这种情况应该出现提示并自动切换到下一首歌曲，
> 而不是疯狂弹错误提示。」

---

## 一、根因：一次失败不是一个事件，而是一连串

后端装载失败后**不会进入「已装载」状态**，而前端的播放意图没变
（`state.playing` 仍是 `true`、`state.currentId` 仍是那首坏歌）。
两者叠加就把「一次失败」放大成了持续不断的失败流：

```
后端 playerLoad 失败 ──┬──> Emit player:error ──> toast（第 1 条）
                       │
                       └──> Promise reject ──> loadSong 的 catch ──> toast（第 2 条）

同时：state.playing=true / currentId=坏歌 / position 在走
      └─> runtime 依赖键（currentId|playing|position/250|…）每 250ms 变一次
          └─> 每 tick 重跑 syncAudio() ──> 重新 playerLoad ──> 再失败 ──> 又一条 toast
```

于是表现成：

- **提示刷屏** —— 每 250ms 一条「无法播放」；
- **永远不跳下一首** —— 没有任何一处代码在失败后推进 `currentId`。

legacy `<audio>` 链路（后端声卡不可用时的回退路径）是同一个毛病：
`error` 监听弹一条 toast 就结束，`switchPhase` 置 IDLE 后下一次
`syncLegacy()` 又重新设 `src` → 再 `error` → 又一条 toast。

### 实测佐证

用户曲库 8725 首里有一首真正的坏文件
（`Music\clm\当你孤单你会想起谁-clm.m4a`，AAC 流损坏）：

```
[aist#0:0/aac] Decode error rate 1 exceeds maximum 0.666667
Task finished with error: Error number -1145393733 occurred
```

用它在真实应用里复现，确认了刷屏现象与「不跳下一首」。

---

## 二、修法

### 核心：`audio.js#handlePlaybackFailure()`

把「失败之后该做什么」收敛到**一个**函数，三处入口全部改走它：

| 入口 | 位置 | 原本行为 |
| --- | --- | --- |
| `player:error` 订阅 | `audio.js` 事件订阅段 | 只 toast |
| `loadSong()` 的 `catch` | 装载函数 | 只 toast |
| legacy `<audio>` 的 `error` | 回退链路 | 只 toast |

函数做四件事：

1. **`failedSongId` 当闸门** —— 同一首歌的失败只处理一次。重复报告
   （事件 + catch 双报、tick 反复重试）一律吞掉并记一行 console.warn。
2. **只弹一条提示**，文案包含歌名与原因，并说明**接下来会做什么**
   （会跳才写「已跳到下一首」，不跳就不写 —— 文案不能与实际行为不符）。
3. **自动跳下一首**：复用 `playNext(true)`，随机 / 列表循环 / 播完即停
   这些语义都由它统一处理，不在这里重写。
4. **连败熔断**：连续失败到 5 首就停下并给一条汇总提示，
   避免「坏文件成批」时一路刷到列表末尾。

不跳的三种情况（就地停下，与各自语义一致）：

- 暂停状态下用户点的坏歌 —— 不该「自动播放」后面的歌；
- 单曲循环 —— 坏文件重播多少次都一样；
- 播完即停（`sleepTimer.type === "after-song"`）—— 本就该停。

### 闸门必须能被用户的主动点播打开

`failedSongId` 若是单向的，用户修好文件（或换了张能读的盘）后再点这首歌
会**完全没反应** —— `syncAudio()` 被闸门拦住直接 return，连提示都没有。
这比弹提示更糟。

于是 `store.js#playSong` 在**非自动**调用时经注入的钩子通知 audio.js
解除闸门（`resetFailureGate`）。为什么用注入而不是直接 import：`store` 是
底层模块，`audio.js` 依赖它，反向 import 会形成循环依赖 —— 与既有的
`setRealAudioProbe` 同一套做法。

`playNext` 走的也是 `playSong`，所以用 `options.auto` 区分：
自动跳转**不**解除闸门（那正是要避免的反复重试）。

### 后端：同一首歌的同一失败只广播一次

前端已有闸门，后端再兜一层（`services_player.go#fail`）：
记录 `lastFailSong` / `lastFailMsg`，命中就只 `log.Printf` 不再 `Emit`。
装载成功时清掉抑制键，所以「修好后再试」仍能正常收到通知。

理由：事件风暴不该从后端发起。排查日志时「同一条错误刷了几十遍」
会淹没真正有用的行。

## 四、顺带说明：为什么不做「自动重试」

对「转码失败」这类失败**重试是没有意义的** —— 输入文件本身解不出来，
再跑一次 ffmpeg 只会再失败一次、再花几秒到几分钟。所以这里的选择是
「报一次、跳过去、继续放」，而不是重试。真正的偶发失败（IO 抖动）
用户重新点一下就能过 —— 闸门为此留了开口。

## P1（严重：数据损坏、缓存被整体清空、磁盘无上限增长）

### B1 metadata-cache 加载失败后，SaveCache 会用空表覆盖索引并删光整个封面目录

- **位置**：`internal/library/library.go:236-247`（loadCache）、`341-367`（SaveCache）、`376-390`（pruneCoverCache）、`internal/covercache/covercache.go:242`（Prune）
- **现象**：用户升级后（缓存格式版本变化）、或 metadata-cache.json 被写坏/被杀软截断时，**内嵌封面会全部消失**；最坏情况下（关掉「启动时自动扫描」或没有配置音乐文件夹）**不会自愈**，因为封面文件已被物理删除、索引也被清空。
- **根因**：`loadCache` 有 4 条**静默 return**（读文件失败 / JSON 解析失败 / `cf.Version != cacheVersion` / `cf.Entries == nil`），却没有留下「这次加载是失败的」这个信息：

  ```go
  // library.go:236-247
  func (m *Manager) loadCache() {
      raw, err := os.ReadFile(m.cachePath())
      if err != nil { return }              // ← 失败静默
      var cf cacheFile
      if err := json.Unmarshal(raw, &cf); err != nil { return }   // ← 失败静默
      if cf.Version != cacheVersion || cf.Entries == nil { return } // ← 失败静默
      ...
  }
  ```

  而 `SaveCache` 无条件走到 `pruneCoverCache`，后者把「m.cache 里出现过的 CoverFile」当唯一的 keep 集合：

  ```go
  // library.go:376-386
  keep := make(map[string]struct{}, len(m.cache))   // m.cache 是空 map
  for _, entry := range m.cache { ... }
  removed, freed := m.covers.Prune(keep, time.Hour) // keep 为空 ⇒ 删除所有 >1h 的文件
  ```

  `SaveCache` 的调用点：扫描结束（`library.go:565`）、应用退出（`main.go:399`）、重启前（`services.go:1798`）。也就是说**只要用户开着应用退出一次**，这条链就会走完。
- **证据**：`covercache.Prune` 的语义就是「不在 keep 里的都删」（`covercache.go:242-261`），而它唯一的调用方传入的 keep 完全依赖内存索引是否加载成功；`migrateLegacyCovers`（`library.go:256-311`）同样在这种状态下什么都不做。
- **建议修法**：给 `Manager` 加 `cacheLoadFailed bool`（或让 `loadCache` 返回 error，`ensureCacheLoaded` 记录结果）；`pruneCoverCache` 在加载失败时**直接 return**（宁可不回收，也不能删）。真正需要「谁都没引用」的判定时，改为「扫描成功提交后才允许 prune」（例如只在 `Scan` 成功路径传一个 `allowPrune=true`），并在 `SaveCache` 里对「空 entries + 非空 covers 目录」这一组合拒绝覆盖落盘、改为写 `.bak` 并记日志。

### B2 程序自动管理的下载目录被写进 `config.Folders`，改下载路径后旧目录永远是扫描根

- **位置**：`internal/library/library.go:561-565`（`foldersCopy` → `store.Update(c.Folders = foldersCopy)`）、`429-434`（ReloadFolders）、`internal/bootstrap/config.go:479-510`（EffectiveFolders，`503-508` 追加合成条目）
- **现象**：用户的「下载目录」一旦被改到别处（设置 → 下载 → 更改位置），**旧下载目录仍然被扫描并统计**，新目录与旧目录同时出现在文件夹列表里，而且两者 `id` 都是 `auto_downloads`（前端列表按 id 做 key/去重时会打架）。
- **根因**：`m.folders` 的来源是 `EffectiveFolders()`，它把「用户文件夹 + 合成下载根」一起返回：

  ```go
  // config.go:503-508
  out = append(out, Folder{ID: DownloadFolderID, Path: c.DownloadDir, Status: "ok", Watching: false})
  ```

  而 `Scan` 结束时把 `m.folders`（含上面这条合成条目）整体写回配置：

  ```go
  // library.go:561-564
  foldersCopy := append([]bootstrap.Folder(nil), m.folders...)
  m.mu.Unlock()
  _ = m.store.Update(func(c *bootstrap.Config) { c.Folders = foldersCopy })
  ```

  之后 `EffectiveFolders` 不再区分「用户配置的」与「上次被程序写进来的」，于是旧下载目录变成普通用户文件夹；再改一次下载路径就产生**两条同 id、不同 path** 的条目（`config.go:484-499` 会把它们都 append 进 out）。
- **证据**：`DownloadFolderID` 的设计注释明确说「它不出现在 config.Folders 里」（`config.go:465-469`），但代码路径与注释相反；现有测试全部用 `userFolders()` 过滤掉这个 id（`internal/library/library_test.go:163-174`、`services_test.go:152-157`），所以**没有任何断言能发现它被持久化**。`Scan` 的 `statuses` 是 `map[folder.ID]string`（`library.go:492-499`），同 id 两条时后写入覆盖前一条，两条文件夹会显示同一个状态。
- **建议修法**：写回配置前剔除合成条目，例如 `foldersCopy := userOnly(m.folders)`（过滤 `ID == bootstrap.DownloadFolderID`），或让 `ReloadFolders` 只在 `m.folders` 里保留 `store.Get().Folders` 的副本、把下载根单独存成 `m.downloadRoot` 并在遍历阶段拼接。另外在 `EffectiveFolders` 里对 `f.ID == DownloadFolderID` 的条目做一次「路径等于当前 DownloadDir 才保留」的自愈，兜住已经写坏的老配置。

### B3 转码缓存只有内存账本，重启后 600MB 预算失效，磁盘可无上限增长

- **位置**：`internal/media/server.go:78`（`cache: map[string]*cacheItem{}`）、`350-425`（ensureTranscoded）、`440-477`（evictIfNeeded，预算常量 `37`）
- **现象**：一首 4 分钟曲子转成 WAV 约 42MB；`%APPDATA%\LocalMusicPlayer\cache\transcode` 会随使用无限增长，用户只能手动点「清空转码缓存」。
- **根因**：缓存是**纯内存 map**，构造时为空（`server.go:78`）；`evictIfNeeded` 只统计 `s.cache` 里条目的 `size`：

  ```go
  // server.go:441-449
  s.cacheMu.Lock()
  var total int64
  for _, it := range s.cache { total += it.size }
  if total <= transcodeBudgetBytes { s.cacheMu.Unlock(); return }
  ```

  上一轮进程留下的 `tc_*.wav` 在本次启动时既不计入 total、也不会被淘汰（只有再次请求同一首歌时才会重新入表）。于是「600MB 预算」只是**单次运行内**的预算。
- **证据**：`bootstrap.StableID(key,"tc")+".wav"` 命名（`server.go:361`）意味着同一个文件在新旧进程里同名，完全可被识别和统计，但代码里没有任何启动扫描（`grep -rn "ReadDir" internal/media` 只命中 `ClearCache` 与 `CacheStats` 无关处）。
- **建议修法**：在 `SetCacheDir`（或首次 `ensureTranscoded`）里做一次目录清点：把 `tc_*.wav` 按 modtime 从旧到新入表（size 用 `os.Stat`），然后调用 `evictIfNeeded()` 把总量压回预算；对超过 N 天未访问的文件直接删除。这是「预算语义」能成立的最小改动。

### B4 同名文件并发下载会写同一个临时文件，导致成品损坏却被标记为「已完成」

- **位置**：`services_download.go:421`（`uniquePath` 调用）、`491-534`（fetchTo）、`773-785`（uniquePath）
- **现象**：同时对两首**标题相同**的在线曲目点下载（同一首歌的两个投稿、或两个不同视频用了同一标题），两个任务会算出同一个目标路径，两个 `os.Create(target+".part")` 互相截断、并发写入交错字节，最后各自 `os.Rename` 到同一个目标；结果是文件内容损坏，而任务面板显示 `done`。
- **根因**：去重闸门只按 bvid：

  ```go
  // services_download.go:262-268
  s.mu.Lock()
  if s.running[bvid] { ... }
  s.running[bvid] = true
  ```

  而目标路径的分配是「先查存在性、再创建」的两步（TOCTOU）：

  ```go
  // services_download.go:773-777
  candidate := filepath.Join(dir, base+ext)
  if !fileExists(candidate) { return candidate, nil }   // 两个 goroutine 同时为 true
  ```

  临时文件名固定为 `target + ".part"`（`fetchTo:492`），两个 worker 共用。
- **证据**：`fetchTo` 全程没有对「目标路径的独占所有权」做任何声明（没有 `O_EXCL`、没有跨任务的路径占用表）。
- **建议修法**：把「路径分配」并入一个受 `s.mu` 保护的分配器：在 `Start`（或 `run` 开头，拿到真实 title 后）一次性 `reservePath(dir,name,ext)` 并把结果记入 `s.running`（键改为目标路径或 `dir+"|"+base`），随后 `os.OpenFile(tmp, O_CREATE|O_EXCL)`，`EEXIST` 时改用新后缀。

## P2（一般：功能静默失效、竞态、可感知卡顿）

### B5 `ffmpeg.Reset()` 不复位解包 once：一次失败后「重新检测」永远无效

- **位置**：`internal/ffmpeg/ffmpeg.go:98-103`（Reset）、`142-146`（`extraction` 结构体）、`155`（`extraction.once.Do`）
- **现象**：内置 ffmpeg 首次解包失败（磁盘暂满、杀软拦截、写入中断）后，用户点设置里的「重新检测」、或后台 prewarm 之后的 `RefreshFFmpeg/RefreshTools`，都仍然得到「未找到 ffmpeg」，转码与响度均衡整个会话不可用（重启才行）。
- **根因**：`Reset()` 只清 `ffTools/ffReady`，而 `extractBundled` 用 `sync.Once` 缓存了**失败**（`extraction.err`），once 永不复位：

  ```go
  // ffmpeg.go:155-197
  extraction.once.Do(func() {
      ...
      if err := os.MkdirAll(dir, 0o755); err != nil { extraction.err = ...; return }
      ...
      if err := atomicfile.Write(target, data, 0o755); err != nil { ... }
  })
  return extraction.path, extraction.err   // err 被永久缓存
  ```
- **证据**：`RefreshTools`（`internal/loudness/loudness.go:157-163`）与 `media.Server.RefreshFFmpeg`（`internal/media/server.go:96-102`）都是「`ffmpeg.Reset()` + `ffmpeg.Resolve()`」，语义上就是「重新检测」，但后者不会重试解包。
- **建议修法**：`Reset()` 里加 `extraction = struct{...}{}`（需为结构体加锁，或改用 `sync.Mutex + extracted/extractErr` 手写一次性）；更简单：把 `extraction.err != nil` 视为「未缓存」，在 `extractBundled` 开头判断 err 非空就重跑一次。

### B6 `loudness.Save()` 先清 `dirty` 再写盘：一次写失败就静默丢掉本轮全部测量结果

- **位置**：`internal/loudness/loudness.go:213-240`
- **现象**：落盘失败（磁盘满、文件被占用）时用户看不到任何提示，且这批测量结果在进程内被标记为「已保存」，之后不再尝试写盘 —— 重启后全部需要重测（每首一次 ffmpeg 全解码）。
- **根因**：

  ```go
  // loudness.go:224-239
  m.dirty = false          // ← 先清标记
  m.mu.Unlock()
  raw, err := json.Marshal(...)
  if err != nil { return err }
  return atomicfile.Write(m.cachePath(), raw, 0o644)   // ← 失败时 dirty 已经是 false
  ```
- **证据**：调用点普遍忽略返回值：`services.go:1102`、`1119`、`1152`、`1225` 全是 `_ = s.mgr.Save()`；只有 `MeasureAll` 把错误往上传（`loudness.go:532`）。
- **建议修法**：改成「先写盘成功再清 dirty」：写盘期间持有 `mu` 会阻塞测量提交，所以更稳的写法是 `m.dirty=false` 前先记录一份待写版本，写失败时把 `m.dirty` 重新置为 `true`（可在 `m.mu` 内做），并至少 `log.Printf` 一次；同时把 `services.go` 里的 `_ =` 换成记录日志。

### B7 封面聚合器的 6 小时缓存与「没查到」负缓存从未生效；设置里的「清空封面缓存」是空操作

- **位置**：`internal/coverfetch/aggregator.go:33-38`（TTL）、`125-183`（`Find`：唯一读写缓存的入口）、`186-220`（`FindAll`：**不碰缓存**）、`251-259`（setCache）、`services_online.go:255-260`（InvalidateCovers）
- **现象**：每次打开封面面板/在线曲目封面代理都会**重新并发打 5 个来源**（iTunes/网易云/QQ/Deezer/MusicBrainz），最慢可到 `DefaultWorstCase`（23s）；同一首歌反复浏览也如此；而设置界面里的「清空封面缓存 / 重新抓取」点了没有任何变化。
- **根因**：生产代码只调用 `Resolve`/`ResolveAll` 这条链，而它内部走的是 `FindAll`：

  ```go
  // resolve.go:61-68
  func (a *Aggregator) ResolveAll(...) {
      candidates, err := a.FindAll(ctx, req)   // FindAll 无 cache 读写
  ```

  `getCache/setCache` 只被 `Find` 调用，而 `Find` 在整个仓库里只有测试引用：
  `grep -rn "\.Find(" --include=*.go` → `internal/coverfetch/aggregator.go:125`、`internal/coverfetch/probe_test.go:46`（生产调用点 0 个）。
- **证据**：`services_cover.go:179`（`s.covers.ResolveAll`）、`services_online.go:219` 与 `307`（`s.covers.Resolve`）是全部生产入口；`InvalidateCovers` 清的正是那张永远为空的表（`aggregator.go:262-266`）。
- **建议修法**：在 `FindAll` 里接上同一套缓存（命中即返回单元素结果；未命中才并发查询并 `setCache`），把 `ResolveAll` 的命中路径短路；同时把 `Invalidate` 的语义写进返回给前端的文案（否则界面在撒谎）。

### B8 `metacache.AddCover` 在持锁状态下做 fsync 落盘，所有封面/歌词读接口被一起堵住

- **位置**：`internal/metacache/store.go:336-376`（`s.mu.Lock()` 在 336，落盘在 364）
- **现象**：用户连续添加多张封面（`AddMany` 逐张调用）、或在线抓取落盘时，同进程内其它封面/歌词读取（`Covers / CoverPathAt / Lyrics / Stats / CoverIDs`，全部用同一把 `s.mu`）会被串行阻塞；单张上限 6MB + `atomicfile.Write` 内含 `f.Sync()`，每次都是「写盘 + fsync + rename（Windows 上还可能退避重试最高约 180ms）」。
- **根因**：`AddCover` 把「写文件」放在索引锁的临界区内（注释只讨论了 `CoverDataURLs` 的持锁读盘问题，写入这条路径没有同步收紧）。
- **证据**：

  ```go
  // store.go:336-366
  s.mu.Lock()
  defer s.mu.Unlock()
  ...
  if err := atomicfile.Write(full, data, 0o644); err != nil { ... }   // ← 持锁 fsync
  ```

  `atomicfile.Write` 的重试退避序列见 `internal/atomicfile/atomicfile.go:27-30`（5/10/15…40ms，累计约 180ms）。
- **建议修法**：把 `atomicfile.Write(full, ...)` 挪到取锁之前（内容寻址文件名由 hash 决定，天然可以先写文件再登记索引）；只把「去重判断 + 追加 items + saveIndexLocked」留在锁内。注意 `saveIndexLocked` 本身也带一次 `atomicfile.Write`，必要时把索引写盘也挪出锁（先复制快照，再由调用方串行化）。

### B9 `metacache/embed.go` 的 `writeFileAtomic` 没有 rename 重试，与全仓统一的 `atomicfile.Write` 语义不一致

- **位置**：`internal/metacache/embed.go:654-681`
- **现象**：把封面/歌词写回**用户音乐文件**时（`EmbedCovers`/`EmbedLyrics`/`WriteCacheToFiles`），Windows 上目标文件被 OneDrive/杀软/正在播放的句柄短暂占用时，`os.Rename` 直接失败；而其它所有落盘点（配置、元数据缓存、响度缓存、封面缓存、内置 ffmpeg、索引）都有 8 次退避重试。用户看到「歌词已缓存，但写入文件失败：替换原文件失败: ...」，重试一次往往就好了。
- **根因**：`atomicfile` 的包注释明确写了「仓库里原本有 7 处各自手写这套逻辑…统一到这里之后，唯一临时名和 fsync 对所有调用方都生效」（`atomicfile.go:1-15`），但 `embed.go` 保留了私有实现且**没有**那段退避：

  ```go
  // embed.go:677-679
  if err := os.Rename(tmpName, path); err != nil {
      return fmt.Errorf("替换原文件失败: %w", err)   // 只试一次
  }
  ```
- **证据**：`atomicfile.Write` 的重试循环 `atomicfile.go:76-83`；`grep -rn "os.Rename" --include=*.go` 剩下的裸调用还有 `services_download.go:530`（下载成品）、`ffmpeg.go:531`（WAV 成品）。
- **建议修法**：`writeFileAtomic` 直接改成 `atomicfile.Write(path, data, modeFromOriginal)`（需要保留原权限时先 `os.Stat` 取 mode 再传参，`atomicfile.Write` 已经负责建目录/fsync/退避）。

### B10 桌面歌词窗口位置保存：`posSaveSeq` 无锁读 + 无锁自增（真实数据竞争）

- **位置**：`desktop_lyrics.go:169-188`（写：`185-188`；读：`176`）
- **现象**：拖动桌面歌词窗口时，窗口移动事件（Wails 事件 goroutine）与去抖定时器回调（runtime timer goroutine）会并发访问 `posSaveSeq`。后果是去抖判定可能失效（旧的一次写入胜出）或丢一次位置保存；这是未同步的读写，属于数据竞争。`go test -race` 覆盖不到（没有测试驱动窗口移动事件）。
- **根因**：

  ```go
  // desktop_lyrics.go:170-182
  id := s.nextPosSaveSeq()          // 内部 s.posSaveSeq++（无锁）
  s.desktopMu.Lock()
  ...
  s.posSaveTimer = time.AfterFunc(desktopLyricsPosSettle, func() {
      if id != s.posSaveSeq { ... } // 无锁读
      s.saveDesktopLyricsPos(w)
  })
  ```

  `posSaveTimer` 本身守规矩地放在 `desktopMu` 里，唯独序号这一对读写漏了。
- **附带风险**：`time.Timer.Stop()` 与「回调已经在执行」互斥失败时，回调仍会拿着**已 Close 的窗口句柄**调 `w.Position()`（`saveDesktopLyricsPos:191-195`），Wails 对已销毁窗口的行为未定义。`closeDesktopLyricsWindow`（`desktop_lyrics.go:96-113`）先 Stop 再 Close，属于「通常能挡住」而不是「保证能挡住」。
- **建议修法**：把序号读写都收进 `desktopMu`（`nextPosSaveSeq` 加锁；回调里先 `s.desktopMu.Lock()` 取 `s.posSaveSeq` 再比较），并在回调开头判断 `s.desktopOn` 与窗口是否仍是当前窗口。

### B11 `WriteCacheToFiles` 一次同步改写全库用户文件，无取消、无分批、无进度上限

- **位置**：`services_cover.go:951-1084`
- **现象**：缓存里有几百上千首封面/歌词时，这个 Wails 绑定调用会连续重写每个音频文件（每首 = 读整个文件 + 重建 moov/FLAC metadata + 写临时文件 + fsync + rename），期间：前端只能等（没有任何取消入口）、每首都发一条事件（`emit("meta:embed-progress")`）、用户无法中止，若中途退出应用则剩余文件未处理且不记录断点。
- **根因**：函数签名没有 `context`，循环里没有任何 `ctx.Err()` 检查（对比同仓库其它批量任务：`loudness.MeasureAll` 有 ctx 检查与取消、`library.readAll` 有 cancelled 语义）。
- **证据**：`services_cover.go:997-1071` 是纯 `for i, id := range order` 循环，唯一的中断路径是 return 错误（而错误只在内存里累计成 `reasons`）。
- **建议修法**：加 `WriteCacheToFiles(ctx context.Context)` 或拆成 `beginWriteCacheToFiles()/cancelWriteCacheToFiles()`：每 N 首检查一次 ctx、分批（例如每批 20 首）后重新调用、把已完成的 id 落盘成断点文件；前端在按钮上同时给出「中止」。

### B12 `WindowService.Restart()` 先拉起新进程再退出，与单实例锁冲突（推测）

- **位置**：`services.go:1790-1810`、`main.go:256-263`（`SingleInstance.UniqueID + OnSecondInstanceLaunch → ShowMain`）
- **现象（推测，未在本机复现）**：点「重启以应用材质」后，新进程启动时若旧进程还持有单实例锁，Wails 会把「第二次启动」当作拉起已有实例处理：新进程自行退出、旧进程被回调 `ShowMain`，随后旧进程执行 `Quit()` —— 结果是应用整个退出，**重启变成关闭**。
- **根因**：`Restart` 的顺序是 `cmd.Start()` → `s.app.Quit()`（`services.go:1803-1809`），两个动作之间没有任何「旧实例锁已释放」的等待或协议；而单实例的唯一 ID 是硬编码常量，新进程无法以「非单实例」方式启动。
- **建议修法**：改用「先退出，再由一个 detached 的自重启 helper 拉起」；或给新进程传一个 `LMPLAYER_SKIP_SINGLE_INSTANCE=1` 环境变量，由 `main.go` 在构造 Options 时据此不注册 SingleInstance（`Restart` 里 `executil.Command` 已被用来起进程，加一个 env 即可）。若暂不修，至少把按钮文案改成「退出并重新打开」。

### B14 `PlaylistService.Export` 在元数据缓存缺失时静默产出空 m3u，且每次都整读 5.9MB 索引

### B17 转码缓存目录用 `DataDir`，而其它缓存用 `CacheDir`；`cacheDir` 运行期可改却无人重装配
- **位置**：`main.go:97`（`filepath.Join(store.DataDir(), "cache", "transcode")`）、`main.go:144` 与 `main.go:90`（`library.NewManager` 内部 `store.Get().CacheDir`）、`services.go:1965-1966`（前端可写 `cacheDir`）。

### B18 `coverItems` 里被跳过的封面会让 `active` 标记全灭
- **位置**：`services_cover.go:506-534`。读不到文件的项被 `continue` 跳过（510-513），但 `Active` 是对**原始下标**求值（530、533）。若第 0 张的文件被用户手工删掉，列表里没有任何一项被标为 active，前端轮播/缩略图会显示「没有当前封面」。
- **建议**：在跳过时把 active 重映射（或返回 `activeIndex` 为该项在输出切片里的位置）。
- **附带小浪费**：循环内每项都调一次 `s.cache.ActiveCover(songID)`（530），循环外又调一次（533），共 N+1 次加锁查表；把值先取出来即可。

### B19 死代码 / 死状态

### B20 皮肤清单里的 `styles` 未做目录穿越校验（被 handler 兜住，但契约不严）
- **位置**：`internal/skins/skins.go:363-367`（原样收集）与 `381-388`（只校验文件存在）；对比同一函数对 `module` 有 `strings.Contains(module,"..")` 检查（`372-375`）。
- **现象**：`skin.json` 里写 `"styles":["../../../secret.css"]` 时，只要该文件存在就会被写进 `SkinInfo.Styles` 并下发给前端；实际请求会被 `Handler` 的 `filepath.Clean("/"+rel)`（`skins.go:458-460`）折回根目录而 404，因此**不可利用**，但「扫描结果包含目录外文件」这个契约是坏的（设置界面/前端会去请求一个必然 404 的地址）。
- **建议**：给 `styles` 复用一个 `safeRelPath(s)`：拒绝 `..`、绝对路径、盘符、以及 `withinDir(dir, join(dir,s))` 为假的项。

### B21 `mp4Duration` 兜底会把整个文件读进内存（并发 4 ⇒ 峰值数百 MB）
- **位置**：`internal/meta/meta.go:403-421`。头部 2MB 里找不到 mvhd 时，对 ≤64MB 的文件 `whole := make([]byte, st.Size())` 全量读入，再做 `bytes.Index(buf,"mvhd")` 全量扫描。首次扫描（缓存为空）时 `readAll` 并发 4，最坏 256MB 瞬时占用 + 4×O(size) 扫描。
- **建议**：改为「按 box 顺序流式前进、只把 moov 读进内存」（moov 通常几 MB），或至少把上限从 64MB 降到 8MB 并顺序读取 moov。

### B22 本地媒体服务缺少写超时与并发上限
- **位置**：`internal/media/server.go:120-123`。`http.Server` 只设了 `ReadHeaderTimeout`；一个本机进程（或前端的 bug）打开 `/audio/...` 后不读数据，会长期占住 goroutine + 文件句柄 + 转码条目的 `usedAt` 不被刷新（可能被 LRU 删到正在读的文件，见 B3 相关路径）。
- **建议**：加 `WriteTimeout`/`IdleTimeout`，并对播放连接数设一个上限。

### B23 `ffmpeg.writeWAV` 的成品改名既无 fsync 也无重试
- **位置**：`internal/ffmpeg/ffmpeg.go:504-532`。`dst.Close()` 后直接 `os.Rename(tmp,out)`；断电/崩溃可能留下长度正确但内容为空的 WAV（`ensureTranscoded` 用 `st.Size() == existing.size` 判定有效性，长度对得上就会一直被复用）。这与 `atomicfile` 的持久性承诺不一致。
- **建议**：`dst.Sync()` + 复用 `atomicfile` 的退避改名；同时把 `TranscodeToWAV` 的 `out` 写入改为先写 `out+".tmp"`。

### B24 `Probe` / `SoundDurationMS` 完全忽略 `cmd.Run()` 的错误
- **位置**：`internal/ffmpeg/ffmpeg.go:388`、`425`（`_ = cmd.Run()`）。ffmpeg 被删除、被策略拦住、被超时 kill 时都只能从「未能解析出时长」间接推断；`enrichDurations` 会把这批文件标记成 `Probed=true` 永久跳过（`library.go:852-935` 的写回逻辑），于是**一次环境故障会被缓存成「这些文件确实没有时长」**。
- **建议**：`runErr != nil` 时不要写 `Probed=true`（或只在 `DurationSec>0` 或 stderr 明确为空时写），并把 runErr 带进日志。

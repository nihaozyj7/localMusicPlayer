# 桌面背景歌词：启动自动启用的开关 + 启动时机 + 首帧露出

> 需求原文（三点）：
> 1. 在设置里加一个设置项：**桌面背景歌词在启动时自动启用（如果用户已经启用）**；
>    关掉它之后，桌面背景歌词**只在本次启动生效**。
> 2. 启动时自动恢复桌面背景歌词，应当**延后执行** —— 否则会和主窗口抢性能，
>    造成主窗口卡顿与启动缓慢。
> 3. 桌面背景歌词启动时会**黑一下**，应当让它**成功渲染之后再显示到桌面**。

## 1. 问题一：开关的语义被一个字段同时承担了

`ShowDesktopWallpaper` 以前同时回答两个问题：

| 它在回答 | 用户期待 |
| --- | --- |
| 现在开着吗？ | 关掉就该立刻关掉 |
| 下次启动还自动开吗？ | 关掉之后就只在本次生效 |

两个问题的答案被绑在一起，于是「只想临时开一下」根本做不到：临时打开看一会儿，
退出程序，下次启动它又自己冒出来了。

### 解法：拆成两个字段

| 字段 | 含义 | 默认值 |
| --- | --- | --- |
| `showDesktopWallpaper` | **本次运行**开着吗（随开关实时落盘） | `false` |
| `autoStartDesktopWallpaper` | **下次启动**要自动开吗 | `true` |

启动时恢复哪一个，由 `bootstrap.Config.StartupDesktopMode()` 单点回答：

```go
case c.ShowDesktopWallpaper && c.AutoStartDesktopWallpaper: return "wallpaper"
case c.ShowDesktopLyrics:                                  return "lyrics"
default:                                                   return "off"
```

启动恢复（`early_theme.go`）与「用户中途改配置就退让」（`stillWanted`）两条路径
都读它 —— 规则只写一遍，就不会出现「恢复逻辑和退让逻辑各判一套」的错位。

默认值取 `true` 是有意的：加入这个开关**之前**的行为就是「上次开着，下次启动自动
恢复」。默认成 `false` 会让所有老用户在升级后觉得背景歌词不再自动启动了 ——
那是静默的行为回退。`TestAutoStartDesktopWallpaperDefaultsOn` 钉住这一条。

桌面歌词**没有**这个「仅本次」的语义（它的开关本身就是持久的），所以只加在背景
歌词上。

## 2. 问题二：启动恢复和主窗口抢性能

### 原来是怎么抢的

`restoreDesktopModeOnStartup` 收到 `ApplicationStarted` 就立刻 `setDesktopMode`。
那一刻主窗口正处在启动高峰里：解析前端 bundle、解码封面、套主题、建皮肤、画首帧。
而背景歌词要做的恰好是**同一件事的第二个实例** —— 再解析一遍同样的皮肤、再建一块
整屏 WebView2、再渲染一整套画面。两边抢同一批 CPU / GPU 资源，结果就是主窗口卡顿、
启动变慢。

### 关键：`shown` 不够用

最直觉的修法是「等主窗口显示出来再恢复」，也就是等 `WindowService.shown`。但实测
这个判据**太早**：前端的 `markWindowReady()` 写在 `main.js` 模块顶层，模块一执行
就发 `/boot/reveal`，而 `await bootstrap()` 在那之后。

```
模块执行 ──/boot/reveal──► 窗口可见 ──bootstrap/主题/封面……──► /boot/booted
                            ↑ shown                              ↑ booted
                            └──── 这一段才是被抢性能的高峰 ────┘
```

于是新增第二个、**更晚**的信号：前端在 `main()` 末尾（`document.body.dataset.ready
= "true"` 之后）发 `/boot/booted`，Go 侧 `MarkBooted()` 置位 `booted`。

背景歌词的启动恢复等的是 `booted`。

### 为什么不用固定延时

启动耗时在不同机器上差好几倍（杀毒软件扫描、冷启动读盘、曲库大小都会影响）。
固定延时要么短了（还在高峰里，性能问题照旧），要么长了（用户白等）。等信号则是
「主窗口一准备好就立刻动手」。

`waitMainWindowBooted` 用 100ms 轮询，而不是注册回调，因为它要同时覆盖三种情况：

| 情况 | 轮询的应对 |
| --- | --- |
| `booted` 在前端信号到达前就已经置位（刷新页面 / 第二个实例） | 第一次轮询就读到 |
| 前端信号永远不来（脚本报错 / 非标准资源加载） | 30 秒超时后照常恢复 |
| 等待期间用户自己改了配置 / 手动开了背景歌词 | 每一轮都查一次，立刻退让 |

最后一条尤其重要：用户等不及手动打开背景歌词，恢复逻辑**不能**过一会儿再开一次。
`desktopModeTouched` 把「碰过这一组开关里的任意一个」都算作退让信号。

## 3. 问题三：启动时的「黑一下」

这一条在 `docs/17-桌面背景歌词黑闪修复.md` 里已经修过主体：「先在桌面之外把首帧
渲染完、再放进桌面」的两阶段流程（DWM 遮罩后台出帧 → 页面报两帧 rAF → 摘遮罩 +
`SetParent`）本来就是正解，且判定为「成功渲染之后再显示」。

本轮补的是**最后一条还会露色的路径**：本机遮不住（`armDesktopWallpaperOffscreen`
返回 false）时走旧路径，露出来的是窗口自己的 `BackgroundColour` —— 那以前写死成
近黑的 `NewRGB(8, 8, 10)`。

现在它按当前主题的首帧底色算，与主窗口**同一个算法**
（`early_theme.go#firstFrameWindowColour`，即 `--bg-app`）：

```go
func (s *WindowService) desktopWallpaperFirstFrameColour() application.RGBA {
    if s.store == nil { return application.NewRGB(8, 8, 10) }
    return firstFrameWindowColour(s.store, s.themeMgr)
}
```

于是即便遮不住、真的露出了一帧，露出来的也是与桌面画面**同色系**的底色，而不是
一块突兀的近黑；浅色主题下尤其明显。为此 `WindowService` 增加了 `themeMgr` 字段
（由 `main.go` 注入；为 `nil` 时安全退回近黑）。

另外，问题二的延后执行**顺带**又消掉一层黑闪来源：恢复现在发生在主窗口启动完成
之后，那时媒体数据早就推过来了，`MarkDesktopWallpaperPainted` 通常几十毫秒内就
会到达。`wallpaperShowFallback`（5 秒兜底）因此只在「页面真的坏了」时生效，
不再是启动路径上的常客。

## 6. 用户可见行为（一句话版）

- 设置 → 歌词 → 「桌面背景歌词」：开关当前这次运行；
- 设置 → 歌词 → 「启动时自动启用桌面背景歌词」：开关下次启动是否自动恢复；
- 关掉后者后，本次**仍然可以**手动打开背景歌词，只是重启后不再自动出现；
- 自动恢复现在发生在主窗口启动完成之后 —— 桌面上晚一两秒出现，但不再拖慢启动；
- 本机遮不住遮罩时，露出的底色也与当前主题同色系，不再是一块近黑。

## XSS / 注入

### 【P0-1】第三方皮肤是「同源任意 JS 执行」，`script-src 'self'` 无法构成边界

**CONFIRMED**

`frontend/packages/player-skins/src/index.js:224-226`
```js
export async function loadExternalSkin(info) {
  if (!info?.id || !info?.module) throw new Error("皮肤清单缺少 id / module");
  const mod = await import(/* @vite-ignore */ info.module);
```

`frontend/src/js/playerhost.js:450-459`
```js
for (const info of items) {
  if (!info?.id || !info?.module) continue;
  const base = `${SKINS_PREFIX}${encodeURIComponent(info.id)}/`;
  try {
    await loadExternalSkin({
      id: info.id,
      name: info.name,
      module: base + String(info.module).replace(/^\/+/, ""),
```

**为什么重要**：皮肤模块由后端从用户数据目录 `player-skins/<id>/` 托管在**同源** `/skins/<id>/<file>`，前端用动态 `import()` 直接执行。CSP 是：

`frontend/src/index.html:8`
```html
content="default-src 'self'; img-src 'self' data: blob: file:; media-src 'self' blob: file:; style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'self' ws:"
```

`script-src 'self'` 只限制「跨源」，对**同源的用户可控目录**完全没有约束力 —— 一个皮肤文件就是一份拥有完整 DOM/`fetch`/`localStorage` 权限的任意代码。它 `import` 后可以读到 `localStorage` 里的 `music-player.state.v1`、可以 `fetch('/api/...')` 调后端、可以改写界面做钓鱼。这不是「漏洞」而是**有意的扩展机制**，但必须在威胁模型里显式写明，并确认用户数据目录的写入来源（是否可被下载的歌曲文件、歌词、封面等间接投毒）。

**具体修复建议**：
1. 在 README / 安全说明中**明确定级**：安装第三方皮肤 = 运行任意代码，须信任来源。
2. 加载前要求用户在设置界面**显式确认一次**（而不是丢进目录就自动 `import`），把「已确认的皮肤 id + 文件哈希」记进配置，哈希变化后重新确认。
3. 后端 `internal/skins` 在 `List` 时对模块文件做**签名/哈希校验**（若产品允许签名机制）。
4. 若未来允许从网络安装皮肤，必须改为独立 origin（如自定义协议 `skin://`）或 iframe 沙箱，不能继续同源 `import`。

### 【P2-1】`lyrics-view.js` 把未校验的 `time` 直接插进 HTML 属性

**CONFIRMED（数据源受限，风险低）**

`frontend/packages/player-skins/src/lyrics-view.js:159-167`
```js
scroll.innerHTML = lines
  .map((l, i) =>
    interactive
      ? `<div class="lyric" role="button" tabindex="0" data-time="${l.time}" data-lyric-index="${i}">${esc(
          l.text
        )}</div>`
      : `<div class="lyric" data-time="${l.time}" data-lyric-index="${i}">${esc(l.text)}</div>`
  )
  .join("");
```

`l.time` **没有**经过 `esc()`，而 `l.text` 经过了。属性上下文里未转义的 `"` 可以闭合属性并注入新属性（如 `onmouseover`）。

**为什么重要**：`lines` 来自 `parseLrc(text)`，`text` 来自后端歌词（内嵌标签 / 同目录 `.lrc` / 在线匹配）。攻击路径是：用户下载了一个 `.lrc` 或音频文件，其歌词里混入非数字的 `time` 字段。是否可行取决于 `lrc.js` 的解析是否**强制** `time` 为数字。`fx-lyrics.js` 同样如此：

`frontend/packages/player-skins/src/fx-lyrics.js:191-192`
```js
? `<div class="fxl__line" role="button" tabindex="0" data-index="${i}" data-time="${lines[i].time}" data-state="todo" data-text="${esc(text)}">`
: `<div class="fxl__line" data-index="${i}" data-time="${lines[i].time}" data-state="todo" data-text="${esc(text)}">`
```
注意 `data-text="${esc(text)}"` 是**正确**的，唯独 `data-time` 裸奔 —— 说明这是遗漏而非设计。

**具体修复建议**：最小改动 —— 两处都改成 `data-time="${esc(l.time)}"` / `${esc(lines[i].time)}`；更彻底的做法是在 `lrc.js` 的 `parseLrc` 出口处加一道 `Number()` 强制转换（数值类型天然安全，也免去调用方每次都想起来要转义）：

```js
// lrc.js 解析出口
lines = raw.map((l) => ({ time: Number(l.time) || 0, text: String(l.text ?? "") }));
```

> 说明：该条我列为 **CONFIRMED 的代码缺口**，但**实际可利用性 SUSPECTED**（未验证 `lrc.js` 是否已强制数值化）。

### 【P2-2】`esc()` 只覆盖 5 个字符，未覆盖属性引号场景的全部风险面

**CONFIRMED**

`frontend/src/js/utils.js:162-174`
```js
export function esc(s) {
  return String(s ?? "").replace(
    /[&<>"']/g,
    (c) => ({ "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;" })[c]
  );
}
```

转义集包含 `& < > " '` —— 对**HTML 文本与双引号属性**是正确的。但项目的 `esc` 有 **4 份独立副本**，行为一致性靠人工维护：

| 位置 | 函数名 |
| --- | --- |
| `frontend/src/js/utils.js:162` | `esc` |
| `frontend/packages/player-skins/src/html.js:31` | `escapeHtml` |
| `frontend/packages/player-skins/src/lyrics-view.js:244` | `defaultEscape` |
| `frontend/packages/player-skins/src/fx-lyrics.js:52` | `defaultEscape` |

四份实现目前字符集完全一致（已逐字比对），但 `packages/` 两份是**故意**不依赖宿主（包要能独立）。风险是将来只改其中一份。

**具体修复建议**：包内 `lyrics-view.js` / `fx-lyrics.js` 的 `defaultEscape` 改为从 `html.js` import `escapeHtml`（`html.js` 已导出、包内引用完全合理），把包内副本从 3 份降到 1 份。宿主的 `utils.esc` 与包的 `escapeHtml` 保留 2 份是合理边界，但应在两处注释里互相指向对方。

## 状态管理

### 【P1-1】`ui/desktop-lyrics.js` 的 `on()` 订阅在组件卸载时从不取消

**CONFIRMED**

`frontend/src/js/ui/desktop-lyrics.js:64-67, 91`
```js
connectedCallback() {
  super.connectedCallback();
  this.boot();
}
...
async boot() {
  const ready = await connect();
  ...
  on("desktop:lyrics", (state) => this.render2(state));
```

**为什么重要**：
1. `bridge.js#on` 返回取消订阅函数（`bridge.js:128-145`），此处**丢弃了返回值**；
2. 该类直接继承 `LitElement`，**不是** `MpElement`，没有 `_unsubscribers` 机制，也没有 `disconnectedCallback`；
3. 每次 `connectedCallback` → `boot()` 都会**新增**一个监听。Wails 的事件订阅在后端广播层面会累积；在浏览器预览路径下（`bridge.js:142-144`）则是往 `window` 上挂 `dsh:desktop:lyrics` 监听，**永不移除**。

在 `lyrics.html` 这种单页单实例场景下实际影响很小，但它是**错误示范**：`ui/desktop-lyrics.js` 与 `ui/desktop-lyrics.js` 并存两条路径时容易复制到别处。

**具体修复建议**：
```js
class MpDesktopLyrics extends LitElement {
  constructor() { super(); /* … */ this._off = null; }
  async boot() {
    const ready = await connect();
    if (!ready) { /* … */ return; }
    if (this._off) this._off();               // 幂等：boot 可能被重复调用
    this._off = on("desktop:lyrics", (s) => this.render2(s));
    // …
  }
  disconnectedCallback() {
    this._off?.(); this._off = null;
    super.disconnectedCallback();
  }
}
```

### 【P2-3】`playerhost.js` 的歌词缓存 Map 无上限

**CONFIRMED**

`frontend/src/js/playerhost.js:79-82`
```js
let lyricsCache = new Map(); // songId -> { lines, text, source, status }
/** 已经做过在线匹配的歌曲（避免同一首歌反复联网） */
const autoMatched = new Set();
const lyricsPending = new Set();
```

`lyricsCache` 在 `getLyrics` / `applyOnlineLyrics` / `setLyricsStatus` 里不断 `set`，**唯一**的清空入口是显式调用 `invalidateLyrics()`（`playerhost.js:200`）。`autoMatched` 同理，只增不减。

**为什么重要**：每条缓存是 `{ lines, text, source, status }`，`lines` 是解析后的数组。一首歌约 40~80 行歌词，每行一个 `{time, text}` 对象。**1 万首歌 ≈ 数十万个对象常驻**（粗估 20~60 MB）。对一个「后台常驻托盘、可能连续播放数天」的桌面应用，这是可观测的内存增长。`store.js` 那边对同类问题**已经**做了限制（`PROGRESS_MAX = 1500`，`store.js:1258`），说明团队有意识，只是 `playerhost` 漏了。

**具体修复建议**：给 `lyricsCache` 加 LRU 上限（例如 200 首），或在切歌时调用 `pruneOnlineSongs` 同样的思路回收：
```js
const LYRICS_CACHE_MAX = 200;
function touchLyricsCache(id) {
  const v = lyricsCache.get(id);
  if (v) { lyricsCache.delete(id); lyricsCache.set(id, v); } // Map 保序 = 简易 LRU
  while (lyricsCache.size > LYRICS_CACHE_MAX) {
    const oldest = lyricsCache.keys().next().value;
    if (oldest === state.currentId) break;
    lyricsCache.delete(oldest);
  }
}
```

### 【P1-2】`playerhost.js#watchResize` 的 `ResizeObserver` 在详情页关闭后仍观察 `display:none` 的舞台

**CONFIRMED**

`frontend/src/js/playerhost.js:836-848`
```js
function watchResize() {
  if (host.resizeObserver || typeof ResizeObserver !== "function") return;
  host.resizeObserver = new ResizeObserver(() => {
    const r = host.stage.getBoundingClientRect();
    push({ type: "resize", width: Math.round(r.width), height: Math.round(r.height) });
  });
  host.resizeObserver.observe(host.stage, { box: "border-box" });
}
```

`disconnect()` **只**发生在 `unmountSkin()`（`playerhost.js:830-833`）：
```js
if (host.resizeObserver) {
  host.resizeObserver.disconnect();
  host.resizeObserver = null;
}
```

而 `unmountSkin()` 只在两种情况被调用：
1. `renderPlayerView()` 关闭详情页的 `closeTimer` 回调里（`playerhost.js:1044`）—— 这条**是**会走的；
2. `mountSkin()` 开头（换皮肤，`playerhost.js:752`）。

**关键缺口**：`closeTimer` 有 `if (state.playerOpen) return;` 守卫（`playerhost.js:1042`），若用户在关闭动画期间重新打开详情页，`closeTimer` 被 `clearTimeout`（`playerhost.js:1051-1054`），**`unmountSkin()` 永不执行** —— 这正是设计意图（避免闪断），但意味着 **observer 一直活着**。

而 `host.stage` 在详情页关闭时是 `view.hidden = true`（`playerhost.js:1043`）。`fit.js:25` 的注释本身已经点出了这个现象：
```js
详情页关闭时 `#playerview-stage` 是 display:none，ResizeObserver 会推来
```

**为什么重要**：`ResizeObserver` 是**强引用**链 —— `observer → host.stage → DOM 子树`。虽然 `body` 上的元素不会被 GC 回收（本来就在 DOM 里），但 observer 回调在地图/皮肤已卸载后仍会触发 `push({type:"resize"})`，而 `push` → `host.ctx?.push` 此时 `host.ctx === null`（`playerhost.js:828`），是空操作 —— **功能上无害**。真正的代价是：每次窗口尺寸变化（拖拽窗口边缘、DPI 变化、最大化）都会执行一次 `getBoundingClientRect()` **强制同步布局**，在详情页关闭状态下这是纯粹浪费，并且会与 `fit.js` 里的注释所描述的行为互相印证是一条已知但未修的路径。

此外 `host.themeObserver`（`playerhost.js:1207-1217`）**从来没有** `disconnect()` 调用 —— 这是**永久存活**的 `MutationObserver`。它是单例、观察 `documentElement`，危害低，但属于同类遗漏。

**具体修复建议**：
1. 详情页关闭（`!open` 分支）时调 `host.resizeObserver?.disconnect(); host.resizeObserver = null;`，重新打开时 `watchResize()` 会自然重建（函数已有 `if (host.resizeObserver) return` 守卫，重建是安全的）。
2. 或者更简单：在回调开头加早退守卫，避免无意义的强制布局：
```js
host.resizeObserver = new ResizeObserver(() => {
  if (!state.playerOpen) return;          // 详情页没开，尺寸无意义
  const r = host.stage.getBoundingClientRect();
  push({ type: "resize", width: Math.round(r.width), height: Math.round(r.height) });
});
```
3. `themeObserver` 在 `closePlayer` / 应用生命周期结束处补 `disconnect()`；或在 `observeTheme()` 里复用同一个 observer 但记录「是否还需要」。

### 【P2-5】`playerhost.js#ensureCarouselTicker` 的 `setInterval` 一经启动永不停止

**CONFIRMED**

`frontend/src/js/playerhost.js:880-885`
```js
function ensureCarouselTicker() {
  if (host.carouselTimer) return;
  // 1 秒一跳的「检查器」而不是按间隔直接起定时器：
  // 这样改设置、暂停、切歌都能立刻生效，不用到处重起定时器
  host.carouselTimer = setInterval(tickCarousel, 1000);
}
```
调用点：`renderPlayerView()` 首次运行时（`playerhost.js:1023`）。**没有** `clearInterval` 调用点（全仓库搜索 `carouselTimer` 只有此处赋值 + 这段守卫）。

`tickCarousel`（`playerhost.js:864-878`）开头就做了三重早退：
```js
if (!enabled || !state.playerOpen || !state.playing || covers.length < 2) return;
```

**为什么重要**：功能上无害（早退很便宜），但这是一个**每秒唤醒一次、永远不停**的定时器。对于「最小化到托盘、可能整天挂着」的桌面应用，它会阻止浏览器/WebView 进入更深的省电状态，也让「应用空闲时无定时器」这个可测试的属性失效。同文件的注释（`playerhost.js:882-883`）解释了为什么用「检查器」模式 —— 理由成立，但**应该配合生命周期**：详情页关闭 → 停表；打开 → 起表。

**具体修复建议**：
```js
function stopCarouselTicker() {
  if (host.carouselTimer) clearInterval(host.carouselTimer);
  host.carouselTimer = null;
```

### 【P3-6】`bridge.js` 的失败语义清晰，但「后端调用失败」与「未连接」不可区分

**CONFIRMED**

`frontend/src/js/bridge.js:156-159`
```js

  if (!active || !bindings || typeof fn !== "function") return null;

```

未连接时返回 `null`，后端抛错时**异常穿过**。调用方必须同时处理「null」和「throw」两种失败形态。多数调用点做得不错（`settings.js` 有 20+ 处 `catch (err) { toast(...) }`，逐条核对过，见下），但 **`null` 分支常被忽略**。例如：

```js
  const songs = await backend.songs();
  if (Array.isArray(songs)) { … }
```
这里 `Array.isArray(null)` → false，静默跳过。属于**可接受**的防御（有 `if` 守卫）。

**具体修复建议**：给 `call()` 的返回值语义加一层显式化 —— 未连接时返回一个哨兵或抛 `NotConnectedError`，让调用方无法「忘记处理」。或在 `bridge.js` 里统一 `console.warn` 一次未连接的调用（目前只在 `connect()` 里 info 过一次）。

```js
export function notify() {
  for (const fn of listeners) {
```

### 【P2-9】浮层与对话框缺少焦点陷阱（focus trap）

**CONFIRMED**

`frontend/src/js/ui/overlays.js:238-241`（弹窗）
```js

```
`aria-modal="true"` 已声明，但**没有**实现焦点陷阱：`openModal` 里只有初始聚焦（`overlays.js:273-274`）：
```js

```
按 `Tab` 会把焦点移到背后的界面上 —— 而 `aria-modal="true"` **正是向屏幕阅读器承诺「背景不可达」**。声明与实现不符，比不声明更糟。

- `ui/search.js:128`：`role="dialog" aria-modal="true"`，只有初始聚焦（`search.js:90-94`），无陷阱。
- `ui/lyrics.js:159`：`role="dialog"`（无 `aria-modal`），无陷阱。
- `ui/panels.js` 的四个面板：`aria-label` 有，`role` 不明显，无陷阱。

**现有的键盘支持是好的**：`Esc` 关闭在菜单（`overlays.js:123-125`）、弹窗（`overlays.js:231`）、面板（`panels.js:108-112`）、搜索（`search.js:150-155`）全部实现。

**具体修复建议**：抽一个 `trapFocus(root)` 工具（`MpElement` 的兄弟或 `dom.js`）：
```js
export function trapFocus(root) {
  const SEL = 'a[href],button:not([disabled]),input:not([disabled]),select,textarea,[tabindex]:not([tabindex="-1"])';
  const onKey = (e) => {
    if (e.key !== "Tab") return;
    const items = Array.from(root.querySelectorAll(SEL)).filter((n) => n.offsetParent !== null);
    if (!items.length) return;
    const first = items[0], last = items[items.length - 1];
    if (e.shiftKey && document.activeElement === first) { e.preventDefault(); last.focus(); }
    else if (!e.shiftKey && document.activeElement === last) { e.preventDefault(); first.focus(); }
  };
  document.addEventListener("keydown", onKey, true);
  return () => document.removeEventListener("keydown", onKey, true);
}
```
并在关闭时**把焦点还给触发元素**（目前没有任何 restore 逻辑 —— 关闭弹窗后焦点落在 `body`，键盘用户会丢失位置）。

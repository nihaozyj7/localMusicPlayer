# 播放时发现「放不出来」的文件：自动记录并从曲库移除

> 用户需求原文：
> 「可以触发扫描的时候判断音乐是损坏吗，在设置中的扫描结果那里显示扫描到的
> 不合法文件，点击可以查看是哪些文件」
>
> 追问后的最终设计（用户自己的选择）：
> 「只在播放的时候查，这样性能最优，播放的时候如果播放不了自动移除，
> 并在设置的扫描目录那里提示出来」

---

## 一、为什么不在扫描时校验（这是刻意的设计选择）

最初的方案是「扫描时逐首校验」。**放弃它的理由是成本与收益完全不成比例**：

| | 扫描时校验 | 播放时校验（最终方案） |
|---|---|---|
| 每首歌的代价 | 起一个 ffmpeg 进程（内置版静态链接，50~200ms） | **0** —— 解码本来就要发生 |
| 用户 8725 首的库 | 十几分钟起步，且每次扫描都要重来 | 只对真正播放过、且真的失败的那几首记账 |
| 绝大多数文件 | 检测结果是「好」，白花 | 不产生任何开销 |

关键洞察：**播放失败的时候，解码这件事已经发生过了**。登记它不需要任何额外
工作，只是把已经付过的代价变成可见的信息。而扫描时校验是在为「可能永远
不会被播放的文件」预先付一遍钱。

代价不只是时间：它会让扫描从「秒级」变成「十几分钟」，而扫描发生在启动路径
上，用户每次开程序都要等。

## 二、行为

### 播放时

```
用户点到一首放不出来的歌
  → toast 一条：无法播放：<歌名>（已记入「音乐文件夹」清单）
  → 自动跳到下一首继续播（见 docs/30-播放失败提示与自动跳转.md）
  → 后端登记进清单（写进配置，重启后仍在）
  → 从曲库摘掉（磁盘文件不动）
```

连续失败 5 首会停下（避免整库坏文件时一路刷到底），这与上一轮的熔断逻辑一致。

### 设置 → 音乐文件夹

清单**折叠**在文件夹卡片下方，空的时候只占一行（绝大多数用户永远看不到它）：

```
┌─────────────────────────────────────────────────┐
│ ⓘ  发现 2 个无法播放的文件      查看是哪些文件  › │
└─────────────────────────────────────────────────┘
```

点开后是每一条的详情：文件名、歌手、格式、失败次数、时间、**完整路径**、
**失败原因原文**，以及两个操作：

- **已修好** —— 清掉记录 + 重新扫描（文件修好后重新回到曲库）
- **忽略** —— 只从清单里去掉这条提示，不动曲库

底部还有「清空清单」。

空态是一行轻量提示：「没有发现放不出来的文件 / 播放时若某个文件解不出来，
会自动记录到这里」—— 说明这个功能**存在且在工作**，而不是一片空白让人
怀疑是不是没做。

## 三、实现

### 后端

| 文件 | 职责 |
| --- | --- |
| `services_unplayable.go` | `UnplayableService`：`Report` / `List` / `Count` / `Remove` / `Clear` / `Forget` |
| `internal/bootstrap/config.go` | `Config.UnplayableFiles` + `UnplayableFile` 类型 |
| `internal/library/library.go` | `Manager.DropSong` —— 从曲库摘歌（**连元数据缓存一起清**） |
| `services.go` | `LibraryService.DropSong` / `LookupSong`（刻意**不导出**给前端） |

`DropSong` 里最容易写漏的一点：**元数据缓存条目也必须一起清**。
只摘内存不同步缓存的话，下次扫描会命中缓存 → 认为「这个文件没变，复用旧
元数据」→ 这首歌又回到曲库，用户看到的就是「移除之后一扫描它又回来了」。
`TestDropSongRemovesSongAndCache` 锁住这条。

### 前端

| 文件 | 改动 |
| --- | --- |
| `audio.js` | `handlePlaybackFailure` 里调 `reportUnplayable`（不 await，失败路径不该等 IPC） |
| `store.js` | `unplayableFiles` 状态 + `removeSongFromLibrary` + 清单的增删函数 |
| `main.js` | 订阅 `library:unplayable` 事件 → 刷新清单 + 提示用户 |
| `ui/settings-view.js` | 清单的折叠 UI（`unplayableSection` / `unplayableList`） |
| `settings.js` | 三个新动作的处理（展开 / 已修好 / 忽略 / 清空） |
| `styles/components/settings.css` | `.unplayable*` 样式 |

`removeSongFromLibrary` 必须同时改三处，缺一处就会不一致：
`allSongsRaw`（过滤引擎的输入）、`songs`（列表渲染）、`queue`（播放队列，
留着会让「下一首」跳到一首已经没了的歌）。`unplayable-list.test.js` 覆盖。

## 五、踩到的坑：绑定映射是手写字符串键

`bridge.js` 里 `bindings` 对象的键名与 `backend.*` 的调用名是**两套手写的
字符串**，中间没有任何编译期或测试期校验。我加了 `unplayableReport` 的调用
却忘了在 `bindings` 映射里加 `Unplayable: mod.UnplayableService`，结果：

- 构建**完全成功**，没有任何警告
- 运行时 `call()` 拿到 `undefined` 直接返回 `null`，于是清单**永远是空的**
- 端到端测试立刻抓到了（「清单里出现了这条记录 — 0 条」）

这正是 bridge.js 顶部那段注释警告过的同一类错误（`ResetDesktopLyricsPosition`
曾经漏接线，表现是「重置按钮 100% 报 is not a function」）。这次因为
`call()` 对 `undefined` 是静默返回，症状更隐蔽 —— 所以**端到端验证不能省**。

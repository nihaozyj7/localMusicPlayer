## 6. 三个踩过的坑（改代码前务必知道）

1. **`StableID` 必须按 UTF-16 码元计算**
   JS 的 `charCodeAt` 按 UTF-16 取值，中文占 2 个码元。Go 若直接遍历 UTF-8 字节，
   同一路径会算出不同 id。实现里用 `utf16.Encode`，并有测试守着。

2. **`fsnotify` 不递归**
   必须对每个子目录分别 `Add`，并在 `Create` 事件里判断是否是目录、递归补登记，
   否则新建子文件夹里的歌永远不会被扫到。

3. **MP4 的 `covr` 里那个 `data` box 的长度一直多写了 4 字节**
   `covr` 内部的 `data` box 是「8 字节头 + 4 字节版本/类型 + 4 字节 locale + 载荷」，
   所以声明长度必须是 `len(图片)+16`，而旧代码写的是 `+20`。
   `dhowden/tag` 不校验嵌套 box 的长度，所以这个 bug 一直没暴露；
   但**按长度遍历 box 的解析器会读到错位字节** —— 新写的 `meta.ReadPictures`
   需要在一个 `ilst` 里连续读多个 `covr`，一上来就撞上了它。
   现在写入端改成 `+16`，读取端对「超长 data box」做了夹取容错
   （能读旧版本写出的文件，但旧格式下第二张起可能读不到 —— 重新应用一次封面即可修好）。
   **改动写回字节的逻辑后，务必跑 `internal/metacache/covers_embed_test.go`
   与 `go test ./internal/meta/`。**

## 7. 播放链路与响度均衡

### 7.1 音频必须与页面同源（踩过的坑）

打包后前端跑在 Wails 的虚拟主机 `http://wails.localhost`。
最初把音频放在另开的 `http://127.0.0.1:<随机端口>` 上，结果真实应用里
**完全无法播放**，`<audio>` 报：

```
MEDIA_ELEMENT_ERROR: Media load rejected by URL safety check
```

关键事实（用 `tools/netprobe.mjs` 接 CDP 看到）：

- 这是 Chromium 的私有网络/地址空间保护，**请求根本不会发出**——
  CDP 的 Network 域里看不到任何指向音频地址的事件，`fetch` / `XHR` 同样失败；
- 它在**无头 Edge 里复现不出来**（同样的页面源 + 同样的音频地址全部通过），
  所以只靠外部无头浏览器测试会漏掉这个致命问题；
- 加 CORS 头、加 `crossOrigin` 都没用，因为问题出在发起请求之前。

解法：把音频挂到 **Wails 自己的 asset server** 上，走同源路径
`http://wails.localhost/audio/<songID>?t=<token>`：

```go
Assets: application.AssetOptions{
    Handler: application.AssetFileServerFS(assets),
    Middleware: func(next http.Handler) http.Handler {
        audio := mediaSrv.Handler()
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            if strings.HasPrefix(r.URL.Path, media.AudioPrefix) {
                audio.ServeHTTP(w, r)
                return
            }
            next.ServeHTTP(w, r)
        })
    },
},
```

同源之后，CORS、`crossorigin`、Web Audio 的跨源取数限制全部消失
（这些代码保留着，因为独立端口模式仍可能被外部工具跨源访问）。
`MediaService.URL()` 返回的是**相对路径** `/audio/...`，不是绝对地址。

### 7.2 转码为什么要落盘而不是纯流式

最初的做法是 `ffmpeg ... pipe:1` 直接流式返回。问题是：

1. 流式响应没有准确的 `Content-Length` → 浏览器拿不到时长（`duration` 为 null），进度条不可用；
2. 想支持 seek 就得给 `Content-Range`，而要给长度就得知道输出字节数，
   但容器里报的时长与**实际可解码**时长并不相等（实测一首 3 秒的 m4a 差 47ms，
   声明的长度比实际多 44 字节）—— 于是浏览器一直等那几十字节，
   `loadedmetadata` 永不触发，**播放直接卡死**。

现在的做法：把不能原生播放的格式一次性转成 WAV 落到
`%APPDATA%\LocalMusicPlayer\cache\transcode\`，之后当普通文件提供，
用 `http.ServeContent` 处理 Range。好处是长度天然准确、字节级 seek 免费。
缓存按「路径+大小+修改时间」键控，带 600MB LRU 上限，
并发请求用 single-flight 合并（同一首歌只转码一次）。

> 另一个容易踩的 Go 细节：`ResponseWriter` 在第一次 `Write` 时会隐式发出 200，
> 之后再调 `WriteHeader(206)` 会被忽略。所以必须在写任何正文（含 WAV 头）之前定状态码。

### 7.3 响度均衡的实现

```
设置 → 响度均衡
  ├── loudnessMode: off | track | album
  ├── loudnessTarget: 目标整合响度（默认 -16 LUFS）
  └── loudnessLimit: 真峰值保护
```

**按需计算，不预先扫描。** 播到哪首就算哪首：先查缓存，命中就直接套用（零延迟）；
没命中就在后台算一次，算完立刻作用到当前播放，绝不阻塞出声。

补偿：**静态线性增益**，`gain = 目标 − 实测`，再按真峰值收口：

```go
if item.TruePeak != 0 {
    if maxAllowed := -1.0 - item.TruePeak; gain > maxAllowed { gain = maxAllowed }
}
```

为什么不用 loudnorm 的动态归一化：动态模式要实时重采样整条流，
既无法用于原生格式（不想为了调音量就转码），也会压缩音乐本身的动态对比。
静态增益是个恒定 dB，后端实时套用即可，切歌零延迟。

回放链路（**已迁到 Go 后端**）：`internal/audioplay` 把
ffmpeg 转出的 PCM WAV 经环形缓冲喂给 malgo（WASAPI）→ 声卡。
用户音量与响度补偿合成为一个线性增益，在音频回调里**逐样本插值**套用：

逐样本插值是必需的 —— 一次回调覆盖约 23ms 的音乐，整块用同一个增益值的话，
音量变化在波形上仍然是阶跃，拖动音量条会听到一串细碎的「咔」。

（迁移前是 `<audio>` → `createMediaElementSource` → `GainNode` → `destination`，
元素 `volume` 固定为 1。这条链路现在只在「后端音频不可用」时作为回退保留，
见 `frontend/src/js/audio.js` 的 legacy 分支。）

**缓存有效性 = 文件未变 && 算法版本未变。**

> **目标响度不在有效性条件里** —— 这是 2024 重构改掉的一处设计错误。

整合响度(LUFS) / 真峰值(dBTP) / LRA / 门限是**文件本身的固有量**，
与用户选哪个挡位毫无关系；补偿增益才是挡位相关的。所以缓存分两张表：

| 表        | key                       | 内容                            | 失效条件                 |
| --------- | ------------------------- | ------------------------------- | ------------------------ |
| `entries` | 路径 + 大小 + 修改时间    | 固有量（LUFS / dBTP / LRA / 门限） | 文件变了、算法版本变了   |
| `gains`   | songID → 挡位 → `{target, db}` | 各挡位的补偿增益（每条几个字节）  | 测量记录失效、算法升版   |

于是：**一首歌无论切几个挡位都只测量一次**，每多用一个挡位只多出一条
几个字节的增益记录。一万首 × 四挡 = 四万条约 1MB，所以不做淘汰，
只保证同一挡位绝不重复测量第二遍。

> 早期实现把 `Target` 放在 `Measurement` 里、并当作有效性条件，换挡位时
> 旧记录整条作废、还被 `InvalidateTarget` 删掉 —— 用户侧的表现就是
> 「从较响改回默认时，以前在较响算好的补偿丢了」。现在：
>
> - `Measurement` 里**没有** `Target` / `Gain` 字段（把约束写进类型里，
>   比写在注释里更不容易被后人改回去）；
> - `InvalidateTarget` 保留签名但**什么都不删**（返回 `dropped=0`）；
> - 旧格式（version 1）缓存在首次加载时自动迁移到新格式，
>   记录里那个 `gain` 归到它当时的 `target` 挡位下 —— **升级不丢数据**；
> - `GainFor` 两级命中：先查该挡位已缓存的增益；没有就用已有测量结果
>   现算一次（纯算术）并记账。所以「在 -14 测过、切到 -16」是
>   隔一个函数调用就有结果，而不是排一次队、再跑一遍 ffmpeg。

`State()` 暴露两个新字段供界面/诊断用：`concurrency`（实际并发，默认 2）与
`gains`（已记账的挡位增益条数）。

批量测量（界面上的「预先把全部歌曲算好」）只是可选预热，正常使用不需要。
它走**低优先级**队列，且每提交下一首之前让路（`YieldIfPending`），
所以用户点开某首歌时预热会立刻停下来先测那一首。

### 7.3.1 测量的两条路径（提速的关键）

```
主路径（零额外成本）  media.Server 转码 → ffmpeg.TranscodeToWAVWithScan
                      → 同一份 PCM 喂给 ffmpeg.LoudnessScanner
                      → LoudnessService.StoreMeasurement → 落盘

兜底路径（按需）      LoudnessService.Measure → 播放优先队列
                      → ffmpeg ebur128 分析（只扫描、不产生输出）
```

后端播放本来就要把整首歌转成 PCM WAV（`media.PlayableFile`），
那份 PCM 是整首歌唯一一次完整流过我们代码的机会 —— 响度测量挂在它上面，
就不必再起一个 ffmpeg 把同一个文件解码第二遍。实测（240 秒曲目）：

| 步骤                                   | 耗时      |
| -------------------------------------- | --------- |
| 改造前：`ffmpeg loudnorm` 单独测量     | 6,750 ms  |
| 改造后：`ffmpeg ebur128` 兜底测量      | 977 ms    |
| 转码成 PCM（起播本来就做）             | 193 ms    |
| **顺手扫描（额外成本）**               | **549 ms** |

即每首歌从「额外 6.7 秒」降到「额外 0.5 秒」，省掉约 92%。
兜底测量也从 `loudnorm` 换成了 `ebur128`：前者会把整条流重新编码输出，
后者只扫描。解析侧相应换成 `ffmpeg.ParseEBUR128Summary`。

**并发刻意压到 2。** 测量是后台工作，跑起来时用户往往正在听歌。
实测（8 核 16 线程）同时跑 8 个 ffmpeg 时单进程分析速度从 21.7x 实时
掉到 4.1x —— 多开的进程没换来成比例的吞吐，只是把 CPU 铺满、风扇狂转，
顺带拖慢前台播放的音效链。见 `internal/loudness/manager.go` 的
`DefaultConcurrency` / `MaxConcurrency`。

### 7.3.2 首尾静音也搭转码的便车

`ffmpeg.LoudnessScanner` 在一次解码里同时算两件事：响度，以及**首尾静音**。
静音结论随转码缓存一起留着（`media.Server.ScanSilence`）。

装载时的接线（`main.go` 的 resolve）：

```
mediaSrv.PlayableFile     → 转码（顺手扫了静音）
mediaSrv.ScanSilence      → 取那份结论
audioplay.PrimeSilenceInfo → 登记进静音缓存
  ↓ （紧接着）
PlayerService.planTrimLocked → LoadSilenceInfo 直接命中，不再扫文件
```

不接这一步也不会出错 —— `LoadSilenceInfo` 会自己扫一遍文件。
但那是**白做**：同一份数据算两次，而且这种"悄悄退回去"不会有任何报错，
所以它有一条端到端回归测试（`TestPlayerServiceUsesPrimedSilenceInfo`，
用一份与文件真实内容故意不同的预登记值来区分结论来源）。

省下的量级要说清楚（实测，10 分钟 / 100MB 的 WAV）：**约 7ms**。
扫描只读头尾各最多 60 秒（`scanChunkFrames`），**不是**整文件读取 ——
我最初按"105MB 全读"估计，实测后修正了。7ms 在切歌路径上属于
可感知但不致命的一档，而省掉它零风险。

### 7.4 纯 Go 的 BS.1770 实现（ffmpeg 体积问题的第一半）

`internal/loudness/bs1770.go` 是 EBU R128 / ITU-R BS.1770-4 的完整纯 Go 实现：
K 加权（高架 + RLB 高通两级 IIR）、400ms 块 / 100ms 步进、
绝对门限 -70 LKFS、相对门限 -10 LU、真峰值 4 相过采样、LRA（EBU Tech 3342）。

踩过的两个坑（都写在测试注释里，避免以后再犯）：

1. **K 加权在 997Hz 是 +0.691 dB，不是 0 dB。** 标准发布的系数在标定点
   恰好有 +0.691 dB 增益，由公式常数 `-0.691` 抵消。我第一版断言它应为 0 dB，
   差点把正确实现改坏；用独立的频率响应直算确认后才改正断言。
2. **门限聚合不能把已含常数的响度再当功率用。** 第一版在 `integrate` 里
   对已减过常数的块响度又做了一次 `10^(l/10)` 并再减常数，整体偏 0.691 LU。
   改为全程在功率域累加、只在最后转一次响度。

精确性：997Hz 满量程正弦 = **-3.0103 LUFS**（标准值 -3.01）。

与 ffmpeg 的交叉验证（`tools/loudcompare.go`：纯 Go 算响度、ffmpeg 只负责解码）：

| 曲目           | Go LUFS | ffmpeg | Δ    | Go 真峰值 | ffmpeg | Δ     |
| -------------- | ------- | ------ | ---- | --------- | ------ | ----- |
| 踏浪           | -11.24  | -11.29 | 0.05 | 0.14      | 0.21   | -0.07 |
| 星月神话       | -23.21  | -23.25 | 0.04 | -5.67     | -5.67  | 0.00  |
| 犯贱           | -15.18  | -15.25 | 0.07 | -0.58     | -0.60  | 0.02  |
| I Miss You     | -9.12   | -9.15  | 0.03 | 0.79      | 0.77   | 0.02  |
| Sunshine Girl  | -8.48   | -8.51  | 0.03 | 0.27      | 0.32   | -0.05 |
| 你把爱情给了谁 | -21.43  | -21.46 | 0.03 | -7.55     | -7.57  | 0.02  |

平均偏差 0.040 LU / 最大 0.066 LU，真峰值平均 0.029 dB —— 在 EBU R128 允差内。
**响度测量这一环已经可以不再依赖 ffmpeg。**

### 7.5 能不能彻底不用 ffmpeg？—— 实测结论

纯 Go 解码器（已 `go get` 验证可用）：

| 格式          | 库                               | 说明                             |
| ------------- | -------------------------------- | -------------------------------- |
| WAV           | `github.com/go-audio/wav`        | 纯 Go                            |
| FLAC          | `github.com/mewkiz/flac`         | 纯 Go                            |
| MP3           | `github.com/hajimehoshi/go-mp3`  | 纯 Go                            |
| OGG Vorbis    | `github.com/jfreymuth/oggvorbis` | 纯 Go                            |
| Opus          | `github.com/pion/opus`           | 纯 Go，已核对源码无 `import "C"` |
| **AAC / M4A** | **—— 没有可用的纯 Go 解码器**    | 见下                             |

**结论：暂时还不能去掉 ffmpeg。** 原因是 AAC/M4A 没有纯 Go 解码器，
而本机曲库 53 首**全部是 .m4a**。可选出路：

1. **Windows Media Foundation**（推荐方向）：系统自带 AAC 解码器，
   通过 COM 调用即可，不增加任何分发体积；但要写相当多的 COM 胶水代码，
   且是 Windows 专有。
2. **cgo 绑定 fdk-aac**：需要 C 工具链，且要额外分发 DLL，
   等于把「6MB 单文件」换成「若干 DLL」，收益有限。
3. ~~精简 ffmpeg 构建~~ —— **已经做了**，见 7.6。体积从 155MB 降到 6.0MB，
   但这只是把 ffmpeg 变小，并没有去掉它。

因此当前架构是：**响度算法用纯 Go，解码与转码仍交给 ffmpeg**。
等 Media Foundation 那条路走通，才能把内置 ffmpeg 彻底去掉。

### 7.6 内置 ffmpeg（精简构建，6.0MB / LGPL）

原先直接下载第三方通用静态构建：单文件 155MB、GPLv3，把产物撑到 167.6MB。
现在改为**自己按需编译**：

|               | 改前      | 改后                  |
| ------------- | --------- | --------------------- |
| ffmpeg 二进制 | 155.26 MB | **5.99 MB**           |
| 打包产物      | 167.6 MB  | **18.4 MB**           |
| 许可证        | GPLv3     | **LGPL-2.1-or-later** |

之后又做了一步纯体积优化（2025 追加）：**嵌进 exe 的是 gzip 后的二进制**
（`ffmpeg.exe.gz`，构建脚本在编译完 exe 后顺手生成）。

|          | 原始嵌入 | gzip 嵌入   |
| -------- | -------- | ----------- |
| 内嵌件   | 5.99 MB  | **2.21 MB** |
| 打包产物 | 18.4 MB  | **16.2 MB** |

热启动不解压：缓存文件名取压缩数据的 sha256，「能否复用」比对 gzip 尾部的
解压后长度（ISIZE）；只有缓存缺失时才真的解压一次。这同时把「启动时同步解包」
从主线程移走 —— 解包现在只发生在后台 prewarm 里（见 `internal/ffmpeg` 与
`main.go` 的 ffmpeg prewarm goroutine）。

许可证能变成 LGPL 是因为编译时没有 `--enable-gpl`/`--enable-nonfree`，
而需要的 AAC 解码器与 `loudnorm` 滤镜本身都属于 LGPL 部分。

**能力清单是唯一事实来源**，写在 `build/ffmpeg/features.env`：
`build/ffmpeg/build-minimal.sh` 照它生成 configure 参数，
`node tools/build-ffmpeg.mjs --info` 照它逐项核对实际产物是否真的编进去了。
这份产物的编译过程本身也能验证这个机制 —— 清单里写 `dts` 时核对报错，
查出来 ffmpeg 里 DTS 解码器的真名是 `dca`，改对后才编进去。

编进去的能力：26 个音频解码器（aac/alac/ac3/eac3/dca/mp3/flac/vorbis/opus/
wmav1-2/wmapro/ape/dsd__/wavpack/pcm__）、`loudnorm` 等 18 个滤镜、
pcm_s16le 与 flac 编码器、裸 PCM/wav/flac/null 封装、file/pipe 协议。
明确关掉：所有视频编解码器、全部硬件加速、网络、字幕、设备输入输出、
以及所有第三方外部库。

- `internal/ffmpeg/embed_production.go`（`//go:build production`）用 `go:embed`
  把 `bin/ffmpeg.exe` 编进 exe；`embed_dev.go`（`!production`）返回空，
  所以 `go test` 与开发构建不受影响。
- 运行时按 sha256 前 8 字节命名解包到 `%LOCALAPPDATA%\LocalMusicPlayer\bin\`，
  内容不变就复用。可用 `LMPLAYER_FFMPEG_DIR` 改位置。
- 解析优先级：`LMPLAYER_FFMPEG` 环境变量 → 内置 → 系统安装。
- 编译：`node tools/build-ffmpeg.mjs`（或 `wails3 task ffmpeg:build`）。
  **二进制与源码都不入库。** 需要 MinGW-w64（gcc/nasm/mingw32-make）+
  一个 bash（Git for Windows 自带），工具链位置可用 `MP_MINGW_BIN`/`MP_BASH` 覆盖。
- 许可证说明在 `internal/ffmpeg/bin/FFMPEG-LICENSE.txt`（含完整组件清单）。

#### 两条必须记住的 ffmpeg 参数约定

精简构建关掉了所有视频编码器与大多数音频编码器，于是两个以前"能跑就行"的
参数变成了硬要求：

1. **`-vn -map 0:a` 不能省。** m4a/mp4 里常内嵌封面（视频流），
   不禁掉 ffmpeg 会去给它选视频编码器，报 `Error selecting an encoder`。
   响度测量、`Probe`、`SoundDurationMS`、转码四处都加了。
2. **`-c:a pcm_s16le` 不能省。** `-f null` 仍然需要一个音频编码器，
   而精简构建只保留了 pcm_s16le 与 flac。

另外转码不再让 ffmpeg 直接输出 `.wav`，而是 `-f s16le` 输出**裸 PCM**、
由 Go 侧写 44 字节 WAV 头（`ffmpeg.TranscodeToWAV`）。原因：ffmpeg 的 wav
复用器会插入 `LIST/INFO` 元数据块，把 `data` 块从偏移 40 挪到 70，
于是"文件头长度固定 44 字节"这个假设失效，媒体服务算 `Content-Length`
与做 Range seek 的偏移就全错了。自己写头可以让
「头 = 44 字节、data 长度 = 文件大小 − 44」成为硬保证，并有测试守着。

### 7.5 无时长文件的兜底探测

`meta` 包只手写了 mp3/flac/wav/m4a 的时长解析，wma/ape/dsf/ogg 会得到 0。
因此 `library` 在扫描后会用一个**有界**的补充阶段（单次最多 48 个、并发 2）
调用 ffmpeg 探测这些文件，结果写回元数据缓存（带 `probed` 标记，
避免每次重扫都重复起进程）。时长补上后转码缓存才能算出准确长度。

## 6. 两个踩过的坑（改代码前务必知道）

1. **`StableID` 必须按 UTF-16 码元计算**
   JS 的 `charCodeAt` 按 UTF-16 取值，中文占 2 个码元。Go 若直接遍历 UTF-8 字节，
   同一路径会算出不同 id。实现里用 `utf16.Encode`，并有测试守着。

2. **`fsnotify` 不递归**
   必须对每个子目录分别 `Add`，并在 `Create` 事件里判断是否是目录、递归补登记，
   否则新建子文件夹里的歌永远不会被扫到。

## 7. 播放链路与响度均衡

### 7.1 音频必须与页面同源（踩过的坑）

打包后前端跑在 Wails 的虚拟主机 `http://wails.localhost`。
最初把音频放在另开的 `http://127.0.0.1:<随机端口>` 上，结果真实应用里
**完全无法播放**，`<audio>` 报：

```
MEDIA_ELEMENT_ERROR: Media load rejected by URL safety check
```

关键事实（用 `tools/netprobe.mjs` 接 CDP 看到）：

- 这是 Chromium 的私有网络/地址空间保护，**请求根本不会发出**——
  CDP 的 Network 域里看不到任何指向音频地址的事件，`fetch` / `XHR` 同样失败；
- 它在**无头 Edge 里复现不出来**（同样的页面源 + 同样的音频地址全部通过），
  所以只靠外部无头浏览器测试会漏掉这个致命问题；
- 加 CORS 头、加 `crossOrigin` 都没用，因为问题出在发起请求之前。

解法：把音频挂到 **Wails 自己的 asset server** 上，走同源路径
`http://wails.localhost/audio/<songID>?t=<token>`：

```go
Assets: application.AssetOptions{
    Handler: application.AssetFileServerFS(assets),
    Middleware: func(next http.Handler) http.Handler {
        audio := mediaSrv.Handler()
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            if strings.HasPrefix(r.URL.Path, media.AudioPrefix) {
                audio.ServeHTTP(w, r)
                return
            }
            next.ServeHTTP(w, r)
        })
    },
},
```

同源之后，CORS、`crossorigin`、Web Audio 的跨源取数限制全部消失
（这些代码保留着，因为独立端口模式仍可能被外部工具跨源访问）。
`MediaService.URL()` 返回的是**相对路径** `/audio/...`，不是绝对地址。

### 7.2 转码为什么要落盘而不是纯流式

最初的做法是 `ffmpeg ... pipe:1` 直接流式返回。问题是：

1. 流式响应没有准确的 `Content-Length` → 浏览器拿不到时长（`duration` 为 null），进度条不可用；
2. 想支持 seek 就得给 `Content-Range`，而要给长度就得知道输出字节数，
   但容器里报的时长与**实际可解码**时长并不相等（实测一首 3 秒的 m4a 差 47ms，
   声明的长度比实际多 44 字节）—— 于是浏览器一直等那几十字节，
   `loadedmetadata` 永不触发，**播放直接卡死**。

现在的做法：把不能原生播放的格式一次性转成 WAV 落到
`%APPDATA%\MusicPlayer\cache\transcode\`，之后当普通文件提供，
用 `http.ServeContent` 处理 Range。好处是长度天然准确、字节级 seek 免费。
缓存按「路径+大小+修改时间」键控，带 600MB LRU 上限，
并发请求用 single-flight 合并（同一首歌只转码一次）。

> 另一个容易踩的 Go 细节：`ResponseWriter` 在第一次 `Write` 时会隐式发出 200，
> 之后再调 `WriteHeader(206)` 会被忽略。所以必须在写任何正文（含 WAV 头）之前定状态码。

### 7.3 响度均衡的实现

```
设置 → 响度均衡
  ├── loudnessMode: off | track | album
  ├── loudnessTarget: 目标整合响度（默认 -16 LUFS）
  └── loudnessLimit: 真峰值保护
```

**按需计算，不预先扫描。** 播到哪首就算哪首：先查缓存，命中就直接套用（零延迟）；
没命中就在后台算一次，算完立刻作用到当前播放，绝不阻塞出声。

补偿：**静态线性增益**，`gain = 目标 − 实测`，再按真峰值收口：

```go
if item.TruePeak != 0 {
    if maxAllowed := -1.0 - item.TruePeak; gain > maxAllowed { gain = maxAllowed }
}
```

为什么不用 loudnorm 的动态归一化：动态模式要实时重采样整条流，
既无法用于原生格式（不想为了调音量就转码），也会压缩音乐本身的动态对比。
静态增益是个恒定 dB，前端 `GainNode` 实时套用即可，切歌零延迟。

回放链路：`<audio>` → `createMediaElementSource` → `GainNode` →
`destination`。元素自身 `volume` 固定为 1，用户音量与响度补偿都在
GainNode 上相乘，避免两处相乘导致音量阶跃。

**缓存有效性 = 文件未变 && 算法版本未变 && 补偿标准未变。**

这条规则是「改了目标响度后旧补偿自动失效」的实现方式。
`Measurement` 里存了 `Target` / `Algo` / `Gain`：

| 字段 | 作用 |
| --- | --- |
| `Target` | 生成这条记录时用的目标响度；与当前标准不一致即视为过期 |
| `Algo` | 测量算法版本（`AlgoVersion`）；算法改了旧结果自动作废 |
| `Gain` | 当时算出的补偿，缓存下来供回放零延迟套用 |
| `Measured` | 区分「测过但拿不到数据」与「没测过」 |

设置界面改标准时调 `InvalidateTarget(target)` 主动清掉不匹配的记录，
前端同时清空增益表。`State()` 按**当前标准**统计已测量数，
不会把其他标准下的旧记录算进去（否则界面会撒谎）。
`loudness-cache.json` 里的记录**只包含 LUFS 与真峰值**等固有量 ——
这些与目标响度无关，但按标准整体作废，实现简单且不会误用。

批量测量（界面上的「预先把全部歌曲算好」）只是可选预热，正常使用不需要。

### 7.4 纯 Go 的 BS.1770 实现（ffmpeg 体积问题的第一半）

`internal/loudness/bs1770.go` 是 EBU R128 / ITU-R BS.1770-4 的完整纯 Go 实现：
K 加权（高架 + RLB 高通两级 IIR）、400ms 块 / 100ms 步进、
绝对门限 -70 LKFS、相对门限 -10 LU、真峰值 4 相过采样、LRA（EBU Tech 3342）。

踩过的两个坑（都写在测试注释里，避免以后再犯）：

1. **K 加权在 997Hz 是 +0.691 dB，不是 0 dB。** 标准发布的系数在标定点
   恰好有 +0.691 dB 增益，由公式常数 `-0.691` 抵消。我第一版断言它应为 0 dB，
   差点把正确实现改坏；用独立的频率响应直算确认后才改正断言。
2. **门限聚合不能把已含常数的响度再当功率用。** 第一版在 `integrate` 里
   对已减过常数的块响度又做了一次 `10^(l/10)` 并再减常数，整体偏 0.691 LU。
   改为全程在功率域累加、只在最后转一次响度。

精确性：997Hz 满量程正弦 = **-3.0103 LUFS**（标准值 -3.01）。

与 ffmpeg 的交叉验证（`tools/loudcompare.go`：纯 Go 算响度、ffmpeg 只负责解码）：

| 曲目 | Go LUFS | ffmpeg | Δ | Go 真峰值 | ffmpeg | Δ |
| --- | --- | --- | --- | --- | --- | --- |
| 踏浪 | -11.24 | -11.29 | 0.05 | 0.14 | 0.21 | -0.07 |
| 星月神话 | -23.21 | -23.25 | 0.04 | -5.67 | -5.67 | 0.00 |
| 犯贱 | -15.18 | -15.25 | 0.07 | -0.58 | -0.60 | 0.02 |
| I Miss You | -9.12 | -9.15 | 0.03 | 0.79 | 0.77 | 0.02 |
| Sunshine Girl | -8.48 | -8.51 | 0.03 | 0.27 | 0.32 | -0.05 |
| 你把爱情给了谁 | -21.43 | -21.46 | 0.03 | -7.55 | -7.57 | 0.02 |

平均偏差 0.040 LU / 最大 0.066 LU，真峰值平均 0.029 dB —— 在 EBU R128 允差内。
**响度测量这一环已经可以不再依赖 ffmpeg。**

### 7.5 能不能彻底不用 ffmpeg？—— 实测结论

纯 Go 解码器（已 `go get` 验证可用）：

| 格式 | 库 | 说明 |
| --- | --- | --- |
| WAV | `github.com/go-audio/wav` | 纯 Go |
| FLAC | `github.com/mewkiz/flac` | 纯 Go |
| MP3 | `github.com/hajimehoshi/go-mp3` | 纯 Go |
| OGG Vorbis | `github.com/jfreymuth/oggvorbis` | 纯 Go |
| Opus | `github.com/pion/opus` | 纯 Go，已核对源码无 `import "C"` |
| **AAC / M4A** | **—— 没有可用的纯 Go 解码器** | 见下 |

**结论：暂时还不能去掉 ffmpeg。** 原因是 AAC/M4A 没有纯 Go 解码器，
而本机曲库 53 首**全部是 .m4a**。可选出路：

1. **Windows Media Foundation**（推荐方向）：系统自带 AAC 解码器，
   通过 COM 调用即可，不增加任何分发体积；但要写相当多的 COM 胶水代码，
   且是 Windows 专有。
2. **cgo 绑定 fdk-aac**：需要 C 工具链，且要额外分发 DLL，
   等于把「155MB 单文件」换成「若干 DLL」，收益有限。
3. **精简 ffmpeg 构建**：只留 loudnorm 滤镜 + pcm_s16le 编码器 + wav 复用器
   + 需要的解码器，理论上可显著小于当前 155MB 的通用静态构建，
   但需要自己搭交叉编译环境。

因此当前架构是：**响度算法用纯 Go，解码与转码仍交给 ffmpeg**。
等 Media Foundation 那条路走通，才能把内置 ffmpeg 彻底去掉。

### 7.6 内置 ffmpeg

- `internal/ffmpeg/embed_production.go`（`//go:build production`）用 `go:embed`
  把 `bin/ffmpeg.exe` 编进 exe；`embed_dev.go`（`!production`）返回空，
  所以 `go test` 与开发构建不受 155MB 影响。
- 运行时按 sha256 前 8 字节命名解包到 `%LOCALAPPDATA%\MusicPlayer\bin\`，
  内容不变就复用，避免每次启动重写 155MB。可用 `MUSICPLAYER_FFMPEG_DIR` 改位置。
- 解析优先级：`MUSICPLAYER_FFMPEG` 环境变量 → 内置 → 系统安装。
- 下载：`node tools/fetch-ffmpeg.mjs`（或 `wails3 task ffmpeg:fetch`）。**二进制不入库。**
- 内置的是 GPL 构建版，许可证在 `internal/ffmpeg/bin/FFMPEG-LICENSE.txt`。

### 7.5 无时长文件的兜底探测

`meta` 包只手写了 mp3/flac/wav/m4a 的时长解析，wma/ape/dsf/ogg 会得到 0。
因此 `library` 在扫描后会用一个**有界**的补充阶段（单次最多 48 个、并发 2）
调用 ffmpeg 探测这些文件，结果写回元数据缓存（带 `probed` 标记，
避免每次重扫都重复起进程）。时长补上后转码缓存才能算出准确长度。

## 1. S1 级：会造成数据损坏或功能静默失效

### S1-1 【明确失效】`resetDesktopLyricsPosition` 桥接层漏接线，「重置桌面歌词位置」100% 失败

| 层             | 位置                                                                                                | 状态                |
| -------------- | --------------------------------------------------------------------------------------------------- | ------------------- |
| Go 服务实现    | `desktop_lyrics.go:224-229` `ResetDesktopLyricsPosition()`                                          | ✅ 存在             |
| Wails 生成绑定 | `frontend/bindings/musicplayer/windowservice.js:189` `export function ResetDesktopLyricsPosition()` | ✅ 已生成           |
| 桥接封装       | `frontend/src/js/bridge.js:159-329` 的 `backend` 对象                                               | ❌ **没有这个方法** |
| 调用方         | `frontend/src/js/settings.js:742` `await backend.resetDesktopLyricsPosition()`                      | ❌ 抛 `TypeError`   |

`settings.js:748-750` 的 `catch` 把 `TypeError` 当成业务失败处理，所以用户看到的是
**「重置失败：backend.resetDesktopLyricsPosition is not a function」**——一个纯粹因为漏了一行导出而永远失败的功能。

已构建产物里同样是坏的（`frontend/dist/assets/index-CNit4GSQ.js` 内仍是 `y.resetDesktopLyricsPosition()`），说明它**已经发布出去了**。

**修法**（`bridge.js` 窗口段，与相邻的 `desktopLyricsState` 并列）：

```js
desktopLyricsResetPos: () => call(bindings?.Window?.ResetDesktopLyricsPosition),
```

**这类问题的根因值得一并处理**：`bridge.js` 是一个**手写的字符串键名映射**，
而绑定的方法名是自动生成的——两者之间没有任何编译期或测试期校验。
建议加一个启动自检（把 `backend` 的每个 key 与 `mod.*Service` 的方法名比对，缺一个就 `console.error`），
或加一条单测遍历所有 `backend.*` 键断言其在绑定模块里存在。

### S1-2 【S1】`loudness.Save()` 在解锁后序列化共享 map → Go 运行时致命错误

`internal/loudness/loudness.go:212-234`

```go
m.mu.Lock()
if !m.dirty { m.mu.Unlock(); return nil }
cf := cacheFile{Version: cacheVersion, Entries: m.items, Albums: m.albums}  // ← 只是复制了 map 的引用（header）
m.dirty = false
m.mu.Unlock()

raw, err := json.Marshal(cf)   // ← 在这里遍历 m.items / m.albums，但没有锁
```

Go 里 `map` 是引用类型，`cf.Entries` 与 `m.items` 指向**同一个哈希表**。
`json.Marshal` 会遍历它，而下面这些路径会在锁内写它：

- `loudness.go:430` `measureUncached` → `m.items[keyFor(...)] = res`
- `loudness.go:527` `UpdateAlbum` → 写 `m.albums`
- `loudness.go:324` `InvalidateTarget` → `delete(m.items, ...)`

并发「map 迭代 + 写入」在 Go 中**不是**可以被 `-race` 温和报告的普通数据竞争，
而是运行时直接抛 `fatal error: concurrent map iteration and map write`——**进程崩溃，无法 recover**。

触发条件很现实：`MeasureAll`（`loudness.go:507` 会调 `Save`）与按需测量（`Measure`，播放时触发）
同时发生即可。`go test -race ./...` 全绿并不能排除它——现有测试没有构造这个交错。

**修法**（锁内做浅拷贝）：

```go
m.mu.Lock()
if !m.dirty { m.mu.Unlock(); return nil }
items := make(map[string]Measurement, len(m.items))
for k, v := range m.items { items[k] = v }
albums := make(map[string]Album, len(m.albums))
for k, v := range m.albums { albums[k] = v }
m.dirty = false
m.mu.Unlock()
raw, err := json.Marshal(cacheFile{Version: cacheVersion, Entries: items, Albums: albums})
```

> **同一个模式在 `internal/library/library.go:243-247` 也存在**（`cf.Entries = m.cache`，
> `RUnlock` 之后才 `json.Marshal`）。它目前靠「扫描被 `beginScan/endScan` 串行化」侥幸避开，
> 但一旦将来有人从别处调 `SaveCache`（例如「退出时保存」与「扫描结束保存」重叠）就会踩到同一个坑。
> **建议两处一起修，并把这个「锁内建新 map 再序列化」写成一个共用小工具。**

### S1-3 【S1】索引加载失败被静默当空，随后覆盖写回 → 缓存条目永久成为孤儿

`internal/metacache/store.go:754-761`

```go
func (s *Store) ensureLoadedLocked() {
	if s.loaded { return }
	s.loaded = true                      // ← 先置位
	_ = s.loadIndexLocked(KindCover)     // ← 错误被丢弃
	_ = s.loadIndexLocked(KindLyrics)
}
```

两个问题叠加：

1. `s.loaded = true` 在**加载之前**设置——加载失败后也再不会重试。
2. 两个返回值都用 `_` 丢弃——`os.ReadFile` 失败、JSON 截断、版本不符，全部等同于「空索引」。

而 `saveIndexLocked`（`store.go:822-855`）会把内存里的（空）map 当权威写回磁盘。
于是 `covers/index.json` 一旦损坏：**磁盘上的图片文件都还在，但索引被清空并覆盖，
用户看到的是「封面缓存全没了」**——而 `store.go:841-843` 的注释恰恰写着他们做临时文件 + rename
就是为了防这个场景。原子写只防了「写到一半崩溃」，没防「读到坏数据后覆盖」。

**修法**：`loadIndexLocked` 出错时**不要**置 `loaded`，并让调用方拿到错误；
若 JSON 解析失败，把坏文件改名备份（`index.json.corrupt-<ts>`）而不是静默当空——
至少让用户/日志知道发生过什么。

## 2. S2 级：明确的正确性与安全问题

### S2-1 【S2·安全】封面代理的 `CheckRedirect` 不复用白名单 → SSRF

`internal/coverfetch/http.go:33-46`

```go
var client = &http.Client{
	Timeout: 15 * time.Second,
	CheckRedirect: func(req *http.Request, via []*http.Request) error {
		if len(via) >= 6 {
			return fmt.Errorf("重定向次数过多")
		}
		if len(via) > 0 {
			req.Header.Set("User-Agent", UserAgent)
			req.Header.Set("Referer", via[0].URL.Scheme+"://"+via[0].URL.Host+"/")
		}
		return nil        // ← 没有对 req.URL 做 AllowedImageURL 校验
	},
}
```

`Download`（`http.go:158` 附近）只校验**初始 URL**。白名单里包含 `y.qq.com`、`deezer.com`、
`archive.org`、`discogs.com`、`kugou.com` 等（`http.go:97-123`）——
其中任何一个存在开放重定向，就能把请求导到 `http://127.0.0.1:<port>/` 或内网地址，
响应体还会被原样返回（`http.go:186`）。虽然服务只在本机跑，但封面下载的 URL 部分来自
**在线搜索结果的元数据**，属于「外部输入 → 本机网络请求」的典型 SSRF 面。

**修法**：在 `CheckRedirect` 里加一行 `if !AllowedImageURL(req.URL.String()) { return err }`；
并顺带收紧白名单本身（`http.go:126-148` 目前接受 `http://` 且 `u.Hostname()` 丢掉了端口，
应强制 `https` 并拒绝显式端口）。

### S2-2 【S2·数据破坏】`ClearCache` 会删掉用户配置目录下的**所有** `.wav`

`internal/media/server.go:486-508`

```go
dir := s.getCacheDir()
...
for _, e := range entries {
	if e.IsDir() || !strings.HasSuffix(e.Name(), ".wav") {
		continue
	}
	_ = os.Remove(filepath.Join(dir, e.Name()))
}
```

`cacheDir` 来自用户配置并且**会展示在设置界面里**（`server.go:562` 的 `ToolsInfo` 返回 `cacheDir`）。
如果用户把它指到一个音乐目录（界面上这是完全可做的操作），
「清空转码缓存」就会删掉该目录下所有无关的 WAV 文件——**不可恢复的数据丢失**。

**修法**：只删由本服务生成的产物。转码文件名是 `bootstrap.StableID(key, "tc") + ".wav"`（`server.go:370`），
所以完全可以按前缀 + 长度校验（StableID 的格式是确定的），或维护一份已知文件清单/只删缓存子目录。

### S2-3 【S2】`walkFolder` 把非权限类遍历错误当作「成功」

`internal/library/library.go:853-858`

```go
if err != nil {
	if os.IsPermission(err) {
		return out, "denied"
	}
	return out, "ok"      // ← 磁盘 I/O 错误 / 路径过长 / 网络盘断开，一律报 success
}
```

后果：曲库**被静默截断**，前端收到 `scan:done`，用户看到「扫描完成」但少了一批歌，
而且 `status` 是 `ok` 所以界面上没有任何提示。排查这类问题极其困难。

**修法**：返回 `"error"` 状态（`Folder.Status` 已经是字符串枚举，前端加一个分支即可），
并至少 `log.Printf` 一次。

### S2-4 【S2】`isUnder` 用 `strings.HasPrefix(rel, "..")` 判断，误判以 `..` 开头的子目录

`internal/library/library.go:863-872`

```go
rel, err := filepath.Rel(root, path)
...
return !strings.HasPrefix(rel, "..")
```

`filepath.Rel("C:/Music", "C:/Music/..hidden/a.mp3")` 得到 `"..hidden/a.mp3"`，
它以 `..` 开头，于是**真实的子目录被判定为「不在 root 之下」**。
影响面：`TrackCount` 统计、`RescanPaths` 的「受影响目录」判定（`library.go:481-485, 500-505`）
都会漏掉这类目录——即增量重扫时它们的歌不会被正确替换。

**修法**：`return rel == "." || (rel != ".." && !strings.HasPrefix(rel, ".."+string(filepath.Separator)))`

### S2-5 【S2】前端 `notify()` 无错误隔离；`rescan()` 无 `try/finally`

`frontend/src/js/store.js:227-230`

```js
export function notify() {
  for (const fn of listeners) fn(state);
}
```

任一订阅者抛异常会**中断后续所有订阅者**，并把异常抛回调用者（可能是 `audio` 事件回调、
可能是 `requestAnimationFrame`），表现为「界面某一块从此不再更新」而且没有明确报错。
项目在别处已经做对了这件事——`playerhost.js:679-688` 对皮肤监听器逐个 `try/catch`。**照抄即可**。

`frontend/src/js/store.js:1459-1498`：

```js
state.scanning = true;
commit();
const started = await backend.scan(...);   // ← 这里 reject 就再也走不到 scanning = false
...
state.scanning = false;
```

没有 `try/finally`，`backend.scan()` 或 `backend.songs()` 一旦 reject，
**「正在扫描」遮罩会永久挂在界面上**（用户只能重启）。

### S2-6 【S2】后端写操作即发即忘，失败后前后端状态静默分叉

`frontend/src/js/store.js:544, 561, 573, 587, 599, 612` 六处：

```js
if (isWails()) backend.toggleLike(songId); // 不 await、不 .catch
```

`store.js` 采取乐观更新（先改内存状态再调后端），但**没有任何回流机制**：
后端失败时内存状态已经是「成功」的样子，且不会被纠正。全局 `unhandledrejection`
处理器（`main.js:549-556`）会弹一条 toast，然后内存与磁盘继续不一致，
**重启后用户的改动消失**。

**修法**：至少 `.catch(err => { toast(...); /* 回滚乐观更新 */ })`；
更好的做法是把这六处收敛成一个 `mutate(optimisticFn, backendCall, rollbackFn)` 辅助函数。

### S2-7 【S2】`scan:done` 被两处独立处理 → 每次扫描拉两遍整库

`frontend/src/js/store.js:1501-1515`（`waitForScanDone`）与
`frontend/src/js/main.js:256-281` 都订阅 `scan:done`，**各自都 `await backend.songs()` 并重写 state**。
一次扫描 = 两次全量曲库 IPC + 两次过滤/排序。
（在封面走 data URL 的现状下，这两次每次都是数百 MB，见性能报告 P0-1。）

**修法**：只保留一处（让 `rescan()` 复用 `main.js` 的处理结果，或反过来），
并用一个 `scanVersion` 序号防重入。

### S2-8 【S2】`MP3Probe` 参数与注释不符 / `SoundDurationMS` 的目标未达成

- `internal/ffmpeg/ffmpeg.go:347-353` 的注释明确写着「加上 `-t 0` 可以在多数情况下提前结束」，
  但 `ffmpeg.go:377-383` 的 `Probe` 参数里**没有 `-t 0`**（对比 `ffmpeg.go:420` 的 `SoundDurationMS` 有）。
- `ffmpeg.go:403-410` 的注释说该函数是为了拿到「解码样本数换算出的真实时长」，
  但 `-t 0` 意味着不解码，`ParseDuration` 只能读到容器的 `Duration:` 行——
  **注释描述的行为与实现相反**。

两处都是「注释与代码不一致」，而注释本身写得很自信，最容易误导后续维护者。

### S3-2 结构性「重复实现同一件事」——其中一处已漏改

审查中反复出现同一个模式：**正确写法在 A 处，B 处漏改**。

| 逻辑                      | 正确实现                                                          | 漏改处                                                                                             | 后果                          |
| ------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------- |
| 「移除的曲目数」集合差    | `store.js:1484-1486` 用 `Set`                                     | `main.js:271` 用 `filter + some`                                                                   | O(n²)（性能报告 P0-4）        |
| JSON 落盘缩进             | `services.go` 多数字典用 `json.Marshal`                           | `library.go:247`、`config.go:778`、`metacache/store.go:834` 用 `MarshalIndent`                     | 每次重写数 MB 的多余 CPU      |
| 锁内复制 map 再序列化     | 无（两处都是错的）                                                | `loudness.go:218`、`library.go:244`                                                                | 并发崩溃（S1-2）              |
| 原子写 + `Sync()`         | `metacache/embed.go:654-680` `writeFileAtomic`（有 `tmp.Sync()`） | `metacache/store.go:845-853`、`:631-639`、`library.go:251-255`、`config.go:786-801` 都没有 `fsync` | 断电可能留下空/截断文件       |
| 相似度 / LCS / 文本归一化 | `coverfetch/itunes.go:251-298`                                    | `lyricsfetch/types.go:389-453`、`coverfetch/deezer.go:209-236` 各写一份                            | 三份 O(n·m) DP 实现需同步维护 |

**注意最后一行**：`writeFileAtomic` 已经是「对的」那份实现，但**另外四处都没用它**。
这是一个非常低成本的统一机会。

**另一类重复：皮肤包的公共辅助函数被复制了 6 份。**
`frontend/packages/player-skins/src/skins/` 下 6 个皮肤各自定义了一份**逐字节相同**的
`emptyTextFor`（`classic.js:130`、`minimal.js:87`、`immersive.js:108`、
`anime.js:384`、`arcade.js:446`、`magia.js:1113`）：

```js
function emptyTextFor(lyrics) {
  if (lyrics?.source === "online") return "在线匹配没有结果";
  return "暂无歌词";
}
```

每个皮肤还各写了 3~4 处同一段调用样板
（`lyrics.setLines(m.lyrics.lines, { emptyText: emptyTextFor(m.lyrics) })`）。
`magia.js` 另外自己实现了 `clamp` / `mulberry32` / `hashStr` / `jitter` /
`parseCssColor` / `parseRgb` / `splitUnits` / `toPath` 等**与「魔法阵」这个皮肤主题无关**的通用小工具
（39 个函数集中在一个 1358 行的文件里）。

皮肤包是给第三方作者参照的模板，因此这里的重复有真实的传染性——
新作者会照着现有皮肤再抄一份。建议在 `player-skins` 里提供一个
`src/lib/lyrics.js` / `src/lib/math.js` 供各皮肤 import（`defineSkin` 已经是共享入口，
说明这个包本来就有共享基础设施的位置）。

### S3-3 绑定层/桥接层无契约校验（S1-1 的根因）

`bridge.js` 用字符串键名手写映射（`backend.songs` → `bindings.Library.Songs`），
而绑定的方法名由 `wails3 generate bindings` 生成。**两者之间没有任何自动校验**：
Go 侧改名、新增、删除方法，前端都不会在构建期报错，只会在用户点击时静默失败。

**修法**（任选其一，成本都很低）：

1. 在 `connect()` 成功后遍历绑定模块，把所有 `*Service` 的方法名收集成集合，
   再遍历 `backend` 的每个 key 断言之存在，缺失就 `console.error` 汇总一次。
2. 加一个 Node 测试：`import` 绑定模块与 `bridge.js`，对每个 backend 方法做存在性断言。

> 现状下这类「静默失效」的暴露方式是用户在设置里点一下、看到「失败」——
> 而**没有任何测试或构建步骤会提前发现它**。

### S3-5 并发状态机里的隐性缺陷（响度模块）

`internal/loudness/loudness.go:475-505` `MeasureAll`：


## 5. 值得明确保留的优点（不要在这些地方「重构」）

审查中反复确认了一批**质量显著高于平均水平**的实现，建议在后续改动中刻意保护：

1. **注释解释「为什么」，并附上历史失败案例**。例如 `library.go:37-40` 记录了
   「早先用未导出小写字段，`encoding/json` 把每条序列化成 `{}`，缓存从未生效」；
   `library.go:370-375` 记录了「取消时返回空切片导致整个曲库被清空」。
   这类注释是真正的资产。

2. **边界处的防御很扎实**：所有出站 HTTP 响应体都有 `io.LimitReader`
   （`coverfetch` 4MB/2MB、`lyricsfetch` 12MB、`bilibili` 16MB）且都 `Close`；
   `media/server.go` 只监听 `127.0.0.1` + 随机端口 + 每次启动随机 token，且
   `id → song` 强制走曲库注册表，未发现路径穿越。

3. **媒体服务正确委托给 `http.ServeContent`**（`server.go:316-347`），
   Range / If-Range / 206 / 416 / HEAD 全部交给 `net/http`，**没有**把音频整文件读进内存——
   这是很多人会写错的地方。

4. **取消语义被认真对待**：`library.readAll`（`library.go:553-617`）返回
   `(songs, cancelled)` 二元组并**明确拒绝**用残缺结果覆盖曲库，
   `library.go:370-376, 489-493` 两处都据此提前返回。

5. **前端渲染键的设计有据可依**：`store.js:449-484` 用 FNV-1a 指纹而不是拼接 ID 串，
   注释里解释了「1000 首每次 commit 会产出几十 KB 垃圾」以及「为什么不能用自增计数器」。
   实测切歌只产生 52 个 DOM 变动，证明这套设计是有效的。

6. **防白闪/首帧的工程化很细**（`main.go:286-309`、`boot_frame.go`、`early_theme.go`）：
   窗口隐藏创建 → DWM 遮罩 → 前端 `/boot/reveal` 走普通 HTTP 而不是 Wails 绑定
   （注释里给出了「实测能晚到近一秒」的依据）。这类决策通常不会被写下来，这里写了。

7. **`preloadSkins` 用 `void` 明确表示「不 await，不拖首屏」**，
   并且读代码能确认它确实没被 await（`main.js:468-470`）——
   前端对「关键路径」的取舍是有意识的。

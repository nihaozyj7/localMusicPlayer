## 2. 拆分的判据（先立规矩，免得越拆越乱）

1. **判据是「能不能被单独测试」，不是行数。** 一个 2000 行的纯脊线表（`effects.go` 的 DSP 系数）不需要拆；
   一个 600 行的函数如果每个分支都伸手去改模块级可变状态，就必须拆。
2. **只在同一文件里存在两个以上「不共享可变状态」的职责时拆。** 共享 `state` 的部分留在 `store.js`。
3. **对外导出面不许变。** `store.js` 有 82 个导出、`settings.js` 有 15 个，`ui/` 组件与 `tools/*.mjs` 自检脚本都按名字调用；
   拆分的产物只能是**新的内部模块**，导出的名字、参数、语义一个都不动。
4. **一次只拆一个职责**，拆完立刻 `npm run check` + `npm run build`（`frontend/dist` 入库，
   `dist` 里资源哈希变化属于预期噪音）。
5. **移动代码时，按源码文本找东西的守卫会失败，这是好事** —— 它拦的正是「搬家时漏了一个键」。
   要同步改的是守卫里的**路径**，不是放宽断言。

## 3. 第一批 A：`store.js` 的持久化与配置同步

### 3.1 现状事实

| 位置 | 内容 | 备注 |
| :--- | :--- | :--- |
| L2251 / L2259 | `persist()` / `persistNow()` | 对外导出（`commit()`、`beforeunload` 调它） |
| L2267 | `writeSnapshot()` | 读 `state` 的 12 个字段，`localStorage.setItem(LS_KEY, …)` |
| L2300 起 | `SYNCED_KEYS` | 400ms 去抖推给后端 `applyPatch` |
| L2385 | `flushConfigSync()` | 关窗/显式保存前 flush |
| L2532 / L2626 / L2654 | `hydrateFromBackend()` / `bootstrap()` / `rescan()` | 装载路径，**本次不动** |

### 3.2 拆法（依赖注入 + 纯函数内核，与仓库既有写法一致）

| 新模块 | 内容 | 为什么这样切 |
| :--- | :--- | :--- |
| `frontend/src/js/store-snapshot.js` | `snapshotOf(state)`（纯函数，返回要落盘的对象）+ `pruneProgress(progress)` | 不 import `store.js`，`state` 当参数传进来 → 可以直接跑 `node:test`；`rememberVolume` 开关、progress 剪枝这类分支从此有测试 |
| `frontend/src/js/store-config-sync.js` | 去抖调度 + `flush()`，签名 `createConfigSync({ read, push, keys, delay })`；**`SYNCED_KEYS` 留在 `store.js`**（理由见 §3.3 的守卫清单） | 「怎么同步」与「哪些键要同步」解耦；`push` 注入后单测能用一个假后端断言「只推白名单键」 |
| `store.js`（保留） | `state`、`commit()`、`persist()` / `persistNow()` 三个薄封装；对外导出名全部不变 | 调用方（`ui/`、`runtime.js`）一行都不用改 |

**不许做的**：把 `state` 本身搬出去。`state` 是单一真源（`AGENTS.md` §6 第 3 条），
一搬就会引出「两份当前值」，那类故障（设置了不生效、切歌丢进度）正是本仓库历史上踩过的坑。

### 3.3 验收

- 新增 `frontend/tests/store-snapshot.test.js`：① 快照只含约定字段；② `rememberVolume === false` 时**没有** `volume`/`muted`；
  ③ `progress` 剪枝；④ `filterRules` 原样带出（它同时是 `SYNCED_KEYS` 的争议点，见审查登记项）。
- 已有的跨进程配置守卫必须保持绿：`config_service_test.go`（Go 侧读盘验证）以及一批**按源码文本**找键的前端用例 ——
  实测有 **15 个** `frontend/tests/*.test.js` 会去读 `frontend/src/js/store.js` 的源码
  （`playlist-id` / `player-options` / `ai-base-url-hint` / `filter-parity` / `fresh-download` / `hydrate-resilience` /
  `legal-notice` / `scan-wait` / `seek-must-reach-audio` / `settings-effect` / `skip-silence` / `sort` /
  `store-pure` / `update` / `no-dead-events`），其中 **3 个**直接断言 `const SYNCED_KEYS = [ … ]` 里有没有某个键
  （`skip-silence`、`player-options`、`legal-notice`）。
  **结论：`SYNCED_KEYS` 这份清单留在 `store.js` 里（作为唯一的「键白名单」出口），只把「去抖与推送机制」搬进
  `store-config-sync.js`。** 反过来做的话要改这一批用例的路径 —— 那等于把守卫的注意力从「键漏没漏」引开。
- 手工回归（浏览器预览即可，`npm run dev:static`）：改音量 → 刷新 → 音量还在；改主题 → 刷新 → 主题还在。
- 风险：**中**。`writeSnapshot` 是唯一落盘路径，改完要真跑一次上面的手工回归，不能只看测试绿。

## 4. 第一批 B：`settings.js` 的动作分派表

### 4.1 现状事实

- `handleSettingsAction`：**L806–L1448，643 行**，入口是 `const act = actEl.dataset.act;`（L807）+
  一个 `switch (act)` 长链，把「设置层里所有非控件动作」全串在一起（实测 **47 个 `case` 标签**）。
- 触发点有两类：`ui/settings-view.js` 里的 `data-act="…"` 元素（全前端实测 **97 处** `data-act=`），
  以及 `ui/content.js:380` 那种**空状态委托**——它传的是一个合成的假元素
  （`handleSettingsAction({ dataset: { act: "add-folder" } })`），已经有 `empty-state-delegation.test.js` 守着。
- `handleSettingControl`：L1810–L1914（开关 / 分段 / 滑杆的通用处理；本次清理删掉了其中不可达的 `effectPreset` 分支）。
- 调用方：`ui/settings-view.js:2194` 与 `:2209`（以及上面那处空状态委托）。

### 4.2 拆法

1. 先把 `switch` 变成**动作表**：`const ACTIONS = { "about-open-url": handler, ... }`，
   骨架只留「取 `act` / `id` → 查表 → 调 handler → 统一错误提示 → 未知名动作用 warn 报出来」。
   ★ 未知动作**必须留痕**：现在的 `switch` 落到末尾是静默什么都不做，
   而 `data-act` 拼错时的表现就是「点了没反应」，这正是要顺手消掉的一类故障。
2. 再按分区把表与 handler 分到**平铺命名的兄弟文件**（`ui/` 是仓库里唯一的子目录，不为这次拆分新开子目录）：
   `settings-actions-lyrics.js` / `settings-actions-appearance.js` / `settings-actions-data.js` /
   `settings-actions-online.js` / `settings-actions-ai.js`；`settings.js` 只保留装配与共享工具。
3. 导出面不变：`handleSettingsAction(actEl, ctx)` 仍在 `settings.js` 上。

### 4.3 验收

- 新增守卫 `frontend/tests/settings-actions.test.js`：**双向**比对 ——
  ① `ui/*.js` 里出现的每个 `data-act="X"` 都要在动作表里有 handler；
  ② 动作表里每个键都要有对应的 `data-act="X"`（或给出理由，例如空状态委托与程序化调用）。
  这条守卫才是拆分的收益：以前漏接一个分支是静默无反应，现在是红。
- 手测 3 个动作（挑有副作用的三类）：主题导入、下载目录迁移、AI 清洗首次确认。
- 风险：中。动作表是「按下按钮什么都不发生」的高发区，所以守卫必须先落地，再搬代码。

## 5. 第二批（后端）：`services.go` 的服务分组

- 现状 2,397 行 = 8 个绑定服务 + 主窗口/桌面歌词两套状态机。
- 拆法：**纯搬移**，按服务种类落到同名前缀文件（仓库已有先例：`services_online.go` / `services_cover.go` / `services_player.go`）。
  顺序：`ThemeService` → `ConfigService` → `MediaService` → `LoudnessService` → 最后 `WindowService`（最大、与启动序列纠缠最深）。
- 每步验收：`node tools/check-gofmt.mjs`、`go vet . ./internal/... ./tools/...`、`go test -race -count=1 .`、
  `npm run check`（绑定生成物不变，所以前端无需重建；若 `wails3 generate bindings` 输出有变则必须一起更新并说明）。
- 注意：根包里按源码文本扫描的守卫（`atomic_flags_test.go` 扫根包 `*.go`）跨文件仍然有效，
  但**别把它挪进被搬走的文件所在的包**，否则扫描范围变了会静默失效。

## 6. 明确不拆（附理由，免得后来者再议一遍）

| 目标 | 为什么不拆 |
| :--- | :--- |
| `ui/settings-view.js`（2,304） | 单个 Lit 组件类 + 模板；拆开会把 `static deps()` 与渲染边界打散，容易变成「状态更新了但没重绘」 |
| `ui/lyrics.js`（1,621） | 模板与在线探测纠缠，正确顺序是先把探测抽成纯函数（另立一项），再谈拆文件 |
| `internal/bootstrap/config.go`（1,624） | 主体是**数据**（配置字段表）；复杂度来自「键多」，拆文件只会让「三处同步」更难查 |
| `internal/audioplay/effects.go` | DSP 系数表，读得慢不等于改得危险 |
| 测试大文件（`effects_test.go` 等） | 用例按主题聚集反而好读；拆测试不产生收益 |

## 0. 结论摘要

| # | 风险 | 等级 | 一句话 |
| :--- | :--- | :--- | :--- |
| H1 | 在线试听 / 下载把第三方平台的作品复制到用户磁盘 | **高** | 核心卖点即「从平台取音乐」，且下载入口没有任何版权提示 |
| H2 | 解密 QQ 音乐 QRC / 酷狗 KRC 专有歌词格式 | **中高** | 硬编码密钥 + 3DES/XOR 解密，可能被主张为「避开技术措施」 |
| H3 | 复现 B 站 WBI 反爬签名 + 伪造 Referer/UA/设备标识 | **中高** | 合同违约明确；是否构成不正当竞争取决于规模与商业化 |
| M1 | 歌词与封面本身是受保护作品，被复制并写回用户文件 | 中 | 个人欣赏可援引合理使用，系统性补全更接近批量复制 |
| M2 | AI 清洗把本地歌曲信息（含文件名）发往第三方 API | 中 | 默认关闭，但开启时无告知；境外 API 涉跨境提供 |
| M3 | 首次启动即默认联网，且全仓没有隐私说明 | 中 | 三个默认开的联网行为（封面 / 歌词 / 更新检查） |
| M4 | 未遵守部分上游 API 的条款（尤以 MusicBrainz 明确） | 中 | 伪装浏览器 UA、无节流、无应用标识 |
| M5 | 更新安装走第三方镜像且允许无校验和安装 | 中 | 不是版权问题，是「分发不受控二进制」的责任 |
| L1 | 对外声明漏了酷狗音乐 | 低 | `THIRD-PARTY-NOTICES.md` §5 与实际调用不一致 |
| L2 | 第三方商标的指示性使用 | 低 | 已有「无隶属/背书」声明，做法基本正确 |

**总体判断**：这是一个**技术上是「客户端」，法律上却是「内容获取工具」**的项目。
风险的主要来源不是代码写得不好，而是**能力本身**（下载 + 破解格式 + 绕反爬）与**对外披露不足**（没有版权提示、没有隐私说明）。
在「个人自用、不收费、不分发安装包给第三方」的前提下，实际被追究的概率不高；一旦**收费（含赞助换功能）、放进应用商店、
或做全库批量下载**，H1/H3 的等级会立刻上一档。

## 2. 高风险项

### H1 · 在线试听 / 下载：把第三方平台的作品复制到用户磁盘

**事实**

- 下载接口把 B 站视频的音频轨取回并写入用户音乐目录：`services_online.go:462`（`handleDownload`）→
  `services_download.go:299`（`Start`）→ `:447`（`run`）→ `:675`（`fetchTo`，临时文件 + 原子改名）。
  默认目录是 `%USERPROFILE%\Music\downloads`（`bootstrap.DefaultDownloadDir`），并**立刻自动入库**（`services_download.go:550`）。
- 试听路径会把整首音频**落盘缓存**（`services_online.go:588` `teeToCache` → `internal/onlinecache`），
  即使用户只点了「试听」，磁盘上也已经有了一份完整副本。
- 界面上「下载」按钮**没有任何提示**：`frontend/src/js/ui/search.js:295-307`（按钮）与 `:490`（`downloadOnline`）
  只有成功/失败 toast，没有版权或使用范围说明。
- 对外文案把「在线试听与下载」作为能力列出：`README.md:320-327`、`frontend/src/js/about-info.js:194-203`。

**法律依据（中国大陆）**

- 复制权与信息网络传播权：《著作权法》第 10 条第 1 款第（五）（十二）项。
- 个人使用例外：《著作权法》第 24 条第 1 款第（一）项（为个人学习、研究、欣赏而使用他人已发表作品）
  —— 这是**用户**的抗辩，不是**工具作者**的免责条款。
- 工具作者的暴露面：帮助侵权（《民法典》第 1169 条）与网络服务提供者的明知/应知标准（第 1197 条）；
  若被认定「以营利为目的」且规模、情节达到门槛，实务中存在以《刑法》第 217 条侵犯著作权罪追究
  「提供解析/下载软件者」的案例（参见 [为他人提供解析软件是否构成犯罪的分析](https://javy-lawyers.com/news/dongtai/1996833916178153473.html)）。

**缓释因素（真实存在，应在评估中计入）**

- 全程**匿名**访问，不存在会员 / 付费内容绕过：客户端只随机生成一个 `buvid3` 设备标识（`internal/bilibili/client.go:71-90`），
  没有登录态、没有 `SESSDATA`、仓库内 grep 不到任何 VIP / 付费相关分支。
- 不做服务端、不托管内容、不代替用户传播；下载是用户逐首主动触发的。
- 项目本身开源、不收费（Apache-2.0）。

**建议（P0）**

1. 「下载」按钮加**首次确认弹窗**：内容版权归原作者与平台，仅供个人学习欣赏，不得传播或商用。
2. README「免责声明」补一条同义条款（同时覆盖试听缓存也落盘这一事实）。
3. 对外描述避免「免费下载全网音乐」一类措辞；不要在搜索结果里暗示这是「音乐曲库」。

### H2 · 解密 QQ 音乐 QRC / 酷狗 KRC 专有歌词格式

**事实**

- QQ QRC：硬编码 24 字节 3DES 密钥（`internal/lyricsfetch/qq_qrc.go:34`），自实现「位序被重排过的 DES 变体」
  （`:86-256`），`qrcDecrypt` 做 hex → 3DES → zlib（`:299`）。
- 酷狗 KRC：硬编码 16 字节异或密钥（`internal/lyricsfetch/kugou.go:273`），`decodeKRC` 做 base64 → 去 `krc1` 头 → XOR → zlib（`:283`）。
- 两者都被自动匹配路径主动调用（`internal/lyricsfetch/types.go:299` `Match`，酷狗/QQ 声明了 `WordProvider`）。

**法律依据**

- 《著作权法》第 53 条第（六）项：**故意避开或者破坏技术措施**的，承担民事/行政责任。
- 争点在于 QRC/KRC 是否属于该条意义上的「技术措施」：它保护的是**歌词文本的呈现格式**，
  而非作品的访问控制 —— 接口本身匿名可取、密钥是行业公知常量（代码注释也是这个立场：
  `qq_qrc.go:33`、`kugou.go:271`）。

**缓释因素**

- 未破解任何访问控制/身份认证，只对**已经拿到手的响应体**做格式解析。
- 目的正当：为了显示逐字时间轴（互操作），不是为了复制牟利。

**建议（P1）**

1. 在两处注释与文档中明确写清「为互操作而实现、未规避访问控制」的立场（保留证据链，不要只留实现）。
2. 给上游字级来源提供一个**可关闭开关**（设置项），一旦上游主张权利可以立刻下线该来源。
3. 对外文案不出现「破解」「解锁」「提取会员歌词」一类描述。

### H3 · 复现反爬签名 + 伪造请求头

**事实**

- 复现 B 站 WBI 签名：`internal/bilibili/wbi.go:11-18`（`mixinKeyEncTab` 注释即「必须与官方 JS 实现保持完全一致」），
  在请求前追加 `wts` 与 `w_rid`（`internal/bilibili/client.go:182-217`）。
- 伪造来源与设备标识：`client.go:83-90`（Referer/Origin/浏览器 UA/自造 `buvid3` Cookie）；
  `services_online.go:510-512`、`:728-730`、`services_download.go:725-727`（音频 CDN 同样伪造 Referer/Origin/UA）。
- 歌词与封面侧同样：`internal/lyricsfetch/netease.go:89`、`:138`，`internal/lyricsfetch/kugou.go:258`，
  `internal/lyricsfetch/qq.go:77`；`internal/coverfetch/http.go:21` 全局使用桌面浏览器 UA。

**法律依据**

- 合同层面：违反各平台用户协议 / robots 约定（违约），平台可封禁、可发函要求停止。
- 竞争法层面：《反不正当竞争法》第 12 条（互联网专条）与最高法网络不正当竞争司法解释 ——
  实务中「绕过反爬措施抓取数据」是被援引的典型行为。是否构成通常取决于**规模、是否替代对方核心业务、是否营利**。
- 刑事层面：《刑法》第 285 条相关罪名的门槛较高（关键看是否**突破身份认证/访问控制**）。
  本项目只访问免登录公开接口，未突破认证，属于相对有利的事实。

**缓释因素**

- 有限流与退避：网易云命中 405 后 5 分钟退避（`netease.go:28`），封面来源有熔断（`internal/coverfetch/aggregator.go:79-82`），
  所有请求都带 ctx 超时；请求量由用户行为驱动，**没有**批量抓取/全库补全的循环。
- 上游依赖被隔离成独立包（`internal/bilibili` / `lyricsfetch` / `coverfetch`），单点下线成本很低。

**建议（P1）**

1. **不要**新增任何「批量抓取」「一键下载整个歌单/整个曲库」的功能 —— 这是把风险从中档推到高档的那一步。
2. UA 不要一律伪装成浏览器：对明确要求**应用标识**的服务单独设置 UA（见 M4）。
3. 保留并强化现有的熔断/退避；在文档里把它记录为「合规缓释措施」而不只是性能优化。

## 3. 中风险项

### M1 · 歌词与封面本身是受保护作品

- 事实：在线歌词抓取后会写进用户音频文件的标签（`services.go:829` `Save` → `:888` `metacache.EmbedLyrics`），
  并落盘到 `<cacheDir>/meta/lyrics/`；封面落进 `internal/covercache`，也可写回文件内嵌图。
- 依据：歌词是文字作品（多由音著协等集体管理），专辑封面是摄影/美术作品。
  抓取 + 本地缓存 + 写回文件都是**复制**行为；个人欣赏可援引《著作权法》第 24 条，但
  「自动为整库补全并写回」更接近系统性复制。
- 建议（P1）：关于页与设置项写明「歌词/封面来自公开曲库，仅供个人欣赏，请勿传播或商用」；
  全库批处理式的自动写回如果要加，必须逐次确认。

### M2 · AI 清洗把本地信息发给第三方 API

- 事实：请求体里带标题、歌手、专辑与**完整文件名**（`services_ai.go:164-167`；调用点
  `ai_tags.go:126`、`services.go:955`、`services_cover.go:152` 均传 `filepath.Base(path)`，**不含路径**，这点是对的）；
  歌词自动匹配路径上会**自动**触发（`services_online.go:62-71`）。
- 依据：《个人信息保护法》第 13/17 条（告知同意）、第 38–39 条（向境外提供个人信息需单独同意并告知）。
  文件名可能含个人信息（例如「张三-翻唱」）；用户填的 baseUrl 通常在境外。
- 缓释：默认关闭，必须同时填 baseUrl 与 apiKey 才启用；密钥不回传前端（`services.go:1074-1104`，有回归测试）。
- 建议（P1）：首次启用 AI 时给一次**明确确认**：会把什么字段、发往哪个地址（可能境外）、如何关闭。
  设置页文案已有一句（`frontend/src/js/ui/settings-view.js:1528`），但不含「境外 / 发送什么字段」。

### M3 · 默认联网、且全仓没有隐私说明

- 事实：`OnlineCover: true`（`internal/bootstrap/config.go:469`）、`UpdateCheckOnStart: true`（`:512`）；
  歌词自动匹配挂在**每次切歌**的路径上；启动即访问 `api.github.com`（`internal/update/checker.go:158`）。
- 依据：PIPL 第 17 条的告知义务（即便只是 IP、版本号这类网络标识，也宜披露）；若面向欧盟分发，
  IP 属个人数据（GDPR）。
- 建议（P1）：在「关于」页新增一个「联网与隐私」区块：列出会联网的功能、各自默认开关、
  访问的域名、发送什么内容、在哪里关闭；README 加同段。成本很低，收益是它同时缓解 M2/M4/H1 的「隐瞒」色彩。

### M4 · 未遵守部分上游 API 的服务条款

| 服务 | 事实 | 要求 / 风险 |
| :--- | :--- | :--- |
| **MusicBrainz** | 与其它来源共用浏览器 UA（`internal/coverfetch/http.go:21`），调用点 `internal/coverfetch/deezer.go:154`；无节流 | 官方明确要求 UA 内含**可联系的应用名/版本**，且 IP 平均 **1 req/s**（[Rate Limiting](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting)）；违反会被 503 封禁 |
| iTunes Search API | `internal/coverfetch/itunes.go:83` | Apple 对 Search API 的使用有独立条款（署名、缓存、用途限制），仓库内无核对记录 |
| Deezer / LRCLIB | `internal/coverfetch/deezer.go`、`internal/lyricsfetch/lrclib.go` | 各自的速率与再分发限制未核对 |

- 依据：这是**合同风险**（对方可封禁/发函），一般不产生行政或刑事责任；但若被认定大规模无授权抓取，可升级为不正当竞争。
- 建议（P1）：给 MusicBrainz 单独设置带项目地址的 UA 并加节流；
  （P2）逐条核对四家条款，在 `docs/` 留一份「上游服务条款核对记录」，便于条款变更时复查。

### M5 · 更新安装链路：第三方镜像 + 校验可选

- 事实：内置 7 个第三方 GitHub 加速代理（`internal/update/mirror.go:33-41`）；
  取不到 `SHA256SUMS.txt` 时 `Verified=false` 仍**继续允许安装**（`services_update.go:346-348`、`:419-445`）；
  安装时写 `.bat` 并启动独立进程替换自身 exe、重启（`services_update.go:462-528`）。
- 风险性质：不是知识产权，而是**「分发你无法控制的二进制」带来的产品/安全责任**。镜像被投毒时用户机器受损，
  用户会直接找分发者。Apache-2.0 的免责条款不能覆盖这种事实层面的过失主张。
- 建议（P1）：`Verified=false` 时必须**显式警告并要求二次确认**；
  （P2）在安装确认里展示「来源：github.com/…，通道：某代理」并建议优先直连官方 Releases。

## 4. 低风险与「做得对」的部分

- **许可证链是干净的**：Apache-2.0 + 内嵌自编译 FFmpeg（LGPL-2.1-or-later），
  以独立可执行文件分发、用户可替换，`NOTICE`、`THIRD-PARTY-NOTICES.md:160-173`、
  `internal/ffmpeg/bin/FFMPEG-LICENSE.txt` 齐备。
- **L1（需修）**：`THIRD-PARTY-NOTICES.md:177-189` 的「在线数据来源」表**漏了酷狗音乐**，
  而 `README.md:324-327` 与 `frontend/src/js/about-info.js:194-203` 都有 —— 对外声明应保持一致。
- **商标使用基本正确**：全部为指示性使用（说明调用了哪个服务），且三处都写了「无隶属或背书关系」
  （`README.md:322`、`THIRD-PARTY-NOTICES.md:191`、`about-info.js:217`）。注意不要在资源里使用对方 logo 图形。
- **L3 本地接口是可以的**：`/online/*` 全部强制 token（`services_online.go:363-367`、`:438-442`、`:463-466`）；
  封面代理有图床白名单且**重定向链每一跳复检**，并挡掉 IP 字面量，避免 SSRF（`internal/coverfetch/http.go:92-176`）；
  媒体服务只监听 `127.0.0.1`（`internal/media/server.go:294`）并校验 token（`:429`）。
  这些同时也是**合规缓释措施**（避免把自己的播放器变成任意站点的取流工具）。
- **不接触用户凭证**：无账号体系、无 Cookie 登录、无第三方 OAuth，个人信息暴露面很小。
- **AI 密钥不回传前端**（`services.go:1074-1104` + `config_secret_test.go`）—— 这一点做得比多数同规模项目好。
  唯一残留：密钥**明文存在 config.json**，属可接受但应在文档中说明的取舍。

## 5. 建议的最小整改清单

| 优先级 | 动作 | 落点 |

## 7. 未能确认的事项（如实声明）

- 各平台用户协议与 API 条款的**最新文本**（可随时变更），本报告只核对了 MusicBrainz 的官方速率页。
- B 站是否对「未登录状态下取音频轨」有明文禁止条款（公开文档中未检索到权威表述）。
- Apple Search API / Deezer / LRCLIB 条款中关于**缓存与再分发**的具体要求。
- 中国司法对「个人自用、开源、不营利的解析客户端」的裁判倾向：检索到的判例以**商业化、规模化**为主，
  不能直接外推到本项目。
- 若未来引入**收费（含赞助解锁）、云曲库、账号体系或应用商店上架**，风险等级需整体重新评估 ——
  那会同时触发信息网络传播行为、著作权授权需求，以及 ICP / 网络文化经营等资质问题。

### 1.2 总体结论

**这是一个工程质量明显高于同类个人项目的代码库，但当前处于「门禁失效 ＋ 一个文件的高危缺陷未修」的状态。**

三条最重要的判断：

1. **前几轮的核心性能问题确实修好了，且修复是可验证的。** 本次实测 `metadata-cache.json` 从历史记录的 5,867,147 B 降到 **18,056 B（−99.69%）**，文件内 `base64` 出现 0 次；曲库含 base64 封面走 IPC 的问题已从根上消除。`RescanPaths` 的持锁优化、`recalcVisible` 的输入签名 memo、`Intl.Collator` 复用等都是真实且带数字的改进。

2. **但防护网本身是破的。** 本次实测：
   - `npm run check`（项目自己的前端门禁）**退出码 2**，`tsc` 报 5 个真实类型错误；
   - `node tools/check-gofmt.mjs`（项目自己的格式门禁）**退出码 1**，报 6 个文件不合格；
   - 全仓**不存在任何 CI 配置**（`.github/workflows` 为空）。
   这解释了为什么「mock 假数据泄漏进生产构建」这类问题能长期存活：**没有任何自动检查在跑。**

3. **数据安全风险高度集中在一个文件。** 后端安全审查未发现任意文件读取或目录穿越（路径防护与 SSRF 白名单做得是对的），但 **`internal/metacache/embed.go` —— 唯一会改写用户音乐文件的那个文件 —— 存在 1 个已实测复现的 P1**（`findChildAbs` 缺 `size==0/1` → 按错误结构重写用户音频文件），以及若干加固项。另有一处原判为 P0 的 panic 经复核**不可达**，已订正为纵深防御问题（见 §2.6）。

### 2.5 本次审查对子代理结论的两处修正（重要）

> 审查的价值不仅在于发现问题，也在于**不把不存在的问题写进报告**。

**修正一：UX 子代理的 P0「设置页显示『保留 NaN 首』」→ 降级为「陈旧截图，当前不成立」。**

子代理依据 `docs/screenshots/05-settings-folders.png` 中「保留 **NaN** 首」判定为线上缺陷。主审回源核实：

- 该截图 **LastWriteTime = 2026/9/12**，且 `git log` 显示它属于**初始提交** `713d869`（2026-09-12）；
- 当前 HEAD 为 `1ccf51d`（**2026-09-19**），`frontend/dist` 构建于 2026/9/19 13:05；
- 即该截图比当前代码**旧 7 天、跨越多个提交**，是原型期产物；
- 对当前源码实测：`applyRules` 返回 `{kept: 数组, excluded: 数字, total: songs.length}`，`kept.length` **不可能为 NaN**；用截图里的规则（`10240` 字节 + `\.mp4$`）在 Node 里复跑，输出为 `保留 0 首`（数字），符合预期。

**结论**：`NaN` 在当前代码下**不复现**，不应作为本轮 P0。但**保留一条真实建议**：截图集已陈旧，应重新生成（见 UX 章 P3），否则后续审查会反复基于错误证据下判断。

**修正二：前端子代理标为 SUSPECTED 的「`data-time` 未转义可能是 XSS」→ 判定为「不可利用，已排除」。**

子代理发现 `lyrics-view.js:162/165` 与 `fx-lyrics.js:191/192` 的 `data-time="${l.time}"` 未套 `esc()`（同行 `data-text` 套了）。主审回源 `packages/player-skins/src/lrc.js`：

```js
// lrc.js:31-35
while ((m = TIME_TAG.exec(raw))) {
  const min = Number(m[1]);
  const sec = Number(m[2]);
  const frac = m[3] ? Number(`0.${m[3].padEnd(3, "0")}`) : 0;
  times.push((min * 60 + sec + frac) * 1000);   // ← 恒为 number
}
```

`parseLrc` 产出的 `time` **恒为 `Number` 运算结果**，不可能是字符串，因此**不存在注入面**。保留为 P3 一致性建议（与同行 `esc(text)` 不统一，容易被误认为漏洞）。

```go
udta := findChildAbs(raw, moovStart+8, moovEnd, "udta")   // ← 先经过这里
if udta < 0 { /* 走「追加新 udta」分支，根本不读 udtaSize */ }
udtaSize := int(binary.BigEndian.Uint32(raw[udta : udta+4]))
udtaEnd := udta + udtaSize                                 // ← 报告说这里会越界
```

`findChildAbs` **原本就有**检查 `if size < 8 || off+size > to { return -1 }`。**能返回合法 `udta` 偏移，就已蕴含 `udta+udtaSize <= moovEnd`**，`udtaEnd` 不可能越界。用修复前的代码实测确认：恶意超大 `udtaSize` 会让 `findChildAbs` 返回 `-1`，代码走「追加」分支，**不 panic**；`meta` 同理。

**订正后定性**：写法确实不安全（裸读长度即切片，一旦 `findChildAbs` 的检查被改动、或两行之间插入新逻辑，立刻变成崩溃），修复保留，但**严重度从 P0 降为「健壮性加固」**。原报告 §1.4 Top 10 里的第 1 条应据此看待。

**订正四：C-18「`ffmpeg.Probe` 缺 `-t 0`」→ 早已修复，属陈旧信息。**

报告（转述性能子报告）称其「前两轮提过两次未修」。实测 `internal/ffmpeg/ffmpeg.go` 的 `Probe` **已有 `-t 0`**，注释还写明了 48 文件批量探测的考量。**该条不成立。**

> 这两条订正说明同一件事：**子代理结论必须回源复核，主审自己的复现也要复核「可达性」**。本轮 4 条高危结论中 1 条错、1 条已修、2 条成立。

### 4.2 启动性能（正向为主）

启动路径的设计**已经过针对性优化**，本次未发现新的同步重活（【事实】）：

1. **元数据缓存惰性加载**：`library.go:114-117` 明确记录「5.9MB JSON 的同步 `json.Unmarshal` 发生在建窗口之前，是首屏里最贵的一段」，改为首次真正用到时才读（`ensureCacheLoaded`）。
2. **ffmpeg 后台 prewarm**：`main.go:112-129` 在 goroutine 里解包；`internal/ffmpeg/ffmpeg.go` 的 `bundledIdentity()` 用 gzip 尾部 ISIZE **免解压**即可算出缓存名 —— 热启动只需 hash 2.21 MB + 一次 `stat`，不解压 5.99 MB。设计精巧。
3. **窗口隐藏创建 + 首帧过渡图**：`main.go:316-339` 用 `Hidden: true` 避开 WebView2 白底首帧，配合 `boot_frame.go` 缓存上次退出画面、`early_theme.go` 在首帧前注入主题色，并有 `MarkReady` 的 1.5s/4s 兜底重试。
4. **首帧信号走 HTTP 而非 JS 绑定**：`main.go:205-231` 注释说明「JS→Go 绑定那条链路要交给宿主线程，实测能晚到近一秒」，故用 `/boot/reveal` 普通 HTTP 请求。这是**基于实测的正确取舍**。

### 4.4 CPU / GPU 与渲染

- **magia** 是唯一仍不达标的样式（43 fps，`follow()` 占 48% 采样）。归因是**每帧同步布局**，加帧率上限只会掩盖问题。`docs/24` §3.5 已给出正确解法方向（改用「前缀测量 + `background-clip: text` + mask 扫过」替代「每字素一个 span + 每字素一个动画」）。
- **C-17** 使增量重扫（丢一个文件即触发）也要拉两遍整库 —— 这是**高频路径上的浪费**，修复性价比很高。
- **待测量（收益可能很大）**：`F-10` 桌面背景歌词窗口 = **第二份皮肤实例**。本机 `config.json` 实测 `showDesktopWallpaper: true`，若开机同时运行主窗口皮肤 + 壁纸皮肤，等于**两份渲染开销**。一条 `Get-Process` 就能出数，建议优先测。

- 无数据库（项目不使用 SQLite；数据目录里的 `musicplayer.db` 是**早期遗留孤儿**）。

### 4.6 卡顿与响应延迟

- 曲目表首帧 2,882 ms（5,000 首）是**最影响"能不能用"的一项**。
- 扫描期间的后端进度推送（每 40 个文件一次）已被 `recalcVisible` 的输入签名 memo 挡住（`store.js:587-612` 明确记录「实测 5,000 首一次 ≈ 20ms；20,000 首就是 500 次 ≈ 10 秒纯主线程占用」）—— ✅ **已修复**。
- `runtime.js` 用 250ms 依赖键把进度类副作用压到 4 Hz —— ✅ 设计合理。

### 4.7 包体与构建性能

- 构建入口 `Taskfile.yml` → `common:build:frontend` + `go build`；前端 `tools/build-frontend.mjs` 收尾拷贝绑定与内置主题。
- **体积构成（实测，重要）**：Go 运行时 + Wails **82%** / ffmpeg.gz **13.4%** / 前端 dist **4.6%**。
- `vite.config.js` 已开启 `reportCompressedSize` 并把 `chunkSizeWarningLimit` 从 900 降到 320（注释说明「900 意味着 Rollup 永远不会对最大产物报警」）—— ✅ 有意识的改进。
- 构建时间：**未测量**（待补充材料）。
